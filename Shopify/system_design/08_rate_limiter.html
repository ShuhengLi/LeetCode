Design a Rate Limiting System for the Shopify API为 Shopify API 设计限流系统

Shopify exposes REST and GraphQL APIs to millions of apps and merchants. The rate limiter must protect the platform from abuse and overload while being scrupulously fair across tenants — one rogue app must never exhaust capacity that other merchants depend on.Shopify 向数百万应用和商户开放 REST 和 GraphQL API。限流系统必须保护平台免受滥用和过载，同时在租户间保持严格公平——一个行为异常的应用不能耗尽其他商户所依赖的容量。

Seen: platform/infrastructure framing考察方向：平台/基础设施架构 Tests: multi-tenancy + distributed correctness考点：多租户 + 分布式正确性 60 min
Why this question is interesting at Shopify specifically为什么这道题在 Shopify 面试中特别有意思 Shopify's real API model is non-trivial: REST uses a leaky/token bucket (burst + steady refill), while GraphQL uses calculated query cost because a single GraphQL call can be arbitrarily expensive — fetching thousands of orders in one request costs far more than fetching a single product. Request-count alone is the wrong metric for GraphQL. Frame your answer around fairness + platform protection across a multi-tenant, multi-protocol API surface.Shopify 真实的 API 模型并不简单：REST 使用漏桶/令牌桶（突发 + 稳定补充），而 GraphQL 使用计算查询成本——因为一次 GraphQL 调用的代价可以差异极大，一次请求拉取数千条订单比拉取单个产品耗费的服务器资源多得多。对于 GraphQL，单纯统计请求次数是错误的度量方式。你的回答应围绕在多租户、多协议 API 层面的公平性与平台保护来展开。

Clarify requirements澄清需求

~7 min · ask, don't assume约 7 分钟 · 主动提问，不要假设

Functional功能性需求

  • Limit requests per API client: per shop, per app, per access token.按 API 客户端限流：按商店、按应用、按访问令牌分别计算。
  • Support REST (request-count) and GraphQL (cost-based points).同时支持 REST（请求次数计费）和 GraphQL（基于成本积分）。
  • Return clear 429 Too Many Requests with Retry-After and rate-limit headers.返回清晰的 429 Too Many Requests，并附带 Retry-After 和限流响应头。
  • Configurable limits per plan/tier (Basic, Advanced, Plus, Partner).按套餐/等级（Basic、Advanced、Plus、Partner）可配置限额。
  • GraphQL response includes query cost breakdown: points requested, available, restore rate.GraphQL 响应中包含查询成本明细：请求积分、可用积分、恢复速率。

Non-functional非功能性需求

  • Distributed enforcement across many gateway nodes — no per-node blindspot.分布式强制执行——跨多个网关节点，不存在单节点盲区。
  • Low added latency — limiter check must be a single-digit-ms fast path.低附加延迟——限流检查必须是个位数毫秒的快速路径。
  • High accuracy — avoid badly over- or under-counting; short-term approximation acceptable.高准确性——避免严重的多计或漏计；短期近似可接受。
  • Resilient — graceful behavior when the limiter store is degraded.高可用——限流存储降级时能优雅降级。
  • Multi-tenant fairness — one shop/app must not starve others on the platform.多租户公平性——一个商店/应用不得抢占其他商户在平台上所需的资源。
Clarifying questions to ask out loud面试时应主动提出的澄清问题
  • What is the primary limit dimension — per shop, per app, or per access token? (All three; they compose.)主要限流维度是什么——按商店、按应用，还是按访问令牌？（三者都有，且相互叠加。）
  • REST, GraphQL, or both? Different algorithms apply.限制 REST、GraphQL，还是两者都包含？不同协议适用不同算法。
  • Hard vs soft limits — strict 429 or graceful degradation with warnings first?硬限制还是软限制——严格返回 429，还是先发出警告再优雅降级？
  • Global limits or per-region limits? Affects consistency model.全局限制还是按地区限制？这将影响一致性模型的选择。
  • If the Redis store is unavailable — fail open (allow requests, risk overload) or fail closed (block all, risk SLA breach)?如果 Redis 存储不可用——失败开放（放行请求，有过载风险）还是失败关闭（拦截所有请求，有 SLA 违约风险）？

Capacity estimation容量估算

find the binding constraint找到瓶颈约束

The key insight: the rate limiter is in the hot path of every API call. It must add minimal latency, which means the check must be a single cheap operation — one Redis round trip — not a read-modify-write fan-out.核心洞察：限流器处于每次 API 调用的热路径上。它必须只增加极小的延迟，这意味着检查操作必须是单次廉价操作——一次 Redis 往返请求——而不是读-改-写的扇出操作。

  • Redis ops per request: must be ~1 (an atomic Lua script = one round trip). At 500k QPS that is 500k Redis ops/s — achievable on a small sharded cluster since each op is a tiny key read-modify-write.每请求 Redis 操作数：必须约为 1 次（一个原子 Lua 脚本 = 一次往返）。在 500k QPS 下，这意味着 50 万次 Redis 操作/秒——在小型分片集群上完全可行，因为每次操作只是一次微小的键读-改-写。
  • Key space: 10M buckets × ~32 bytes each ≈ 320 MB. Fits comfortably in memory; no persistence needed beyond the TTL of the bucket window.键空间：1000 万个桶 × 约 32 字节/桶 ≈ 320 MB。完全能放入内存；除桶窗口的 TTL 之外，无需持久化。
  • Hot-key risk: some shops generate far more traffic than others. Shard Redis by clientId hash so no single shard becomes a bottleneck. A single flash-sale merchant should not saturate the limiter for everyone else.热键风险：某些商店产生的流量远多于其他商店。按 clientId 哈希对 Redis 分片，确保单个分片不成为瓶颈。一个正在举办闪购活动的商户不应耗尽整个平台的限流容量。
  • Gateway nodes: stateless; the limiter middleware makes one async call to Redis per request. No per-node state.网关节点：无状态；限流中间件每次请求向 Redis 发起一次异步调用，节点本身不保存任何状态。

The rate limiter is gateway middleware, not a separate user-facing service. Its observable contract is the set of response headers it injects on every request and the 429 it emits when a bucket is exhausted.限流器是网关中间件，而非独立的用户端服务。其对外可见的契约是：在每次请求中注入的一组响应头，以及当令牌桶耗尽时返回的 429 状态码。

Data model数据模型

Redis: token-bucket state per clientRedis：每个客户端的令牌桶状态

-- Key schema (bucket per client)
bucket:{shopId}:{appId}          // REST bucket: tokens + last_refill_ts (HASH)
gql_bucket:{shopId}:{appId}      // GraphQL cost bucket: points + last_refill_ts (HASH)

-- HASH fields
tokens          // current token/point count (float or integer)
last_refill     // Unix ms timestamp of last computed refill

Config store: per-plan rate-limit config配置存储：按套餐的限流配置

-- Postgres / config table (cached in-process, refreshed every 30 s)
rate_limit_config(
  plan_tier         -- 'basic' | 'advanced' | 'plus' | 'partner'
  api_type          -- 'rest' | 'graphql'
  bucket_capacity   -- max tokens / points
  refill_rate       -- tokens or points per second
  burst_capacity    -- optional burst ceiling above steady state
)

Atomic Lua script — token bucket check + refill + decrement原子 Lua 脚本——令牌桶检查 + 补充 + 扣减

-- KEYS[1] = bucket key
-- ARGV[1] = now (Unix ms)  ARGV[2] = cost  ARGV[3] = capacity  ARGV[4] = refill_rate (pts/ms)

local data       = redis.call('HMGET', KEYS[1], 'tokens', 'last_refill')
local tokens     = tonumber(data[1]) or tonumber(ARGV[3])
local last       = tonumber(data[2]) or tonumber(ARGV[1])
local elapsed    = tonumber(ARGV[1]) - last
local refilled   = math.min(tonumber(ARGV[3]),
                     tokens + elapsed * tonumber(ARGV[4]))

if refilled < tonumber(ARGV[2]) then
  -- update last_refill without deducting; return remaining + ms until enough
  redis.call('HSET', KEYS[1], 'tokens', refilled, 'last_refill', ARGV[1])
  redis.call('PEXPIRE', KEYS[1], 3600000)
  return {0, math.ceil((tonumber(ARGV[2]) - refilled) / tonumber(ARGV[4]))}
end

local remaining = refilled - tonumber(ARGV[2])
redis.call('HSET', KEYS[1], 'tokens', remaining, 'last_refill', ARGV[1])
redis.call('PEXPIRE', KEYS[1], 3600000)
return {1, remaining}   -- {allowed, remaining}

The entire check-refill-decrement sequence is one atomic round trip to Redis — no race conditions possible regardless of how many gateway nodes are running concurrently.整个检查-补充-扣减序列是对 Redis 的一次原子往返请求——无论有多少网关节点并发运行，都不可能产生竞态条件。

High-level architecture高层架构

gateway middleware → shared Redis → upstream services网关中间件 → 共享 Redis → 上游服务
client edge / gateway service cache / bucket store (Redis) config / datastore
Every gateway node runs the limiter middleware synchronously. The shared Redis cluster is the single source of truth for bucket state. Requests that exceed the limit get a 429 at the gateway; allowed requests flow to upstream services with rate-limit headers injected.每个网关节点同步执行限流中间件。共享 Redis 集群是令牌桶状态的唯一权威来源。超过限额的请求在网关层直接返回 429；被放行的请求在注入限流响应头后转发至上游服务。

Component walk-through组件详解

  • API Clients — apps, merchants, and partners sending REST or GraphQL API requests. All traffic enters through the gateway tier.API 客户端——发送 REST 或 GraphQL API 请求的应用、商户和合作伙伴。所有流量均通过网关层进入。
  • Gateway nodes (stateless) — each node runs the same limiter middleware. On every request, the middleware resolves the clientId (shop + app from the access token), loads the limit config from the local cache, and fires one atomic Lua call to Redis.网关节点（无状态）——每个节点运行相同的限流中间件。每次请求时，中间件从访问令牌中解析出 clientId（商店 + 应用），从本地缓存加载限额配置，然后向 Redis 发起一次原子 Lua 调用。
  • Redis Cluster (sharded by clientId) — the authoritative bucket store. Each shard holds a portion of the 10M+ client buckets. The Lua script atomically computes elapsed-time refill, checks whether the request's cost fits, decrements if so, and returns the result — all in one network round trip.Redis 集群（按 clientId 分片）——权威令牌桶存储。每个分片持有 1000 万以上客户端桶中的一部分。Lua 脚本原子性地计算时间流逝后的补充量、检查请求成本是否足够、若足够则扣减，并返回结果——全部在一次网络往返内完成。
  • Config Service — holds per-plan limit config (capacity, refill rate). Gateways cache this locally for 30 s so a Redis call is not needed just to look up limits. Updates propagate within one cache TTL.配置服务——保存按套餐的限额配置（容量、补充速率）。网关在本地缓存 30 秒，无需为查询限额而调用 Redis。配置更新在一个缓存 TTL 内传播到所有节点。
  • Upstream Services — only reached if the request is allowed. Rate-limit headers are injected before forwarding. REST and GraphQL handlers apply their respective charging models.上游服务——仅在请求被放行时才会被访问。转发前注入限流响应头。REST 和 GraphQL 处理器分别应用各自的计费模型。
  • 429 fast path — rejected requests are terminated at the gateway immediately, before any upstream compute is consumed. The Retry-After value is computed from the Lua return value (ms until bucket refills enough) so clients can back off precisely.429 快速路径——被拒绝的请求在网关层立即终止，不会消耗任何上游计算资源。Retry-After 值由 Lua 脚本返回值（桶补充至足够量所需毫秒数）精确计算得出，使客户端能够精准退避。

① Algorithm comparison — choosing the right bucket model① 算法对比——选择正确的桶模型

Multiple algorithms exist; Shopify's REST API uses a leaky bucket / token bucket. Understanding why is as important as knowing how.限流算法有多种；Shopify 的 REST API 使用漏桶/令牌桶。理解"为什么"与理解"怎么做"同等重要。

② GraphQL cost-based limiting — why request count is wrong② GraphQL 基于成本的限流——为何请求次数计费是错的

A single GraphQL query can be trivially cheap ({ shop { name } }) or extremely expensive ({ orders(first:250) { lineItems(first:100) { ... } } }). Counting them equally would allow one deeply-nested query to consume as much server compute as 10,000 simple queries.一次 GraphQL 查询可以非常廉价（{ shop { name } }），也可以极其昂贵（{ orders(first:250) { lineItems(first:100) { ... } } }）。若将它们等同计数，一个深度嵌套的查询就能消耗相当于 10,000 次简单查询的服务器计算资源。

Shopify computes a query cost from the requested fields and connection limits using a static analysis pass over the parsed query AST before execution:Shopify 在执行前对已解析的查询 AST 进行静态分析，根据所请求的字段和连接限制计算查询成本：

-- Shopify's model: an object costs 1, a scalar costs 0, and a connection
-- costs (first|last) × (cost of one node). Computed on the parsed AST, before execution.

def cost(selection):
    total = 0
    for field in selection:
        if field.is_connection:
            n = field.arg('first') or field.arg('last') or 1
            total += n * (1 + cost(field.selection))   # n nodes, each = 1 + its children
        elif field.is_object:
            total += 1 + cost(field.selection)
        # scalar fields add 0
    return total

-- Example: orders(first:10) { lineItems(first:5) { title } }
--   lineItems = 5 * (1 + 0) = 5;   orders = 10 * (1 + 5) = 60 points

The client's GraphQL point bucket typically has capacity ~1000 points, restoring at 50 points/second. The computed cost is deducted atomically at request time. If the estimated cost exceeds available points, the request is throttled before execution — no server compute wasted.客户端的 GraphQL 积分桶容量通常约为 1000 积分，每秒恢复 50 积分。计算出的成本在请求时原子性地扣除。若估算成本超过可用积分，请求将在执行之前被限流——不浪费任何服务器计算资源。

Static vs runtime cost静态成本 vs 运行时成本 Static analysis (before execution) is fast but approximate — a query asking for orders(first:250) may actually return 3 orders if few exist. So the limiter gates on the requested (estimated) cost up front — you cannot know the real cost before running — then records the actualQueryCost and refunds the difference (requested − actual) back into the bucket after execution.静态分析（执行前）速度快但存在近似误差——一个请求 orders(first:250) 的查询，若数据库中订单数量少，实际可能只返回 3 条记录。因此限流器以请求时的（估算）成本为门控依据——在执行之前无法得知真实成本——随后记录 actualQueryCost，并在执行后将差值（估算 − 实际）退还回令牌桶。

③ Distributed enforcement — centralized Redis vs per-node local buckets③ 分布式强制执行——集中式 Redis vs 节点本地桶

With 100 gateway nodes, each request can land on any node. Two enforcement approaches:在 100 个网关节点的情况下，每个请求可能落在任意节点上。有两种强制执行方式：

Centralized Redis (recommended)集中式 Redis（推荐）

One authoritative bucket store单一权威令牌桶存储

Every gateway node calls the Redis cluster for every request. Accuracy is near-perfect: all nodes share the same view of each client's bucket.每个网关节点对每次请求都调用 Redis 集群。准确性接近完美：所有节点共享同一个客户端桶视图。

Cost: one network round trip per request (~1–3 ms local AZ); Redis becomes a critical path dependency.代价：每次请求一次网络往返（同可用区约 1–3 ms）；Redis 成为关键路径依赖。

Per-node local buckets + async sync节点本地桶 + 异步同步

Each node tracks a fraction of the budget每个节点跟踪预算的一部分

Each node holds a local bucket (1/N of the total budget). No network hop per request; extremely fast. Nodes reconcile periodically.每个节点持有本地桶（总预算的 1/N）。每次请求无需网络跳转，极快。节点定期对账。

Cost: approximate — a client can exceed the global limit by up to N× in the worst case (N = node count) before sync catches up.代价：近似——在同步跟上之前，最坏情况下客户端可超出全局限额最多 N 倍（N = 节点数）。

Race conditions without atomicity缺乏原子性导致的竞态条件 If you implement the bucket check as separate GET → compute → SET operations without Lua atomicity, two gateway nodes can read the same bucket value simultaneously, both decide the request is allowed, and both decrement — effectively allowing 2× the intended traffic. This is a classic TOCTOU (time-of-check-time-of-use) race. The Lua script eliminates this entirely: Redis executes it as a single atomic unit with no interleaving possible. Never implement rate limiting with non-atomic multi-command sequences in Redis.如果将桶检查实现为独立的 GET → 计算 → SET 操作而不使用 Lua 原子性，两个网关节点可能同时读取相同的桶值，都判断请求被允许，然后都进行扣减——实际上放行了 2 倍预期流量。这是经典的 TOCTOU（检查时间-使用时间）竞态条件。Lua 脚本完全消除了这一问题：Redis 将其作为单个原子单元执行，不可能发生任何交错。永远不要用 Redis 的非原子多命令序列来实现限流。
Hot-key / hot-shard risk热键/热分片风险 A high-traffic merchant making 50k QPS can concentrate all those requests on a single Redis shard (since the key is bucket:{shopId}:{appId}). Mitigations: (a) shard the Redis cluster by clientId hash so each shard handles a different subset; (b) for the very hottest clients, consider a short-TTL local token cache on the gateway (e.g. pre-purchase a batch of 100 tokens, use them locally, then replenish) — this trades slight over-admission for a 100× reduction in Redis ops for that client.一个产生 50k QPS 的高流量商户会将所有请求集中到单个 Redis 分片（因为键为 bucket:{shopId}:{appId}）。缓解措施：(a) 按 clientId 哈希对 Redis 集群分片，使每个分片处理不同的客户端子集；(b) 对于流量最高的客户端，考虑在网关上使用短 TTL 的本地令牌缓存（例如预先购买 100 个令牌批次，本地消耗，再补充）——以轻微的超额放行换取该客户端 Redis 操作量减少 100 倍。

④ Multi-tenant fairness — per-shop and per-app limits that compose④ 多租户公平性——按商店和按应用限额的叠加组合

A single access token represents a specific app installed on a specific shop. Shopify's real model enforces limits at multiple dimensions:单个访问令牌代表安装在特定商店上的特定应用。Shopify 的真实模型在多个维度上强制执行限额：

  • Per-shop limits: each shop has a global API budget (across all installed apps). Prevents a shop from collectively exceeding platform-safe traffic.按商店限额：每个商店拥有全局 API 预算（涵盖所有已安装应用）。防止一个商店的总请求量超出平台安全阈值。
  • Per-app limits: each app has a per-shop budget. Prevents one noisy app from consuming all the shop's budget and starving other apps installed on the same shop.按应用限额：每个应用拥有按商店计算的预算。防止一个吵闹的应用耗尽商店的全部预算，从而饿死同一商店上安装的其他应用。
  • Per-access-token limits: for fine-grained tracking and revocation.按访问令牌限额：用于精细化跟踪和撤销。
  • Tiered by plan: a Shopify Plus merchant gets a larger bucket than a Basic plan merchant, reflecting their higher entitlement.按套餐分级：Shopify Plus 商户获得比 Basic 套餐商户更大的桶，反映其更高的权益。
  • Per-endpoint cost: certain endpoints (e.g. bulk operations, product list) can carry a higher per-request cost multiplier.按端点成本：某些端点（如批量操作、产品列表）可携带更高的每请求成本系数。

In practice the gateway checks the most-restrictive bucket that applies: if the per-app budget is exhausted, the request is rejected even if the per-shop budget still has room.实际上，网关检查适用的最严格桶：如果按应用预算已耗尽，即使按商店预算仍有余量，请求也会被拒绝。

Redis outage — fail open or closed? How do you implement the fallback?Redis 宕机——失败开放还是失败关闭？如何实现降级兜底？

Fail open with a conservative local cap is the right call for a platform where merchant revenue depends on availability. Implementation: each gateway node maintains an in-memory token bucket per client (initialized on first request, sized at global_limit / node_count). When Redis is unreachable (detected by circuit breaker with ~100 ms timeout), the middleware falls back to the in-memory bucket. Log every fallback event. When Redis recovers, flush local state and revert to the centralized path. The over-admission window is bounded to the outage duration and the local cap.对于一个商户收入依赖可用性的平台，失败开放加保守本地限流兜底是正确选择。实现方式：每个网关节点为每个客户端维护一个内存令牌桶（首次请求时初始化，大小为 global_limit / node_count）。当 Redis 不可达（通过约 100 ms 超时的熔断器检测到）时，中间件回退到内存桶。记录每个降级事件。Redis 恢复后，清空本地状态，恢复到集中式路径。超额放行窗口受限于宕机持续时间和本地限额。

Clock skew across gateway nodes — does it affect correctness?网关节点间的时钟偏差——会影响正确性吗？

Clock skew matters because the token-bucket Lua script uses now to compute elapsed time for refill. If two nodes disagree on now by Δt, the computed refill can differ by Δt × refill_rate — for a 50 pts/s refill rate and 100 ms clock skew, the error is only 5 points, which is negligible for a 1000-point bucket. Use NTP with sub-10ms accuracy (standard in cloud environments). Pass now as a Lua argument from the gateway (Redis itself has its own clock via TIME); if you want to avoid gateway-clock dependency entirely, use redis.call('TIME') inside the Lua script to get the Redis server's clock — this eliminates gateway clock skew entirely and is the more robust approach.时钟偏差是有影响的，因为令牌桶 Lua 脚本使用 now 来计算补充的时间间隔。如果两个节点对 now 的认知相差 Δt，计算出的补充量就会相差 Δt × refill_rate——对于 50 积分/秒的补充速率和 100 ms 的时钟偏差，误差仅为 5 积分，对于 1000 积分的桶来说可以忽略不计。使用精度低于 10 ms 的 NTP（云环境标配）。将 now 从网关作为参数传入 Lua（Redis 本身通过 TIME 命令提供时钟）；如果想完全避免对网关时钟的依赖，可在 Lua 脚本内使用 redis.call('TIME') 获取 Redis 服务器时钟——这完全消除了网关时钟偏差，是更健壮的做法。

Bursty vs sustained traffic — how does the token bucket handle legitimate bursts?突发流量 vs 持续流量——令牌桶如何处理合理的突发？

This is a feature of the token bucket design, not a problem. An app that has been idle for 10 seconds accumulates 10 × refill_rate tokens up to bucket capacity. It can then fire a burst of that many requests without being throttled — the cost is paid from the accumulated reserve. Sustained traffic above the refill rate will drain the bucket and get throttled. This is exactly the intended behavior: absorb legitimate bursts (e.g. a cron job that processes orders in batches once per minute) while bounding sustained throughput. The bucket capacity controls burst size; the refill rate controls sustained throughput. Both are configurable per plan tier.这是令牌桶设计的特性，而非问题。一个空闲了 10 秒的应用最多可积累 10 × refill_rate 个令牌至桶的容量上限，然后可以发出同等数量的突发请求而不被限流——成本从积累的储备中扣除。持续超过补充速率的流量会耗尽令牌桶并触发限流。这正是预期行为：吸收合理的突发（例如每分钟批量处理订单的定时任务），同时限制持续吞吐量。桶容量控制突发大小，补充速率控制持续吞吐量，两者均可按套餐等级配置。

Ensuring distributed correctness without Redis becoming a central bottleneck如何在不让 Redis 成为中心瓶颈的前提下保证分布式正确性？

Three strategies compose: (1) Shard Redis by clientId hash — each shard serves a disjoint set of clients, so throughput scales linearly with shard count. No single shard sees the full platform QPS. (2) Token pre-purchase for ultra-hot clients — the gateway pre-purchases a batch of tokens (e.g. 100) from Redis and serves them locally, reducing Redis ops by 100×. The gateway re-purchases when the local reserve drops below a threshold. This trades a bounded over-admission window for dramatically lower Redis pressure on hot keys. (3) Pipeline or connection pooling — use persistent Redis connections from each gateway node; avoid per-request connection overhead.三种策略组合使用：(1) 按 clientId 哈希对 Redis 分片——每个分片服务于不相交的客户端集合，吞吐量随分片数线性扩展，没有单个分片会承受全平台 QPS。(2) 对超热客户端使用令牌预购——网关从 Redis 预购一批令牌（如 100 个）并在本地消耗，将 Redis 操作量减少 100 倍；本地储备低于阈值时再补购，以有界的超额放行窗口换取热键 Redis 压力的大幅降低。(3) Pipeline 或连接池——每个网关节点使用持久 Redis 连接，避免每次请求的连接开销。

Estimating GraphQL query cost accurately — static vs runtime tradeoffs精确估算 GraphQL 查询成本——静态 vs 运行时权衡

Static analysis runs on the parsed query AST before execution. It is fast (sub-millisecond) but approximate: a query requesting orders(first:250) may actually return 3 orders, costing far less server compute than estimated. Three strategies: (a) Charge static estimate, no refund — simple, conservative; clients learn to write efficient queries. (b) Charge static, refund delta — deduct the static cost upfront, then issue a credit for estimated - actual after execution; accurate but requires a second async Redis write. (c) Require explicit cost hints — clients declare their expected cost in the request header; server validates against static analysis with a tolerance band. Shopify uses a variant of (a) with the static estimate as the charged cost, but exposes actualQueryCost in the response so clients can tune their queries.静态分析在执行前对解析后的查询 AST 运行，速度快（亚毫秒级）但存在近似误差：一个请求 orders(first:250) 的查询实际可能只返回 3 条订单，消耗的服务器计算资源远少于估算值。三种策略：(a) 按静态估算收费，不退款——简单保守；客户端会学着编写高效查询。(b) 按静态估算收费，退还差值——预先扣除静态成本，执行后针对 估算 - 实际 发放积分退款；精确，但需要一次额外的异步 Redis 写入。(c) 要求显式成本提示——客户端在请求头中声明预期成本，服务器以容差带对照静态分析进行验证。Shopify 使用 (a) 的变体，以静态估算作为计费成本，但在响应中暴露 actualQueryCost，供客户端优化查询。

Per-region vs global limits — how do you keep them consistent?按地区 vs 全局限额——如何保持一致性？

Pure per-region limits: a client gets a full bucket per region, effectively multiplying their allowed throughput by the number of regions. This is often acceptable — most clients only call from one region. If a client geographically distributes their API calls to circumvent limits, the fix is global limit accounts: a thin cross-region consensus service (or a CRDTs-based distributed counter) holds the global truth. Each region's Redis runs a local sub-bucket; the global service periodically reconciles and adjusts regional allocations. This adds complexity and cross-region latency — deploy it only if global arbitrage is an observed abuse pattern. For most Shopify partners, per-region is sufficient and the simpler choice.纯按地区限额：客户端在每个地区获得完整的令牌桶，实际上将允许的吞吐量乘以地区数。这通常是可接受的——大多数客户端只从一个地区发起调用。如果客户端通过地理分散 API 调用来规避限制，解决方案是全局限额账户：一个轻量的跨地区共识服务（或基于 CRDT 的分布式计数器）持有全局真相；每个地区的 Redis 运行本地子桶，全局服务定期对账并调整各地区分配。这增加了复杂性和跨地区延迟——只有在观察到全局套利滥用模式时才部署。对大多数 Shopify 合作伙伴而言，按地区方案已足够且更简单。

How do you communicate limits to clients so they back off gracefully?如何将限流信息传达给客户端，使其能够优雅地退避？

Every response must carry the standard rate-limit headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, and — on a 429 — a Retry-After header with the precise number of seconds until the bucket refills enough to permit the next request. This value comes directly from the Lua script return value, so it is accurate to the millisecond. For GraphQL, embed the cost metadata in extensions.cost on every response (not just throttled ones) so clients can self-pace before hitting the limit. SDKs should implement automatic retry with jitter (randomized delay around the Retry-After value) to prevent thundering-herd re-entry after a burst. Document the headers and the cost model clearly in the API reference — a well-informed developer writes adaptive code; a confused one hammers retries.每次响应都必须携带标准限流头部：X-RateLimit-Limit、X-RateLimit-Remaining、X-RateLimit-Reset，以及在返回 429 时附上 Retry-After 头部，精确表示距桶内令牌恢复到允许下一次请求所需的秒数。该值直接来自 Lua 脚本返回值，精度到毫秒。对于 GraphQL，应在每次响应的 extensions.cost 中嵌入成本元数据（不仅限于被限流的响应），让客户端在触达限流前主动调速。SDK 应实现带 jitter（在 Retry-After 值附近随机抖动）的自动重试，以防止大批请求在爆发后同时重入造成"惊群效应"。在 API 文档中清晰说明这些头部字段及成本计算模型——开发者信息充分才会编写自适应代码，否则只会盲目不断重试。

How do you allow short bursts but cap sustained abuse?如何允许短时突发流量，同时限制持续滥用？

This is the core insight of the token bucket: the two knobs — bucket depth (capacity) and refill rate — control burst and sustained throughput independently. Set capacity = burst_ceiling (e.g. 80 tokens for Shopify Plus) to allow a legitimate burst of that many requests immediately after an idle period. Set refill_rate = sustained_limit (e.g. 4 tokens/second) to cap how fast the bucket recovers, which bounds sustained throughput. A client can fire 80 requests in a second, then is limited to 4/s thereafter until it goes idle again. Tune these parameters per plan tier and monitor the distribution of actual burst sizes in production — a burst ceiling that trips 10% of legitimate Plus merchants is misconfigured.这正是 token bucket 的核心设计：桶深度（容量）与补充速率这两个参数相互独立地控制突发量和持续吞吐量。将 capacity 设置为突发上限（例如 Shopify Plus 为 80 个令牌），以允许在空闲期后立即发出同等数量的请求。将 refill_rate 设置为持续限速（例如每秒 4 个令牌），限制桶的恢复速度，从而约束持续吞吐量。客户端可以在一秒内发出 80 次请求，此后每秒只能发出 4 次，直到再次进入空闲状态。应按套餐等级分别调整这两个参数，并在生产环境中监控实际突发大小的分布——如果突发上限会触发 10% 的合法 Plus 商户被限流，说明配置有误。

A trusted partner needs a higher limit — how do you configure tiers dynamically?受信任的合作伙伴需要更高限额——如何动态配置等级？

The limit config must be externalized from the gateway binary into a config service (e.g. a small Postgres table or a dedicated feature-flag store). Each row in the rate_limit_config table represents a plan/tier (Basic, Advanced, Plus, Partner, or a named partner override). The gateway caches this in-process with a 30-second TTL; a hot-reload event or a short TTL expiry picks up new values without a redeploy or restart. To grant a specific partner a higher limit, insert or update a row for their clientId (or plan tag) and push the change to the config store — all gateways reflect it within one TTL window. This pattern also supports A/B testing of limit values and emergency throttle-down by pushing a config change, not a code change.限流配置必须从网关代码中抽离，存入独立的配置服务（例如一张小的 Postgres 表或专用的功能开关存储）。rate_limit_config 表中的每一行代表一个套餐/等级（Basic、Advanced、Plus、Partner 或指定合作伙伴的覆盖配置）。网关在进程内缓存该配置，TTL 为 30 秒；缓存过期或热重载事件会自动拉取新值，无需重新部署或重启服务。若要为特定合作伙伴授予更高限额，只需在配置表中插入或更新该合作伙伴的 clientId（或套餐标签）对应的行，变更推送到配置存储后，所有网关节点会在一个 TTL 窗口内生效。这一模式同样支持限流值的 A/B 测试，以及通过推送配置变更（而非代码变更）实现紧急降流。

How do you rate-limit unauthenticated/login endpoints to stop credential stuffing?如何对未认证/登录端点进行限流以阻止撞库攻击？

Authentication endpoints require a different limiting strategy because the client identity is unknown before the request succeeds. Apply two independent buckets in parallel: a per-IP bucket (blocks volumetric attacks from a single source) and a per-account bucket (blocks distributed attacks targeting one account from many IPs). Set the limits stricter than regular API endpoints — e.g. 5 failed login attempts per account per 15 minutes rather than the normal request-per-second budget. On repeated failures, escalate progressively: first return a rate-limit header, then introduce a Retry-After delay with exponential backoff (10 s → 30 s → 5 min), then trigger a CAPTCHA challenge or lock the account pending email verification. Never disclose via the error response whether the account exists, as that leaks account enumeration information to attackers.认证端点需要不同的限流策略，因为在请求成功之前客户端身份尚不明确。应并行应用两个独立的令牌桶：一个基于 IP（拦截来自单一来源的大流量攻击），另一个基于账号（拦截来自多个 IP 针对同一账号的分布式攻击）。限制阈值应比常规 API 端点更严格——例如每个账号每 15 分钟最多允许 5 次失败登录，而非正常的每秒请求配额。在多次失败后采用递进升级策略：首先返回限流头部，然后引入带指数退避的 Retry-After 延迟（10 秒 → 30 秒 → 5 分钟），再触发 CAPTCHA 验证或锁定账号等待邮件确认。错误响应中切勿暴露账号是否存在，避免攻击者利用账号枚举漏洞。

How is the distributed counter kept accurate during Redis cluster resharding?Redis 集群重新分片期间，分布式计数器如何保持准确？

Resharding moves hash slots between Redis nodes, which means a bucket key can be temporarily unavailable or in-flight during the migration. Two mitigations work together. First, use hash-tag keys (bucket:{shopId}:{appId} is fine as written — the curly-brace tag ensures the key always routes to the slot of shopId:appId), so the key's slot is stable and the atomic Lua script runs entirely on one node with no cross-slot issues. Second, during a live resharding event, the Redis Cluster protocol may return a MOVED or ASK redirect for the migrating slot; the client library follows the redirect transparently. For the brief window while a key is being migrated, the worst case is a slightly stale counter or a single request that sees an empty bucket and behaves as if it is a new client. Handle this by treating MOVED/ASK errors with a fail-open local cap (as in the Redis-down path) — the error rate during resharding is very low and brief.重新分片会将哈希槽在 Redis 节点间迁移，意味着桶键在迁移过程中可能短暂不可用或处于传输中状态。两种措施共同应对这一问题。首先，使用哈希标签键（bucket:{shopId}:{appId} 格式本身已满足要求——花括号标签确保该键始终路由到 shopId:appId 对应的哈希槽），使键的槽位保持稳定，且原子 Lua 脚本完全在单节点上执行，不存在跨槽问题。其次，在实时重分片事件期间，Redis Cluster 协议可能为正在迁移的槽返回 MOVED 或 ASK 重定向，客户端库会透明地跟随重定向。在键迁移的短暂窗口内，最坏情况是计数器略微过期，或有一个请求遇到空桶而被当作新客户端处理。对此的处理方式是：将 MOVED/ASK 错误视同 Redis 宕机，采用失败开放的本地限流兜底——重分片期间的错误率极低且持续时间极短。

How do you test and observe rate limiting in production?如何在生产环境中测试和观测限流效果？

Observability requires three layers. Metrics: instrument the limiter middleware to emit per-tier counters for allowed requests, denied requests (429s), and near-limit requests (bucket < 10% remaining). Alert on 429 rate spikes and near-limit client counts — a sudden surge in near-limit clients predicts an imminent 429 storm. Load testing: run synthetic traffic at 2× peak QPS against a staging environment with realistic clientId distributions; verify that the correct clients are throttled, 429s carry accurate Retry-After, and Redis p99 stays under 5 ms. Shadow mode: before enforcing a new tier or stricter limit in production, run the new config in shadow mode — the limiter evaluates the new rules and logs what would have been throttled without actually blocking anything. This validates that the new config does not accidentally throttle legitimate Plus merchants before you flip the enforcement flag.可观测性需要三个层次。指标监控：在限流中间件中埋点，按等级输出已放行请求数、拒绝请求数（429）以及接近限额请求数（桶剩余量 < 10%）的计数器。对 429 速率突增和接近限额客户端数量设置告警——接近限额客户端数量的突然激增预示着即将爆发的 429 风暴。压力测试：在预发布环境中用 2 倍峰值 QPS 的合成流量、真实的 clientId 分布进行测试，验证正确的客户端被限流、429 响应携带准确的 Retry-After，以及 Redis p99 延迟保持在 5 毫秒以内。影子模式：在生产环境正式执行新等级或更严格的限制之前，先以影子模式运行新配置——限流器评估新规则并记录哪些请求本应被限流，而不实际拦截任何请求。这能在切换执行开关之前，验证新配置是否会误杀合法的 Plus 商户。

Staff-level summary — say these in orderStaff 级总结——按顺序说出这些要点
  1. Token/leaky bucket algorithms for REST: they smooth sustained throughput while allowing legitimate bursts, matching how real apps behave.REST 使用令牌桶/漏桶算法：平滑持续吞吐量的同时允许合理突发，与真实应用行为相符。
  2. Cost-based limiting for GraphQL: request count is the wrong unit when one query can be arbitrarily expensive. Compute cost from query AST, debit a points bucket.GraphQL 使用基于成本的限流：当一次查询的代价可以任意大时，请求次数是错误的度量单位。从查询 AST 计算成本，从积分桶中扣除。
  3. Atomic Lua in centralized Redis, sharded by clientId: the check-refill-decrement is one round trip, one atomic operation, no race conditions possible. Shard to avoid hot-key concentration.在按 clientId 分片的集中式 Redis 中使用原子 Lua 脚本：检查-补充-扣减是一次往返、一次原子操作，不可能产生竞态条件。分片以避免热键集中。
  4. Explicit fail-open decision to protect platform availability: fall back to a conservative per-node local cap when Redis is degraded — never silently drop all traffic.明确的失败开放决策以保护平台可用性：Redis 降级时回退到保守的节点本地限流兜底——永远不要静默丢弃所有流量。
  5. Multi-tenant fairness via composing per-shop + per-app limits: one noisy app cannot exhaust a shop's budget and cannot affect other merchants on the platform.通过叠加按商店 + 按应用限额实现多租户公平性：一个吵闹的应用既不能耗尽某个商店的预算，也不能影响平台上的其他商户。
  6. Always return Retry-After so well-behaved clients can back off precisely rather than hammering the 429 response — this is the difference between a rate limiter that helps clients and one that punishes them.始终返回 Retry-After，让行为良好的客户端能精准退避，而非反复冲击 429 响应——这是一个帮助客户端的限流器与惩罚客户端的限流器之间的本质区别。
