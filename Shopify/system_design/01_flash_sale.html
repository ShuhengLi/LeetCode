Design a Flash Sale / BFCM Traffic Surge

"A limited sneaker drop: 1,000 pairs, 1,000,000 buyers, sells out in ten seconds. Design the system so it never oversells, the rest of Shopify stays up, and admitted buyers get a smooth checkout."

"限量球鞋秒杀：1,000 双鞋、1,000,000 买家、十秒内售罄。请设计这套系统，确保永不超卖、Shopify 其余功能不受影响，且已放行的买家能顺畅完成结账。"

📍 Seen: sneaker-drop / BFCM framing 🎯 Tests: spike handling + correctness ⏱ 60 min
Why Shopify loves this one为什么 Shopify 偏爱这道题

It is the purest expression of Shopify's reality: a 1000× spike on a single hot key (one SKU) while a hard business invariant (never oversell) must hold, and the blast radius must not reach other merchants. Generic "design Twitter" instincts (scale the read fleet) actively mislead here.

这道题是 Shopify 现实场景最纯粹的体现：单个热点 key（一个 SKU）上的 1000× 流量尖峰，同时必须遵守一条硬性业务不变式（永不超卖），且爆炸半径不得波及其他商家。套用"设计 Twitter"的惯性思维（扩容读集群）在此会彻底误导方向。

Clarify requirements澄清需求

Functional功能性需求

  • Merchant configures a sale: variant, total units, start time, per-user limit.
  • 商家配置秒杀活动：商品规格、总库存量、开始时间、每用户购买上限。
  • Before start, buyers wait in a queue / waiting room.
  • 活动开始前，买家在虚拟队列 / 等候室中等待。
  • At T0, admit buyers, let them reserve → checkout → pay.
  • T0 时刻放行买家，允许其完成预订 → 结账 → 支付流程。
  • Show an approximate "remaining / sold out" state.
  • 展示近似的"剩余库存 / 已售罄"状态。
  • Enforce per-user limit; mitigate bots/scalpers.
  • 执行每用户购买上限；防范机器人和黄牛。

Non-functional非功能性需求

  • Never oversell — hard invariant (strong consistency on stock).
  • 永不超卖 — 硬性不变式（库存强一致性）。
  • Isolation — must not degrade other merchants' checkout.
  • 隔离性 — 不得影响其他商家的结账流程。
  • Spike: ~1M concurrent, sellout in seconds → 100×–1000× baseline.
  • 流量尖峰：约 100 万并发，数秒内售罄 → 基线的 100×–1000×。
  • Low latency for admitted users; graceful degradation for the herd.
  • 已放行用户低延迟；大量等候用户实现优雅降级。
  • Fairness — not purely "fastest network wins".
  • 公平性 — 不能纯粹由网速决定胜负。

  • 是否需要严格的 FIFO 公平性，还是"不超卖 + 防机器人"即可？这会实质性地影响队列设计。

  • Does a reservation hold stock during checkout? For how long (TTL)?

Capacity estimation容量估算

find the real bottleneck找到真正的瓶颈

The insight that wins the round: the bottleneck is the admission fan-in, not the inventory write. There are only ~1,000 successful purchases — trivial for any database. The pressure is a million people asking at once.

赢得这道题的关键洞察：瓶颈在于入场流量的汇聚，而非库存写入。成功购买的只有约 1,000 笔——对任何数据库都微不足道。压力来自百万人同时发出请求。

  • Static page load (1M) is served entirely by the CDN → ~0 origin load. This is the cheapest place to absorb the herd.
  • 静态页面加载（100 万次）完全由 CDN 承载 → 源站负载约为零。这是吸收洪峰流量成本最低的位置。
  • Admission/status polling is the heavy path: 1M clients asking "am I in yet?" If each polls every 3s, that's ~330k QPS of cheap reads. Mitigate with edge-cached responses, jittered back-off, or push (SSE/long-poll).
  • 入场状态轮询是重负载路径：100 万客户端询问"我进了吗？"若每 3 秒轮询一次，约产生 33 万 QPS 的轻量读请求。应对方案：边缘缓存响应、抖动退避，或使用推送（SSE/长轮询）。

  • Redis DECRBY 延迟为个位数微秒级；单核在离散往返模式下可处理 10 万+ ops/s（流水线模式更高）。1,000 次自减操作毫无压力——Redis 之所以充当闸口，正是因为它既快又原子。

  • 订单数据库：约 1k 条 RESERVED + 1k 条 PAID 记录。不是瓶颈，不要浪费时间在扩容上。

Component walk-through组件详解

  • CDN / Edge — serves the static storefront and a cached "waiting-room" shell. 99% of the 1M never reach the origin. This is where the spike dies.
  • CDN / Edge — 提供静态店面和缓存的"等候室"页面壳。100 万请求中 99% 永远不会抵达源站。这里是流量洪峰消亡之处。
  • Gateway · WAF — per-IP caps, bot filtering, and a kill-switch to circuit-break this sale without touching the rest of Shopify.
  • Gateway · WAF — 每 IP 速率上限、机器人过滤，以及用于熔断本次活动的断路开关，不影响 Shopify 其他功能。
  • Waiting-Room Service — admission control. Issues signed tokens at a metered rate (≈ stock-drain rate × over-admit factor), converting a herd into a thin stream.
  • 等候室服务 — 入场控制。以受控速率（≈ 库存消耗速率 × 超发系数）签发令牌，将洪峰转化为细流。
  • Purchase/Reserve Service — stateless; validates the token, runs the atomic Redis gate, writes a RESERVED row, emits an event.
  • 购买/预订服务 — 无状态；验证令牌，执行原子 Redis 闸口，写入 RESERVED 行，发出事件。
  • Redis — the authoritative live stock counter + admission state. Tiny, fixed-size, blisteringly fast.
  • Redis — 权威的实时库存计数器 + 入场状态。数据量极小、固定大小、速度极快。
  • Order DB — durable source of truth; a conditional UPDATE … WHERE qty_sold < qty_total is the second oversell backstop.
  • 订单数据库 — 持久化权威来源；条件式 UPDATE … WHERE qty_sold < qty_total 是防超卖的第二道防线。
  • Kafka + workers — async reservation-expiry (releases unpaid slots), payment capture, webhooks, analytics.
  • Kafka + workers — 异步处理预订到期（释放未支付名额）、支付捕获、webhook 回调、数据分析。

Deep dives深度解析

where staff signal livesStaff 级信号所在之处

① Virtual waiting room — turn a herd into a metered stream① 虚拟等候室 — 将洪峰转化为受控细流

The edge serves a static shell; client JS hits a lightweight /join then polls /status. The admission controller drains the waiting set and flips buyers to ADMITTED at a controlled rate — only as fast as the purchase pipeline can confirm sales. Buyers without an ADMITTED token never touch checkout. The rate is set to stock-drain-rate × over-admit factor (e.g. admit 2,000 to sell 1,000, since some abandon).

边缘层提供静态页面壳；客户端 JS 调用轻量级 /join 后轮询 /status。入场控制器以受控速率从等待集合中取出买家并将其翻转为 ADMITTED——速率不超过购买流水线的确认速度。没有 ADMITTED 令牌的买家永远不会触达结账。速率设定为库存消耗速率 × 超发系数（例如：卖 1,000 件则放行 2,000 人，因为部分人会放弃）。

Polling vs push at 1M clients百万客户端的轮询 vs 推送

Naïve 1 s polling = ~1M QPS of "not yet". Fixes: (a) edge-cache the "WAITING" response for ~1 s so most polls never reach origin; (b) jittered exponential back-off; (c) SSE / long-poll to push the ADMITTED transition. Pick SSE if the panel pushes on cost at scale.

朴素的 1 秒轮询 = 约 100 万 QPS 的"尚未放行"。修复方案：(a) 在边缘缓存"WAITING"响应约 1 秒，使大多数轮询永远不到达源站；(b) 加入抖动的指数退避；(c) 用 SSE / 长轮询推送 ADMITTED 状态变更。若面试官追问规模成本，选 SSE。

② The atomic inventory gate — never oversell② 原子库存闸口 — 永不超卖

Stock is loaded into Redis at sale start. Each reserve runs an atomic decrement; a negative result is compensated and rejected. Combine the stock check and the per-user guard in one Lua script so it's a single atomic round-trip:

销售开始时将库存加载到 Redis。每次预订执行一次原子自减；结果为负则补偿回滚并拒绝。将库存检查与每用户限购保护合并在一个 Lua 脚本中，实现单次原子往返：

-- KEYS[1]=sale:{id}:stock  KEYS[2]=user:{id}:sale:{id}  ARGV[1]=limit  ARGV[2]=ttlSeconds
-- NOTE: GET returns a string or false, so coerce with tonumber()/or 0 and compare numerically.
local used = tonumber(redis.call('GET', KEYS[2]) or 0)
if used >= tonumber(ARGV[1]) then return 'USER_LIMIT' end
local n = redis.call('DECRBY', KEYS[1], 1)
if n < 0 then redis.call('INCRBY', KEYS[1], 1); return 'SOLD_OUT' end
redis.call('INCR', KEYS[2])
redis.call('EXPIRE', KEYS[2], ARGV[2])  -- TTL so per-user guard keys don't leak after the sale
return 'OK'

③ Reservation TTL & compensation — don't let abandoners lock the inventory③ 预订 TTL 与补偿 — 不让放弃者锁死库存

A successful reserve writes a RESERVED order with expires_at = now + 10 min. If the buyer doesn't pay, the expiry worker cancels the row and INCRBYs the Redis counter, returning the slot to the pool (the dashed loop in the diagram). This is what makes "reserve-then-pay" safe: no oversell and no permanent lockup.

成功预订后写入一条 RESERVED 订单，expires_at = now + 10 min。若买家未完成支付，到期工作器取消该行并执行 INCRBY 恢复 Redis 计数器，将名额归还到资源池（即图中的虚线循环）。这正是"先预订再支付"安全的原因：既不超卖，也不会永久锁死库存。

④ Defense in depth — three oversell barriers④ 纵深防御 — 三道防超卖屏障

Layer层级Mechanism机制Why it exists存在原因
L1 · Redis gate atomic DECRBY, reject on negative原子 DECRBY，结果为负则拒绝 fast authoritative live cap快速权威的实时上限

The durability gap you must name必须主动点出的持久化缺口

Redis can lose the counter on an unclean failover. Mitigations: AOF everysec, and — critically — the DB conditional UPDATE is the real source of truth; Redis is a fast front gate. If they diverge, the DB wins and reconciliation alerts. Naming this gap unprompted is a strong staff signal.

Redis 在非正常故障切换时可能丢失计数器。缓解措施：AOF everysec，以及——最关键的——DB 条件更新才是真正的数据权威；Redis 只是快速前置闸口。若两者出现偏差，以 DB 为准，对账作业触发告警。主动点出这一缺口是强烈的 Staff 级信号。

⑤ Isolation — protect the other 2 million merchants⑤ 隔离 — 保护其他两百万商家

Flash-sale traffic is routed to a dedicated fleet / queue (or its own pod, see Q04) with its own rate limits, so a sneaker drop cannot exhaust connection pools or Redis shared by ordinary checkout. The sale has a kill switch: circuit-break the sale, never the platform.

秒杀流量被路由到独立集群 / 队列（或独立 Pod，参见 Q04），拥有专属速率限制，使一次球鞋秒杀无法耗尽普通结账共用的连接池或 Redis。活动设有断路开关：熔断的是本次活动，而不是整个平台。

⑥ Reservation lifecycle — the state machine behind "held for you"⑥ 预留生命周期 —— "为您保留"背后的状态机

A reservation is a small state machine, and getting its transitions right is what makes reserve-then-pay safe. A RESERVED row moves to PAID on success; to EXPIRED if the TTL elapses unpaid; or to CANCELLED if the buyer backs out. Both EXPIRED and CANCELLED must return the unit to the pool; a later refund moves PAID → REFUNDED and also releases stock.

一条预留就是一个小型状态机，把它的状态转换做对，正是"先预订再支付"安全的关键。RESERVED 行在成功时转为 PAID；若 TTL 到期仍未支付则转为 EXPIRED；若买家放弃则转为 CANCELLED。EXPIRED 和 CANCELLED 都必须把该单位归还到库存池；之后的退款则把 PAID → REFUNDED 并同样释放库存。

States:  RESERVED ──pay ok──▶ PAID ──cancel/refund──▶ REFUNDED
            ├── TTL elapsed, unpaid ──▶ EXPIRED    (release unit)
            └── buyer cancels ────────▶ CANCELLED  (release unit)

-- expiry worker, runs every ~30s; release is idempotent
for r in SELECT * FROM reservation
         WHERE status='RESERVED' AND expires_at < now() LIMIT 1000:
    n = UPDATE reservation SET status='EXPIRED'
        WHERE reservation_id=r.id AND status='RESERVED'   -- single-winner guard
    if n == 1:                                  -- only the winner releases stock
        redis.INCRBY('sale:'+r.sale+':stock', 1)
        UPDATE flash_sale SET qty_sold = qty_sold - 1 WHERE sale_id = r.sale
Why the WHERE status='RESERVED' guard matters为什么需要 WHERE status='RESERVED' 这个守卫

The expiry worker, a retry of that worker, and a user-initiated cancel can all race on the same reservation. Making the release conditional on the current state means exactly one of them wins the transition — so a slot is returned to the pool once, never twice (releasing twice would oversell). This single-winner, idempotent release is what makes reserve-then-pay safe in practice; the TTL length is then a pure business dial — shorter frees stuck inventory faster, longer is kinder to slow-but-real payers.

过期 worker、它的重试、以及用户主动取消，可能同时对同一条预留发生竞争。把释放做成依赖当前状态的条件更新，意味着只有其中一个能赢得这次状态转换——于是槽位只归还一次，绝不两次（归还两次就会超卖）。这种"单一胜者、幂等"的释放，正是"先预订再支付"在实践中安全的根本；而 TTL 时长此时就是一个纯业务旋钮——越短越快释放被占住的库存，越长则对真正慢的付款者越友好。

① Inventory authority — Redis gate vs DB row-lock① 库存权威 —— Redis 闸口 vs 数据库行锁

The tension: where does the authoritative "is there a unit left?" decision live — in fast in-memory state, or in the durable database?

矛盾点："还有没有库存"这个权威判断放在哪里——放在快速的内存里，还是放在持久的数据库里？

Option A · Redis counter方案 A · Redis 计数器

Stock is an integer in Redis; each reserve is an atomic DECRBY, rejected if it goes negative.

库存是 Redis 里的一个整数；每次预订做一次原子 DECRBY，结果为负就拒绝。

+ Microsecond latency; single-threaded Redis serializes every reserve with no locks; one hot SKU with 100k concurrent buyers is trivial; zero DB contention.

+ 微秒级延迟；单线程 Redis 无需加锁就把所有预订串行化；单热点 SKU、十万并发买家也轻松扛；数据库零竞争。

− Not durable — an unclean failover can lose the last ~1s of decrements; it's a second source of truth that can drift from the DB; needs AOF + careful failover.

− 不持久——非正常故障切换可能丢失最近约 1 秒的扣减；它是与数据库并存的第二真相源，可能漂移；需要 AOF + 谨慎的故障切换。

Option B · DB row-lock方案 B · 数据库行锁

UPDATE … SET qty_sold=qty_sold+1 WHERE qty_sold<qty_total; the row lock serializes concurrent writers.

UPDATE … SET qty_sold=qty_sold+1 WHERE qty_sold<qty_total；行锁把并发写串行化。

+ Durable, transactional, a single authoritative source of truth that survives crashes.

+ 持久、事务性，是能在崩溃中存活的唯一权威真相源。

− One hot row is a serialization bottleneck — 10k+ concurrent reserves on the SAME row collapse throughput and spike latency (everyone queues on one lock); risks connection-pool exhaustion.

− 单热点行是串行化瓶颈——同一行上 1 万+并发预订会让吞吐崩塌、延迟飙升（所有人排在同一把锁上）；还可能耗尽连接池。

When to use which何时用哪个

A 1000×-hot SKU is exactly what the DB row alone can't survive, so put Redis in front to absorb the herd — but because Redis isn't durable, the DB conditional write stays the final authority, with reconciliation catching drift. So: use both. For ordinary, non-spiky inventory (see Q02) a DB row with optimistic concurrency is enough on its own.

1000 倍热点 SKU 正是单靠数据库行扛不住的场景，所以用 Redis 挡在前面吸收人潮——但因为 Redis 不持久，数据库条件写仍是最终权威，再用对账发现漂移。所以：两者兼用。对普通、无尖峰的库存（见第 2 题），单用数据库行 + 乐观并发就够了。

② Fairness model — strict FIFO queue vs rate-limited tokens② 公平性模型 —— 严格 FIFO 队列 vs 速率限制令牌

The tension: how "fair" must admission be, and what will you pay in throughput, latency and complexity for it?

矛盾点：入场要多"公平"，你愿意为此在吞吐、延迟和复杂度上付出多少？

Option A · Strict FIFO queue方案 A · 严格 FIFO 队列

Every joiner is appended to an ordered log (Redis Stream / one Kafka partition); a single consumer drains it in exact arrival order.

每个加入者被追加到有序日志（Redis Stream / 单个 Kafka 分区）；单个消费者按精确到达顺序消费。

+ Provable first-come-first-served; auditable and defensible — right when fairness is a brand or legal requirement (concert tickets, regulated drops).

+ 可证明的先到先得；可审计、可辩护——当公平性是品牌或法律要求时（演唱会票、受监管发售）正合适。

− A single ordered consumer is a hard throughput ceiling (can't parallelize one partition without losing order); adds wait latency; one slow step head-of-line-blocks the line.

− 单个有序消费者是硬性吞吐上限（不破坏顺序就无法并行化单分区）；增加等待延迟；一个慢步骤会队头阻塞整条队列。

Option B · Rate-limited tokens方案 B · 速率限制令牌

Admit at a controlled rate (e.g. 2000/min) without strict ordering; whoever is polling when a slot frees gets a token.

以受控速率放行（如 2000/分钟），不保证严格顺序；槽位释放时正在轮询的人拿到令牌。

+ Simple, high-throughput, horizontally scalable, low latency; "fair enough" — everyone's chance is proportional to the admission rate.

+ 简单、高吞吐、可水平扩展、低延迟；"足够公平"——每个人的机会与放行速率成正比。

− Not strictly FIFO — depending on poll timing, a later arrival can get in before an earlier one; harder to defend "exact fairness".

− 并非严格 FIFO——取决于轮询时机，后到的人可能比先到的先进；难以辩护"绝对公平"。

When to use which何时用哪个

Default to tokens for e-commerce flash sales — the goal is no-oversell + bot mitigation + protecting the backend, not courtroom-grade ordering. Reserve strict FIFO for when exact fairness is a hard product/legal requirement and throughput is modest.

电商抢购默认用令牌——目标是不超卖 + 防 bot + 保护后端，而不是法庭级排序。只有当"绝对公平"是硬性产品/法律要求且吞吐不高时，才用严格 FIFO。

③ Order of ops — reserve→pay vs pay→decrement③ 操作顺序 —— 先预订再支付 vs 先支付再扣减

The tension: do you commit a unit before taking money, or take money first and then commit a unit? This one choice decides your failure mode: "inventory locked by people who never pay" vs "money taken for stock you can't deliver".

矛盾点：你是在收钱之前先锁定一个单位，还是先收钱再锁定？这一个选择决定了你的失败模式："库存被永不付款的人锁住" vs "钱已收但货发不出"。

Option A · Reserve → pay方案 A · 先预订再支付

At /reserve you atomically claim a unit (Redis gate + a RESERVED row) before payment; the buyer then has N minutes to pay; an expiry worker releases the unit if they don't.

在 /reserve 时，在支付之前就原子占住一个单位（Redis 闸口 + 一条 RESERVED 行）；买家随后有 N 分钟支付；若未支付，过期 worker 释放该单位。

+ Never oversells — the unit is locked the instant you're admitted, so two people can't pay for the same one. Best UX — "held for you 09:58" lifts conversion; nobody pays then hears "sold out". Clean failures — if payment fails you just release; no money was taken.

+ 绝不超卖——被放行的瞬间单位就锁定，两人无法为同一件付款。最佳体验——"为您保留 09:58"提升转化；没人会付完款才被告知"售罄"。失败干净——支付失败就释放，从未收钱。

− Inventory lockup — admitted users who dawdle or abandon hold units that could have sold, so you may show "sold out" while units sit reserved-but-unpaid. Needs the TTL machinery, and TTL tuning is a balance (too long worsens lockup, too short kicks out slow-but-real payers).

− 库存被占住——磨蹭或放弃的已放行用户占着本可卖出的单位，于是可能在还有"已预留未支付"时就显示"售罄"。需要 TTL 机制，且 TTL 调参是平衡（太长加剧占用，太短把真正慢的付款者踢掉）。

Option B · Pay → decrement方案 B · 先支付再扣减

Take payment first, then try to decrement stock; if stock is already gone, refund the buyer.

先收款，然后再尝试扣减库存；若库存已没，就给买家退款。

+ No inventory lockup — units are consumed only by people who actually paid, so effective sell-through is maximized when abandonment is high. Simpler model — no reservation/TTL state.

+ 无库存占用——单位只被真正付款的人消耗，因此放弃率高时实际售出率最高。模型更简单——无需预留/TTL 状态。

− During a race you can accept more payments than units, then must refund the losers — money taken you can't fulfill (a "soft oversell"). Refunds cost fees, erode trust, and load support — and look terrible for a hyped drop ("you charged me then cancelled!"). Worse UX — the buyer pays under uncertainty.

− 抢购竞争中你可能收到比单位数更多的付款，然后必须退给落败者——收了无法履约的钱（"软超卖"）。退款要付手续费、损害信任、增加客服压力——对热门发售尤其难看（"你扣了我钱又取消！"）。体验更差——买家在不确定下付款。

When to use which何时用哪个

Scarce, hyped drops → reserve-then-pay + a short TTL: the no-oversell guarantee and "held for you" UX are worth the TTL complexity. Pay-then-decrement only when stock is effectively abundant (decrement rarely fails), holds are impractical, or refunds are cheap and instant (e.g. digital goods).

稀缺、热门发售 → 先预订再支付 + 短 TTL：不超卖的保证和"为您保留"的体验值得这点 TTL 复杂度。仅当库存实际充足（扣减很少失败）、无法做预留、或退款廉价即时（如数字商品）时，才用先支付再扣减。

④ Waiting-room transport — polling vs SSE / long-poll④ 等候室传输 —— 轮询 vs SSE / 长轮询

The tension: how do a million waiting clients learn "am I in yet?" without burying the origin in requests?

矛盾点：上百万等待的客户端如何获知"轮到我了吗？"，又不用请求把源站埋掉？

Option A · HTTP polling方案 A · HTTP 轮询

The client GETs /status every few seconds.

客户端每隔几秒 GET 一次 /status。

+ Dead simple, works everywhere, fully stateless, and the "still waiting" response is trivially cacheable at the edge.

+ 极其简单、到处可用、完全无状态，而且"仍在等待"的响应在边缘极易缓存。

− 1M clients polling every 3s ≈ 330k req/s of mostly "not yet". Edge-cache the WAITING response (~1s) + jittered intervals to mitigate, but it's inherently wasteful.

− 100 万客户端每 3 秒轮询 ≈ 33 万 req/s，多是"还没轮到"。可边缘缓存 WAITING 响应（约 1 秒）+ 抖动间隔来缓解，但本质浪费。

Option B · SSE / long-poll方案 B · SSE / 长轮询

The client holds one open connection; the server pushes the moment it flips to ADMITTED.

客户端保持一个长连接；服务端在状态翻转为 ADMITTED 的瞬间推送。

+ Near-zero polling waste and instant admission notification; far fewer requests overall.

+ 几乎零轮询浪费，入场通知即时；总请求数大幅减少。

− Holding ~1M concurrent connections costs file descriptors, memory and LB capacity; connection management is more complex (one-way SSE is fine here).

− 维持约 100 万并发连接消耗文件描述符、内存和负载均衡容量；连接管理更复杂（单向 SSE 在这里够用）。

When to use which何时用哪个

Start with edge-cached polling (simple, robust) for the MVP; switch to SSE / long-poll once polling QPS dominates cost at extreme scale. WebSocket only if you genuinely need bidirectional traffic — an admit signal doesn't.

MVP 先用边缘缓存轮询（简单稳健）；当轮询 QPS 在极端规模下成为主要成本时再换 SSE / 长轮询。只有真的需要双向通信才用 WebSocket——入场信号并不需要。

⑤ Over-admit factor — low vs high⑤ 超发系数 —— 低 vs 高

The tension: you have 1000 units. How many buyers do you let into checkout — exactly 1000, or more to cover the ones who'll abandon?

矛盾点：你有 1000 件。放多少买家进入结账——正好 1000，还是多放些来覆盖会放弃的人？

Option A · Low (≈1.0–1.2×)方案 A · 低（≈1.0–1.2×）

+ Minimal gate contention; almost nobody admitted hits "sold out", so little post-admission disappointment.

+ 闸口竞争最小；几乎没有被放行的人撞上"售罄"，放行后失望很少。

− If abandonment is high (say 40%), you under-sell — units go unsold because too few admitted people actually buy.

− 若放弃率高（比如 40%），你会卖不足——真正下单的放行用户太少，单位卖不掉。

Option B · High (2–3×)方案 B · 高（2–3×）

+ You actually sell out even with heavy abandonment, maximizing revenue.

+ 即使放弃率很高也能真正售罄，营收最大化。

− More admitted users get rejected at /reserve ("sold out" after being let in) → disappointment for those who won admission but lost the race; somewhat more gate contention.

− 更多被放行用户在 /reserve 被拒（进来后才"售罄"）→ 赢得入场却输掉抢购的人会失望；闸口竞争略增。

When to use which何时用哪个

Tune to historical abandonment/conversion; a common start is ~2×, adjusted live during the sale. Crucially, the atomic gate hard-caps at 1000, so over-admitting never oversells — worst case, some admitted users are rejected at reserve.

根据历史放弃率/转化率调参；常见起点是约 2×，并在抢购期间实时调整。关键在于：原子闸口把上限硬卡在 1000，所以超发绝不会超卖——最坏情况只是部分被放行用户在预订时被拒。

Redis dies mid-sale — what happens?Redis 在活动进行中宕机——会发生什么？

Fail over to a replica (AOF everysec bounds loss to ~1 s of decrements). Because the DB conditional UPDATE is the true cap, a slightly-stale Redis counter can only cause extra rejections (it may briefly think stock is lower), never oversell. Reconciliation re-syncs Redis from the DB. Worst case: pause the sale for a few seconds and reload the counter from qty_total − qty_sold.故障切换到副本（AOF everysec 将丢失限制在约 1 秒的自减操作内）。由于 DB 条件 UPDATE 才是真正的上限，略微过期的 Redis 计数器只会导致额外的拒绝（它可能短暂认为库存更少），而不会超卖。对账作业负责将 Redis 与 DB 重新同步。最坏情况：暂停活动几秒，然后从 qty_total − qty_sold 重新加载计数器。

How do you guarantee strict FIFO fairness?如何保证严格的 FIFO 公平性？

Put joiners on a Redis Stream or a Kafka partition keyed by sale; a single consumer drains in order and admits sequentially. Cost: a single ordered consumer caps admission throughput and adds latency, and one partition can't be parallelized. Only pay this when fairness is a product/legal requirement — otherwise rate-limited tokens are "fair enough".将加入者放入按活动 ID 分区的 Redis Stream 或 Kafka 分区；单消费者按顺序排队并依次放行。代价：单有序消费者会限制入场吞吐并增加延迟，且一个分区无法并行化。只有在公平性是产品或法律要求时才值得付出这个代价——否则速率限制令牌已"足够公平"。

What about global / multi-region inventory?全球 / 多区域库存怎么处理？

Two patterns: (a) partition the cap — allocate 600 to NA-Redis, 400 to EU-Redis; each region gates locally, true-up async. Simple, but a region can sell out while another has stock. (b) single global authority — one region owns the counter, others proxy with low-latency RPC; simpler correctness, worse tail latency + a regional dependency. A CRDT counter is tempting but cannot enforce a hard upper bound, so it's wrong for "never oversell".两种模式：(a) 分区上限——将 600 件分配给 NA-Redis、400 件给 EU-Redis；每个区域本地执行闸口，异步对账。简单，但一个区域可能售罄而另一个还有库存。(b) 单一全局权威——一个区域持有计数器，其他区域通过低延迟 RPC 代理；正确性更简单，但尾延迟更差且存在区域依赖。CRDT 计数器虽然诱人，但无法强制执行硬性上限，因此不适用于"永不超卖"场景。

How do you show "remaining count" to a million people without melting Redis?如何向百万用户展示"剩余数量"而不把 Redis 压垮？

Don't read the live counter per request. Broadcast an approximate count: a ticker updates an edge-cached value every 1–2 s (or push over the same SSE channel). Exactness only matters at /reserve, which goes through the gate. "Approximate display, exact at commit" is the consistency split to articulate.不要每次请求都读取实时计数器。广播一个近似数量：一个定时器每 1–2 秒更新边缘缓存值（或通过同一 SSE 通道推送）。精确性只在 /reserve 时重要，那里会经过闸口。"展示近似、提交精确"是需要清楚表达的一致性分层设计。

Scalpers and bots are buying everything — what do you add?黄牛和机器人抢购了所有商品——你会增加哪些防护？

Layered: WAF + per-IP/device caps, account-age and payment-risk checks, proof-of-work or CAPTCHA at /join, and — the strongest product fix — switch the race to a raffle: collect entries during a window, draw winners, which removes the speed advantage entirely. Mention that fairness is partly a product decision, not only infra.分层防护：WAF + 每 IP/设备上限、账号注册时间和支付风险检查、在 /join 处加入工作量证明或 CAPTCHA，以及——最强力的产品级修复——将速度竞争改为抽签：在时间窗口内收集报名，抽取中签者，彻底消除速度优势。需要指出公平性部分是产品决策，而非纯粹的基础设施问题。

A buyer pays, then cancels / refunds. Inventory?买家支付后取消订单 / 退款，库存如何处理？

Cancellation emits an event; a handler restores stock (INCRBY + DB qty_sold-- under the conditional guard) and frees it for the waiting set if the sale is still open. Reconciliation guards against double-restore. Refund of payment is a separate saga (see Q03).取消操作发出一个事件；处理器在条件保护下恢复库存（INCRBY + DB qty_sold--），若活动仍在进行则将名额归还到等待集合。对账作业防止重复恢复。支付退款是独立的 saga 流程（参见 Q03）。

How do you stop one user scripting thousands of /join requests to game the queue?如何阻止单个用户用脚本发送数千个 /join 请求来操控队列？

The first line of defense is the API Gateway / WAF: apply a tight per-IP rate limit (e.g., 5 /join requests per minute) so naive script floods are dropped at the edge before they cost anything. The stronger guarantee is a signed device token issued by the client-side page: the token binds the session to a browser fingerprint and is signed with a short-lived key, making it expensive to forge at scale. At the Waiting-Room Service, enforce a per-identity admission cap — one ADMITTED token per authenticated user ID — so even if a bot slips through multiple IPs, it cannot hold more than one reservation slot. Combine with account-age and payment-risk signals to raise the cost of fresh fake accounts.第一道防线是 API Gateway / WAF：对每个 IP 设置严格的速率限制（例如每分钟最多 5 次 /join），在流量到达源站之前就将简单的脚本洪流在边缘层拦截，几乎不增加成本。更强的保障是客户端页面签发的设备签名令牌：令牌将会话与浏览器指纹绑定，并使用短效密钥签名，使其难以被大规模伪造。在等候室服务层面，对每个认证用户 ID 执行每身份入场上限——每个用户只能持有一个 ADMITTED 令牌——这样即使机器人通过多个 IP 绕过了限流，也无法占用超过一个预订名额。结合账号注册时间和支付风险信号可进一步提高创建虚假新账号的成本。

How exactly do you tune the over-admit factor live during the sale?如何在秒杀进行中实时调整超发系数？

Monitor two real-time signals: abandonment rate (admitted users who never call /reserve within their TTL window) and conversion rate (reserves that reach PAID). If abandonment is high, increase the admission rate so the pipeline stays full and all stock sells; if conversion is close to 100 % and queue depth is deep, reduce admission to avoid over-admitting and holding buyers in limbo. In practice, expose a knob — admit_rate_per_second — on a config service that the Waiting-Room Service polls every few seconds. The Redis gate remains the hard safety cap: it will never let the atomic counter go below zero regardless of how aggressively you admit, so you can tune generously without risking oversell.实时监控两个关键指标：放弃率（被放行但在 TTL 窗口内始终未调用 /reserve 的用户比例）和转化率（预订成功并最终完成 PAID 的比例）。若放弃率偏高，提升入场速率以填满流水线，确保库存全部卖出；若转化率接近 100% 且队列深度仍很大，则降低入场速率，避免过多用户进入等候后被拒。实际操作中，在配置服务上暴露一个 admit_rate_per_second 参数，等候室服务每隔几秒轮询该值。Redis gate 始终是硬性安全上限：无论入场有多激进，原子计数器都不会低于零，因此可以大胆调大入场系数而不必担心超卖。

An admitted buyer's payment fails — how do you return the unit without losing the sale?已放行买家的支付失败时，如何在不丢失销售机会的情况下归还库存名额？

The reservation row carries an expires_at timestamp (TTL). If payment fails, the buyer can retry within that window — no immediate release needed. When the TTL fires, the expiry worker explicitly transitions the row to CANCELLED, calls INCRBY sale:{id}:stock 1 to restore the Redis slot, and decrements qty_sold in the DB under the same conditional guard. To avoid leaving inventory idle, the Waiting-Room Service can optionally re-admit the next buyer from the queue immediately on an explicit payment failure callback — this requires a lightweight Kafka message or direct call from the Purchase Service. The key invariant is that the Redis gate protects against double-restore: the expiry worker and a manual cancel path both hold an idempotency key on the reservation row, so the stock is only restored once.预订行携带 expires_at 时间戳（TTL）。支付失败后，买家可在该窗口内重试——无需立即释放名额。TTL 触发后，到期工作器将该行显式转换为 CANCELLED 状态，执行 INCRBY sale:{id}:stock 1 恢复 Redis 槽位，并在同一条件保护下将 DB 中的 qty_sold 减一。为避免库存名额空置，等候室服务可在收到支付失败的显式回调时立即从队列中再放行下一位买家——这需要从 Purchase Service 发出一条轻量级 Kafka 消息或直接调用。关键不变式在于 Redis gate 防止重复归还：到期工作器和手动取消路径均在预订行上持有幂等键，因此库存只会被归还一次。

Walk through one buyer's full timeline from landing to confirmed order.请完整描述一位买家从进入页面到订单确认的全链路时序。

① CDN shell — the buyer's browser fetches the storefront from the CDN edge node; the page is a static shell that loads instantly, absorbing the herd without touching origin. ② /join — at T0 (or before), client JS fires POST /flash/{saleId}/join; the Waiting-Room Service enqueues the buyer and returns a signed token plus estimated position. ③ Status polling / ADMITTED event — the client polls GET /status?token=… (or receives an SSE push); when the admission controller meters the buyer in, the response flips to state: ADMITTED. ④ /reserve (the gate) — client immediately calls POST /reserve with the ADMITTED token; the Purchase Service validates the JWT, runs the Lua script (atomic Redis DECRBY + per-user guard), writes a RESERVED order row, and returns a reservationId and expiresAt. ⑤ /pay — buyer submits payment details; POST /checkout/{reservationId}/pay authorizes and captures; on success the order row transitions to PAID and an order.paid Kafka event is emitted. ⑥ Confirmation — async workers send the confirmation email and webhook; the buyer sees the order page.① CDN shell — 买家浏览器从 CDN 边缘节点获取店面页面，该页面是静态 shell，秒级加载，吸收大量并发流量而不触达源站。② /join — 在 T0 时刻（或之前），客户端 JS 发起 POST /flash/{saleId}/join；等候室服务将买家加入队列，返回签名令牌及预估排队位置。③ 状态轮询 / ADMITTED 事件 — 客户端轮询 GET /status?token=…（或接收 SSE 推送）；当入场控制器将该买家放行时，响应状态翻转为 state: ADMITTED。④ /reserve（闸口） — 客户端立即携带 ADMITTED 令牌调用 POST /reserve；Purchase Service 验证 JWT，执行 Lua 脚本（原子 Redis DECRBY + 每用户限购保护），写入 RESERVED 订单行，返回 reservationId 和 expiresAt。⑤ /pay — 买家提交支付信息；POST /checkout/{reservationId}/pay 完成授权和扣款；成功后订单行跳转为 PAID，并发出 order.paid Kafka 事件。⑥ 确认 — 异步工作器发送确认邮件和 webhook；买家看到订单确认页面。

How do you rehearse / load-test for the drop, and what do you watch live?如何为秒杀活动进行压测演练，以及活动进行中实时关注哪些指标？

Run a game-day drill at least once before the actual drop: replay a synthetic herd of 1M virtual clients against a production-mirror environment to validate that the CDN absorbs the spike, the gateway rate-limits correctly, and Redis handles the counter without drift. Use a jittered ramp rather than a vertical wall to mimic realistic arrival patterns. During the live sale, watch the following dashboards: (1) admission rate (buyers/s being flipped to ADMITTED) vs remaining stock — are you admitting at the right cadence? (2) gate rejects (SOLD_OUT returns from the Lua script) — a sudden jump means stock exhausted faster than expected; (3) Redis-vs-DB drift — the reconciliation job should show zero; any positive number is a bug; (4) checkout p99 latency — a spike means the Purchase Service is saturated; (5) kill-switch readiness — confirm the circuit-breaker toggle is reachable and tested, so the team can halt the sale in seconds if something goes sideways.在正式活动前至少进行一次全链路演练（game-day drill）：向生产镜像环境回放 100 万虚拟客户端的合成流量，验证 CDN 能吸收流量峰值、网关限流配置正确、Redis 计数器处理无误差。使用抖动式斜坡流量而非垂直阶跃，以模拟真实用户到达分布。活动进行中实时关注以下看板：(1) 入场速率（每秒被翻转为 ADMITTED 的买家数）与剩余库存的比值——入场节奏是否合理？(2) 闸口拒绝数（Lua 脚本返回 SOLD_OUT 的次数）——突然跳升意味着库存比预期耗尽更快；(3) Redis 与 DB 的漂移量——对账作业应显示零，任何正数都是 bug；(4) checkout p99 延迟——飙升说明 Purchase Service 过饱和；(5) 熔断开关可用性——确认断路器拨码随时可用且经过测试，以便团队在出现问题时能在数秒内暂停活动。

⭐ Staff-level summary — say these four thingsStaff 级总结 — 必须说出这四点
  1. Shed at the cheapest layer: kill the herd at the edge; meter a thin stream into a pipeline sized for 1,000 — don't scale checkout 1000×.
  2. 在最廉价的层削减流量：在边缘层消灭洪峰；将细流精准计量地导入按 1,000 件定尺寸的流水线——不要将结账系统扩容 1000 倍。
  3. Defense in depth on the money invariant: Redis gate (fast) + DB conditional write (durable truth) + reconciliation (catches drift).
  4. 对核心不变式实施纵深防御：Redis 闸口（快速）+ DB 条件写（持久化权威）+ 对账（捕获漂移）。
  5. Name the durability gap of the Redis trick and which store is authoritative.
  6. 主动点出 Redis 方案的持久化缺口，以及哪个存储是权威数据源。
  7. Protect the platform: isolate the sale (dedicated fleet/pod + kill switch) so one merchant's drop can't hurt two million others.
  8. 保护平台：隔离活动（独立集群/Pod + 断路开关），使单个商家的秒杀活动不能影响其他两百万商家。
