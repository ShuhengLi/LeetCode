Design Shopify's Multi-Tenant Architecture & Sharding (Pods)设计 Shopify 的多租户架构与分片（Pods）

Millions of independent stores share infrastructure. The challenge: route every request to the right data, isolate tenants so one store's incident can't hurt others, and move a shop between shards with zero downtime. This mirrors Shopify's real Pods architecture — sharded MySQL grouped into self-contained failure domains, routed by shop_id.数百万独立商店共享同一基础设施。核心挑战：将每个请求路由到正确的数据、隔离租户以防止单个商店的故障影响他人，并实现 shop 在 shard 间的零停机迁移。 这与 Shopify 真实的 Pods 架构相对应——以 shop_id 为键的分片 MySQL，按 Pod 组织为自包含的故障域。

Framing: fairness & blast-radius isolation考察点：公平性与爆炸半径隔离 Tests: sharding + tenancy models考察：分片与租户模型 ⏱ 60 min
Why Shopify loves this one为何 Shopify 青睐这道题 It exposes whether you understand operational tenancy at scale: not just "put a tenant_id column on tables" but the hard engineering of shard routing, blast-radius containment, online data movement, and skew handling when the top 0.1% of merchants generate a disproportionate share of traffic. Generic "add replicas" thinking actively misleads here.这道题能揭示你是否真正理解规模化运营下的多租户：不只是"在表里加一列 tenant_id"，而是 shard 路由、爆炸半径限制、在线数据迁移，以及当 top 0.1% 的商户产生不成比例的流量时的倾斜处理。泛泛的"加副本"思路在这里会适得其反。

Clarify requirements澄清需求

~7 min · ask, don't assume~7 分钟 · 先问再假设

Functional功能性需求

  • Every request is shop-scoped; route it to the correct shard without the caller knowing.每个请求都以 shop 为范围；在调用方无感知的情况下将其路由到正确的 shard。
  • Onboard new shops (assign to a shard, zero-downtime).新 shop 上线（分配 shard，零停机）。
  • Admin and support tools may need cross-shop views (scatter-gather or derived store).管理和支持工具可能需要跨 shop 视图（散射收集或派生存储）。
  • Rebalance or move a shop between shards without taking the shop offline.在不使 shop 下线的情况下，对 shop 进行跨 shard 迁移或再平衡。
  • Per-tenant data residency — pin shops to a geographic region (GDPR).租户级数据驻留——将 shop 固定到特定地理区域（GDPR）。

Non-functional非功能性需求

  • Tenant isolation — a noisy, overloaded, or misbehaving shop must not hurt others.租户隔离——吵闹、过载或行为异常的 shop 不得影响其他 shop。
  • Blast-radius containment — a pod failure or bad deploy affects only that pod's shops.爆炸半径限制——Pod 故障或错误发布只影响该 Pod 内的 shop。
  • Horizontal scalability to millions of shops by adding pods, not re-architecting.水平扩展性——通过增加 Pod 而非重构架构，支撑数百万 shop。
  • Online migration — move a shop with zero downtime and no data loss.在线迁移——零停机、零数据丢失地迁移 shop。
  • Skew tolerance — the top 0.1% of merchants are orders of magnitude larger than the median.倾斜容忍——top 0.1% 的商户体量比中位数商户大出数个量级。
Clarifying questions to actually ask out loud面试中应当大声提问的澄清问题
  • Is "tenant" always one shop, or can an enterprise own multiple shops sharing a shard? (Assume shop = tenant unit.)"租户"是否始终等于一个 shop，还是企业可以拥有多个 shop 共享一个 shard？（假设 shop = 租户单元。）
  • What isolation level is required? Shared-table (cheap) vs schema-per-tenant vs shard-per-group? (This is the crux — state you'll walk through all three.)需要什么隔离级别？共享表（成本最低）vs 每租户独立 schema vs 每组独立 shard？（这是核心——说明你将逐一讲解三种方案。）
  • Do we need strict data residency today, or just a future hook? GDPR changes pod assignment strategy.现在就需要严格的数据驻留，还是只需为未来预留钩子？GDPR 会改变 Pod 分配策略。
  • How skewed is traffic? Do we have whale merchants that dwarf an entire shard? (Triggers dedicated-pod discussion.)流量倾斜程度如何？是否有"鲸鱼商户"让整个 shard 相形见绌？（引出专用 Pod 讨论。）
  • Are cross-tenant queries required in the hot path (admin dashboards, analytics) or only offline?跨租户查询是否需要在热路径（管理仪表板、分析）中支持，还是只在离线场景使用？

API / routing contractAPI / 路由契约

infrastructure design — keep the surface small基础设施设计——保持接口面尽量小

This is an infrastructure design; the external API is the merchant and storefront API. The internal routing contract is what matters.这是一道基础设施设计题；对外的 API 是商户和店面 API，内部路由契约才是关键。

GET/internal/shard-map/{shopId}→ {shardId, podId, region} — read from cache first
POST/internal/shard-map/{shopId}assign a new shop to a shard (onboarding)
PUT/internal/shard-map/{shopId}atomic shard-map flip (final step of shop migration)
POST/internal/shop-mover/jobs{shopId, targetShardId} — initiate an online shop move
GET/internal/shop-mover/jobs/{jobId}→ {phase, progress, etaSeconds} — monitor migration
GET/internal/admin/scatter?query=…cross-shard admin query (offline-only, async)

Every inbound request carries a resolvable shop identity — typically the custom domain or subdomain (e.g. acme.myshopify.com). The router resolves this to a shop_id, looks up the shard map (from an edge-local cache), and forwards to the correct pod. The caller never sees shard or pod IDs.每个入站请求都携带可解析的 shop 标识——通常是自定义域名或子域名（如 acme.myshopify.com）。路由器将其解析为 shop_id，从边缘本地缓存查找 shard map，然后转发到正确的 Pod。调用方永远看不到 shard 或 Pod ID。

Data model数据模型

Global shard-map store (small, replicated everywhere)全局 shard map 存储（体量小，全球复制）

shop_shard_map(
  shop_id     BIGINT PK,          -- shard key for all tenant data
  shard_id    SMALLINT NOT NULL,   -- which MySQL shard
  pod_id      SMALLINT NOT NULL,   -- which pod owns that shard
  region      VARCHAR(8),          -- e.g. 'us-east', 'eu-west' (GDPR pinning)
  status      ENUM('active', 'migrating', 'frozen'),
  moved_at    TIMESTAMP
)
-- Tiny table: ~3M rows × 30 bytes ≈ 90 MB. Fits in memory of any replica.
-- Cached at edge; invalidated on every PUT /shard-map/{shopId}.

Per-shard schema (shared tables, shop_id on every row)每 shard 的 schema（共享表，每行都带 shop_id）

-- Every table in the per-shard MySQL instance carries shop_id.
-- PK is always (shop_id, entity_id) for locality.
products(shop_id, product_id, title, status, …)
orders(shop_id, order_id, customer_id, total, created_at, …)
customers(shop_id, customer_id, email, …)
inventory_items(shop_id, item_id, available_qty, …)
-- Indexes always include shop_id as leading key.
-- Cross-shop queries are prohibited on the hot path.

Global services (outside pods — not sharded)全局服务（Pod 之外，不分片）

shop_identity(shop_id, domain, plan, billing_id, …)   -- global DB
billing_subscriptions(shop_id, plan, mrr, …)          -- global DB
analytics_events(shop_id, event_type, ts, payload)     -- columnar store (CDC fan-out)

High-level architecture高层架构

edge routing → shard map → pods边缘路由 → shard map → Pod
client edge / router service / pod cache (Redis) datastore async / CDC
Request flow: clients → Edge → Shard-Map Lookup (cache hit) → target Pod. Each Pod is a self-contained failure domain. CDC fan-out feeds a derived analytics store for cross-shop queries.请求流向：客户端 → 边缘层 → Shard-Map 查询（命中缓存）→ 目标 Pod。每个 Pod 是自包含的故障域。CDC 扇出将数据推送到派生分析存储，用于跨 shop 查询。

Component walk-through组件逐项说明

  • Edge / Router — resolves the incoming domain/subdomain to a shop_id, terminates TLS, enforces WAF rules. All subsequent routing is internal and invisible to the caller.边缘层 / 路由器——将入站域名/子域名解析为 shop_id，终止 TLS，执行 WAF 规则。后续所有路由均在内部完成，对调用方透明。
  • Shard-Map Lookup Service — the routing brain. Reads from an edge-local Redis replica on the fast path (sub-millisecond). On cache miss, queries the Global Shard-Map DB. All writes (assignments, flips) go to the global DB first, then invalidate the cache.Shard-Map 查询服务——路由核心大脑。快速路径从边缘本地 Redis 副本读取（亚毫秒）。缓存未命中时查询全局 Shard-Map DB。所有写入（分配、切换）先写全局 DB，再使缓存失效。
  • Global Shard-Map DB — a small, geo-replicated MySQL instance (or equivalent). The source of truth for which shop lives in which shard and pod. Tiny data footprint: ~90 MB for 3 M shops.全局 Shard-Map DB——一个小型、跨地域复制的 MySQL 实例（或等效方案）。记录每个 shop 所在 shard 和 Pod 的权威来源。数据量极小：3M 个 shop 约 90 MB。
  • Pods — the blast-radius isolation unit. Each pod bundles its own app servers, MySQL shard(s), and Redis. A pod crash, bad deploy, or overloaded shard affects only its shops. You can deploy, scale, or roll back a pod independently.Pod——爆炸半径隔离单元。每个 Pod 捆绑了自己的应用服务器、MySQL shard 和 Redis。Pod 崩溃、错误发布或 shard 过载只影响该 Pod 内的 shop。可以独立对 Pod 进行部署、扩容或回滚。
  • Online Shop Mover — a background service that migrates a shop between shards via snapshot + change-log replay + atomic map flip. Lives outside pods; touches both source and target.在线 Shop Mover——一个后台服务，通过快照 + 变更日志回放 + 原子 map 切换来迁移 shop。部署在 Pod 之外，同时操作源和目标 shard。
  • Analytics / Derived Store — cross-shop queries are prohibited on the live shards. A CDC fan-out (via Kafka/Debezium) streams changes into a columnar store (e.g., ClickHouse). Admin and analytics read from there, never from the live pods.分析 / 派生存储——禁止在实时 shard 上执行跨 shop 查询。CDC 扇出（通过 Kafka/Debezium）将变更流入列式存储（如 ClickHouse）。管理和分析查询从这里读取，永远不直接访问实时 Pod。

Deep dives深度剖析

where staff signal livesStaff 级信号所在之处

① Tenancy models compared — why Shopify chose shard-per-group① 租户模型对比——Shopify 为何选择每组独立 shard

There are three levels of tenant isolation in a relational database, each with a different cost/isolation trade-off:关系型数据库中有三个级别的租户隔离，各有不同的成本/隔离权衡：

Model模型Isolation隔离性Cost / Ops overhead成本 / 运维开销Suitable for适用场景
Shared table (shop_id column)共享表（shop_id 列） Weakest — one runaway query can lock all tenants; same schema for all最弱——一个失控查询可锁住所有租户；所有租户共用同一 schema Cheapest: one DB cluster, one schema最便宜：一个 DB 集群，一个 schema Early stage; homogeneous, small tenants早期阶段；同质化、体量小的租户
Schema-per-tenant每租户独立 schema Logical isolation; a buggy migration only touches one schema逻辑隔离；有问题的迁移只影响一个 schema Medium; schema count grows; migration tooling is complex中等；schema 数量随租户增长；迁移工具复杂 Hundreds to low thousands of tenants数百到数千个租户
Shard-per-group (Shopify's choice)每组独立 shard（Shopify 的选择） Strong: each MySQL instance is owned by a set of shops; an incident is contained强：每个 MySQL 实例归一组 shop 所有；故障被限制在组内 Higher: N MySQL instances to operate; but tooling amortizes较高：需运维 N 个 MySQL 实例；但工具化后可摊销 Millions of tenants; Shopify's reality数百万租户；Shopify 的现实场景
DB-per-tenant每租户独立 DB Maximum isolation; simplest queries最强隔离；查询最简单 Operationally impossible at millions of tenants — too many DB instances数百万租户下运维上不可行——DB 实例太多 Enterprise SaaS with handful of large clients仅有少数大客户的企业级 SaaS

Shopify cannot use DB-per-tenant at 3 M shops (that would mean millions of MySQL instances). Schema-per-tenant breaks down as schema count grows: ALTER TABLE across 3 M schemas is unworkable. Shard-per-group gives strong isolation, bounded schema count (~1,000 shards), and manageable ops — the right trade-off at Shopify's scale.Shopify 不能在 3M 个 shop 的规模下使用每租户独立 DB（那将意味着数百万个 MySQL 实例）。每租户独立 schema 随着 schema 数量增长而崩溃：跨 3M 个 schema 执行 ALTER TABLE 根本不现实。每组独立 shard 提供强隔离、有界的 schema 数量（约 1,000 个 shard）和可管理的运维——在 Shopify 的规模下是正确的权衡。

The shared-table temptation共享表的诱惑 It is tempting to add a shop_id column and call it done. The problem is operational: a single bad query from a large merchant can hold row-locks that stall unrelated shops on the same instance. Shard-per-group eliminates this class of cross-tenant interference at the DB layer, not just at the application layer.加一列 shop_id 就完工看起来很诱人。问题在于运维层面：一个大商户的单个糟糕查询可能持有行锁，导致同实例上无关 shop 的请求全部被阻塞。每组独立 shard 在 DB 层面消除了这类跨租户干扰，而不仅仅是在应用层面。

② Pods — blast-radius isolation as a first-class design primitive② Pod——爆炸半径隔离作为一等设计原语

A Pod is a self-contained failure domain: it bundles app servers, MySQL shards, Redis, and job workers for a fixed set of shops. Nothing a pod does can directly harm shops on a different pod. Key properties:Pod 是一个自包含的故障域：它将应用服务器、MySQL shard、Redis 和任务 worker 捆绑在一起，服务于固定的一组 shop。一个 Pod 的任何行为都无法直接影响其他 Pod 上的 shop。核心属性：

  • Independent deploy and rollback: a bad code push can be rolled back for one pod without touching others. This enables canary deployments at the pod granularity.独立部署与回滚：错误的代码推送可以只对一个 Pod 回滚，无需触动其他 Pod。这使得金丝雀发布可以以 Pod 为粒度进行。
  • Independent scaling: a pod containing disproportionately large merchants can be scaled up (more app-server replicas, read replicas) without scaling the entire fleet.独立扩容：包含超大商户的 Pod 可以独立扩容（增加应用服务器副本、读副本），无需扩容整个集群。
  • Dedicated pods for whales: a merchant generating, say, 5% of platform GMV can be assigned to a dedicated single-tenant pod with its own resource limits — isolating it both from harming others and from being harmed by others.为鲸鱼商户提供专用 Pod：一个贡献平台约 5% GMV 的商户可以被分配到专用的单租户 Pod，拥有独立的资源配额——既防止其影响他人，也防止他人影响它。
  • Failure containment: if a MySQL primary in Pod A crashes, shops in Pod B, C, …N are completely unaffected. The blast radius is bounded to the shops in that pod.故障限制：如果 Pod A 的 MySQL 主库崩溃，Pod B、C……N 上的 shop 完全不受影响。爆炸半径被限制在该 Pod 内的 shop 之内。

③ Routing and the shard map — the brain that must never lie③ 路由与 shard map——绝不能出错的大脑

Every request starts with a lookup: shop_id → shard_id → pod_id. The lookup path is a two-level cache:每个请求都从一次查询开始：shop_id → shard_id → pod_id。查询路径是两级缓存：

  • L1 (process-local): a bounded LRU map inside each app server process. Zero network hops for warm shops. TTL ~30–60 s.L1（进程本地）：每个应用服务器进程内的有界 LRU map。热点 shop 零网络跳转。TTL 约 30–60 秒。
  • L2 (edge Redis replica): shared by all app servers in a pod. Sub-millisecond, still local to the pod's region.L2（边缘 Redis 副本）：Pod 内所有应用服务器共享。亚毫秒级，仍在 Pod 所在区域本地。
  • L3 (Global Shard-Map DB): the authoritative source, queried only on cache miss or explicit invalidation. Read replicas in every region keep latency low.L3（全局 Shard-Map DB）：权威来源，仅在缓存未命中或显式失效时查询。每个区域的读副本保持低延迟。

On a cache miss the lookup writes back into L1 and L2. On a shard-map flip (after a shop migration) the mover sends an explicit invalidation to L2 and lets L1 drain via TTL.缓存未命中时，查询结果回写到 L1 和 L2。shard map 切换（shop 迁移完成后），mover 向 L2 发送显式失效通知，L1 通过 TTL 自然过期。

Critical: stale shard map during a live migration关键风险：实时迁移期间的 shard map 缓存陈旧 During a shop migration there is a window where L1/L2 caches still point to the old shard while the source shard has been frozen and the new shard is live. A write that lands on the old shard after the flip is silently lost. Mitigations: (1) freeze writes to the shop on the old shard before flipping — any arriving write gets a retriable 503 Shop Migrating; (2) the shard-map flip is a compare-and-swap that only succeeds once all caches have been explicitly invalidated; (3) the new shard is write-verified before the old shard is unfrozen. Never flip the map without draining caches first.shop 迁移期间存在一个窗口：L1/L2 缓存仍指向旧 shard，而源 shard 已被冻结、新 shard 已上线。切换后落到旧 shard 的写入会被静默丢失。缓解措施：(1) 切换前先冻结旧 shard 上该 shop 的写入——任何到达的写入都返回可重试的 503 Shop Migrating；(2) shard map 切换是 compare-and-swap 操作，只有在所有缓存被显式失效后才会成功；(3) 在解冻旧 shard 前对新 shard 进行写入验证。切换 map 前务必先排空缓存。

④ Online shop migration — zero-downtime move between shards④ 在线 shop 迁移——零停机跨 shard 迁移

Moving a shop between shards is the most complex operational task in this architecture. The constraint: the shop must remain available for reads and writes throughout. The ordered phases:在 shard 之间迁移 shop 是该架构中最复杂的运维任务。约束：整个迁移过程中 shop 必须持续对读写可用。有序阶段如下：

-- Phase 1: Snapshot
SELECT * FROM orders, products, customers, … WHERE shop_id = X
-- Dump snapshot into target shard. Can take minutes for large shops.
-- Source shard still serves reads AND writes during this phase.

-- Phase 2: Change-log replay (tail replication)
-- Subscribe to MySQL binlog on source shard, filtered to shop_id=X.
-- Apply all changes written during and after snapshot to target shard.
-- Continue until replication lag < threshold (e.g. < 500 ms).

-- Phase 3: Freeze writes (brief, targeted)
UPDATE shop_shard_map SET status = 'frozen' WHERE shop_id = X
-- New writes for this shop get HTTP 503 (retry-after: 2s).
-- Drain remaining binlog delta (usually < 1 s of changes).

-- Phase 4: Verify consistency
-- Checksum row count + max(updated_at) on source vs target.
-- Must match before proceeding.

-- Phase 5: Atomic shard-map flip
UPDATE shop_shard_map
  SET shard_id = new_shard, pod_id = new_pod, status = 'active'
  WHERE shop_id = X AND status = 'frozen'  -- CAS
-- Invalidate L2 cache entry; L1 drains via TTL.
-- New requests now route to target shard. Writes resume.

-- Phase 6: Cleanup
-- After 24 h (L1 TTL elapsed + safety window), delete source data.

The shop is unavailable for writes only during the freeze window (Phase 3–5), typically under 2 seconds for well-tailed replication. Reads from the old shard are still served via cached routes during this window; they see no stale data because writes are frozen.shop 对写入不可用的时间仅限于冻结窗口（阶段 3–5），在复制追尾良好的情况下通常不超过 2 秒。此窗口内，旧 shard 的读取仍通过缓存路由提供服务；由于写入已冻结，读取不会看到陈旧数据。

⑤ Noisy-neighbor protection and cross-shard queries⑤ 扰邻保护与跨 shard 查询

Noisy-neighbor protection: Even within a shard, one large shop can consume a disproportionate share of MySQL connection slots or Redis memory. Defenses:扰邻保护：即便在同一个 shard 内，一个大 shop 也可能消耗不成比例的 MySQL 连接槽或 Redis 内存。防御手段：

  • Per-shop rate limits at the app layer: each shop is allocated a request budget (e.g. 10k API calls/min for Shopify Plus); excess is throttled before touching the DB.应用层每 shop 速率限制：每个 shop 分配请求配额（如 Shopify Plus 每分钟 10k API 调用）；超出部分在触达 DB 之前就被限流。
  • Connection pooling with per-shop caps: a PgBouncer/ProxySQL layer limits how many simultaneous DB connections any single shop can hold.带每 shop 上限的连接池：PgBouncer/ProxySQL 层限制单个 shop 可持有的最大并发 DB 连接数。
  • Hot-shop isolation: if a shop's metrics exceed a threshold (CPU, row-locks, slow queries), the shop mover can relocate it to a dedicated pod or a less-loaded shard in minutes.热 shop 隔离：若某 shop 的指标超过阈值（CPU、行锁、慢查询），shop mover 可在几分钟内将其迁移到专用 Pod 或负载较低的 shard。

Cross-shard queries: Admin dashboards and analytics require data from all shops — but scatter-gathering thousands of live MySQL shards is dangerous (one slow shard stalls the whole query; no isolation). The solution is a derived store:跨 shard 查询：管理仪表板和分析需要来自所有 shop 的数据——但对数千个实时 MySQL shard 进行散射收集是危险的（一个慢 shard 会阻塞整个查询；缺乏隔离）。解决方案是派生存储：

  • Debezium or a custom CDC connector tails the binlog of every shard and publishes events to Kafka.Debezium 或自定义 CDC 连接器追踪每个 shard 的 binlog，并将事件发布到 Kafka。
  • A consumer writes into a columnar store (ClickHouse, BigQuery, Snowflake) partitioned by shop_id.消费者将数据写入以 shop_id 分区的列式存储（ClickHouse、BigQuery、Snowflake）。
  • All cross-shop queries run against the columnar store — eventually consistent but isolated from the transactional path.所有跨 shop 查询都针对列式存储执行——最终一致，但与事务路径完全隔离。
  • For admin support tools that need near-real-time data (e.g. "why did this order fail?"), the shop-scoped lookup goes directly to the correct pod — no scatter needed.对于需要准实时数据的管理支持工具（如"为什么这笔订单失败了？"），shop 范围内的查询直接路由到正确的 Pod——无需散射收集。
Giant-merchant skew巨型商户的流量倾斜 A whale merchant (say, a Flash Sale merchant doing 5% of platform volume) will overwhelm any shared shard. Three escalating options: (1) move the shop to a lightly loaded shard; (2) give the shop a shard with no other tenants (but still inside a shared pod); (3) give the shop a fully dedicated pod with its own resources, deploy cadence, and SLA. Option 3 is "Shopify Plus on dedicated infrastructure" — a product upsell, not just an ops trick.一个鲸鱼商户（如大促商户占平台 5% 的交易量）会压垮任何共享 shard。三个递进选项：(1) 将 shop 迁移到负载较轻的 shard；(2) 给 shop 一个没有其他租户的专属 shard（但仍在共享 Pod 内）；(3) 给 shop 一个完全专用的 Pod，拥有独立资源、发布节奏和 SLA。选项 3 就是"Shopify Plus 专用基础设施"——是产品升级，不只是运维手段。

A single giant merchant outgrows one shard — what do you do?单个超大商户超出了一个 shard 的容量——怎么办？

Three escalating options: (1) move the shop to a lightly loaded shard with no other tenants (still shared MySQL instance, but effectively dedicated). (2) If a single MySQL instance is the bottleneck: split the shop's data vertically — move some tables (e.g. analytics, historical orders) to a separate read-optimized store while keeping the transactional tables on the primary shard. (3) If write throughput is the limit: give the shop a dedicated pod with its own MySQL primary that can be sized independently. This is the "Shopify Plus dedicated infrastructure" tier. The key insight: the shard-map abstraction makes any of these moves possible without changing application code — only the routing entry changes.三个递进选项：(1) 将 shop 迁移到没有其他租户的轻负载 shard（仍是共享 MySQL 实例，但实际上专用）。(2) 若单个 MySQL 实例成为瓶颈：对 shop 的数据进行垂直拆分——将部分表（如分析表、历史订单）移至独立的读优化存储，同时保留事务表在主 shard 上。(3) 若写吞吐量是限制：给 shop 分配一个专用 Pod，拥有可独立调整规格的 MySQL 主库。这是"Shopify Plus 专用基础设施"层级。关键洞察：shard map 抽象让上述任何一种迁移都无需修改应用代码——只需更改路由条目。

The pod's load drops incrementally as shops move out. You can also add a new pod and immediately start routing new shop onboarding to it (future capacity), independent of rebalancing. At no point is there a bulk migration that touches all shops simultaneously.shard map 查询是再平衡的杠杆。排空热 Pod 的步骤：(1) 通过每 shop 的指标找出产生不成比例负载的 shop；(2) 使用 Online Shop Mover 逐一将这些 shop 迁移到负载较低或新建的 Pod——每次迁移冻结窗口不超过 2 秒；(3) 每次迁移后更新 shard map。随着 shop 不断迁出，Pod 负载逐步降低。也可以新增 Pod 并立即将新 shop 上线路由到那里（预留未来容量），独立于再平衡工作。整个过程中不会出现同时迁移所有 shop 的大规模操作。

How do you run schema migrations safely across thousands of shards?如何在数千个 shard 上安全地执行 schema 迁移？

Three-phase online DDL: (1) add the column as nullable with no default — this is a metadata-only change in MySQL 8 (instant algorithm); (2) backfill the column value in background batches, touching only a few thousand rows per iteration with short sleeps between batches to avoid locking; (3) add the NOT NULL constraint and default once backfill is complete. Use pt-online-schema-change or gh-ost (GitHub's online schema change tool) per shard — they shadow-copy rows without holding long locks. Rollout strategy: run the migration on one pod's shards, verify, then proceed pod-by-pod. Application code must be backward-compatible with both old and new schema during the rollout window (expand/contract pattern).三阶段在线 DDL：(1) 将列添加为 nullable 且无 DEFAULT——这在 MySQL 8 中是纯元数据变更（instant 算法）；(2) 在后台以小批量回填列值，每次迭代只处理几千行，批次间加短暂 sleep 避免锁；(3) 回填完成后再添加 NOT NULL 约束和默认值。在每个 shard 上使用 pt-online-schema-change 或 gh-ost（GitHub 的在线 schema 变更工具）——它们通过影子行复制，不持长锁。发布策略：先在一个 Pod 的所有 shard 上运行迁移，验证后再逐 Pod 推进。整个发布窗口内，应用代码必须向后兼容新旧两种 schema（扩展/收缩模式）。

GDPR: how do you ensure a shop's data never leaves its required region?GDPR：如何确保 shop 的数据永远不会离开其所要求的区域？

The region field in shop_shard_map is the enforcement point. At onboarding, the merchant selects a data-residency region; the shard-map assignment engine only assigns the shop to a shard inside a pod in that region. The routing layer enforces that requests for a GDPR-pinned shop are never forwarded to a pod outside the required region — if the nearest pod is in a different region, the request is rejected with a 422. The Online Shop Mover is also region-aware: it refuses to move a GDPR-pinned shop to a target pod outside the allowed region. The global shard-map DB itself stores only metadata (not merchant data), so its geo-replication does not violate residency requirements.shop_shard_map 中的 region 字段是执行点。上线时，商户选择数据驻留区域；shard map 分配引擎只会将该 shop 分配到目标区域内 Pod 的 shard。路由层强制要求：GDPR 锁定的 shop 的请求永远不会被转发到所要求区域之外的 Pod——若最近的 Pod 位于不同区域，请求以 422 被拒绝。Online Shop Mover 同样具备区域感知能力：它拒绝将 GDPR 锁定的 shop 迁移到允许区域之外的目标 Pod。全局 shard map DB 本身只存储元数据（非商户数据），因此其地理复制不违反数据驻留要求。

The shard-map lookup service itself fails — what is the fallback?Shard-map 查询服务本身故障——降级方案是什么？

The lookup service has four layers of resilience: (1) L1 process-local cache in app servers — the shard map for recently-seen shops is held in memory with a 30–60 s TTL. If the lookup service goes down, existing app-server instances can continue routing warm shops for the TTL duration without any lookup. (2) L2 Redis replica — even if the primary lookup service is unreachable, the Redis replica is independently available. (3) Read replicas of the global shard-map DB in every region — app servers can fall back to a direct DB read. (4) Static snapshot fallback — a periodic snapshot of the shard map can be embedded in app-server configuration (refreshed every few minutes) as a last-resort stale-but-safe fallback. Writes to the shard map (new onboardings, map flips) are queued during an outage and replayed on recovery. The key property: an outage of the lookup service degrades to slightly stale routing, not to a total outage of the platform.查询服务有四层弹性保障：(1) 应用服务器中的 L1 进程本地缓存——最近访问过的 shop 的 shard map 以 30–60 秒 TTL 保存在内存中。若查询服务宕机，现有应用服务器实例在 TTL 期间无需任何查询即可继续路由热点 shop。(2) L2 Redis 副本——即使主查询服务不可达，Redis 副本仍独立可用。(3) 每个区域的全局 shard-map DB 读副本——应用服务器可降级为直接读 DB。(4) 静态快照降级——定期生成的 shard map 快照可嵌入应用服务器配置（每几分钟刷新一次），作为最后兜底的陈旧但安全的降级方案。故障期间对 shard map 的写入（新 shop 上线、map 切换）被排队，恢复后重放。关键特性：查询服务故障只会降级为略微陈旧的路由，而非平台整体中断。

How do you build a cross-shop report without scatter-gathering live shards?如何在不对实时 shard 散射收集的情况下构建跨 shop 报表？

Never scatter-gather the live MySQL shards for reporting — one slow shard or pod incident would stall the entire report and create a dependency between analytical and transactional workloads. Instead: a CDC pipeline (Debezium reading each shard's binlog → Kafka topics → a consumer writing into ClickHouse or BigQuery) continuously materializes a replicated, shop-partitioned copy of transactional data into a columnar store. Cross-shop reports query the columnar store, which supports full-table scans efficiently and is completely isolated from the transactional pods. Latency is typically 1–5 minutes behind real-time (acceptable for all reporting use-cases). For near-real-time admin lookups that must be current (e.g., support tool for a live incident), route directly to the specific shop's pod using the shard map — a single-shop query, not a cross-shard scan.永远不要对实时 MySQL shard 进行散射收集来生成报表——一个慢 shard 或 Pod 故障会阻塞整个报表，并在分析与事务工作负载之间制造依赖。替代方案：CDC 管道（Debezium 读取每个 shard 的 binlog → Kafka topic → 消费者写入 ClickHouse 或 BigQuery）持续将事务数据物化为按 shop 分区的列式存储副本。跨 shop 报表查询列式存储——全表扫描高效，且与事务 Pod 完全隔离。延迟通常比实时晚 1–5 分钟（对所有报表场景均可接受）。对于必须实时的管理查询（如支持工具处理线上故障），通过 shard map 直接路由到目标 shop 的 Pod——这是单 shop 查询，不是跨 shard 扫描。

How do schema migrations roll out safely across ~1,000 shards?Schema 迁移如何安全地在约 1,000 个 shard 上滚动发布？

Use the expand/contract pattern combined with an online schema-change tool such as gh-ost. In the expand phase, add the new column as nullable (no DEFAULT) — in MySQL 8 this is an instant metadata-only operation that acquires no row locks. Then backfill the column in small batches (a few thousand rows per iteration with brief sleeps) so the migration never holds a long lock. Only after the backfill completes do you add the NOT NULL constraint in the contract phase. Roll out pod-by-pod: run the migration on Pod A's shards first, verify application health, then proceed to the next pod. Application code must be backward-compatible with both old and new schemas during the rollout window. Monitor replication lag on each shard during the migration — if lag spikes, pause the backfill until it recovers.使用扩展/收缩模式（expand/contract）结合在线 Schema 变更工具（如 gh-ost）。扩展阶段：将新列添加为 nullable、不设 DEFAULT——MySQL 8 下这是纯元数据操作，不持行锁。然后以小批量（每次几千行，批次间加短暂 sleep）回填数据，避免长锁。待回填完成后，再通过收缩阶段添加 NOT NULL 约束。按 Pod 逐步推进：先对 Pod A 的所有 shard 执行迁移，验证应用健康后再滚动到下一个 Pod。在整个发布窗口内，应用代码必须向后兼容新旧两种 Schema。迁移期间持续监控每个 shard 的复制延迟——若延迟飙升则暂停回填，等待恢复。

A pod gets hot — how do you rebalance online without downtime?某个 Pod 过热——如何在不停机的情况下在线再平衡？

Use per-shop metrics (CPU, slow queries, connection usage) to identify the heaviest tenants on the hot pod. Then invoke the Online Shop Mover to migrate those shops one at a time to a less-loaded pod or a freshly provisioned pod. Each individual move has a write-freeze window of under 2 seconds; the mover updates the shard map atomically after each move. Pod load drops incrementally as shops drain out — no big-bang migration. You can also pre-provision a new pod and start routing all new shop onboardings to it immediately, relieving future pressure independently of the rebalance effort. At no point do you need to pause all shops on the pod simultaneously.利用每个 shop 的指标（CPU、慢查询、连接数）找出热 Pod 上负载最重的租户。随后调用 Online Shop Mover，逐一将这些 shop 迁移到负载较低的 Pod 或新预置的 Pod。每次单个 shop 迁移的写入冻结窗口不超过 2 秒；迁移完成后 Mover 以原子方式更新 shard map。随着 shop 不断迁出，Pod 负载逐步下降——无需一次性大规模迁移。也可以提前预置新 Pod，立即将所有新 shop 上线路由至该 Pod，独立于再平衡工作缓解未来压力。整个过程中无需同时暂停该 Pod 上的所有 shop。

A shop must stay in the EU (GDPR) — how is residency enforced end to end?某个 shop 必须留在欧盟（GDPR）——数据驻留如何做到端到端强制执行？

Residency enforcement has three layers. First, the shard-map assignment engine pins the shop to a pod inside the required region at onboarding time — the region field in shop_shard_map is the authoritative record. Second, the edge router reads this field on every request: if the nearest edge PoP is outside the required region, the request is redirected or served from within the required region rather than being forwarded cross-region. Third, the Online Shop Mover is region-aware and refuses to move a GDPR-pinned shop to a target pod outside the allowed region, preventing accidental residency violations during rebalancing. The global shard-map DB stores only routing metadata (not merchant data), so its worldwide replication does not itself violate GDPR. Any attempt to write to the wrong region is rejected at the routing layer before it reaches a shard.数据驻留强制执行分三层。第一，shard map 分配引擎在 shop 上线时就将其锁定到目标区域内的 Pod——shop_shard_map 中的 region 字段是权威记录。第二，边缘路由器在每次请求时读取该字段：若最近的边缘 PoP 位于要求区域之外，则将请求重定向或在要求区域内提供服务，而非跨区域转发。第三，Online Shop Mover 具备区域感知能力，拒绝将 GDPR 锁定的 shop 迁移到允许区域之外的目标 Pod，从而防止再平衡过程中意外违反数据驻留要求。全局 shard map 数据库仅存储路由元数据（不含商户数据），因此其全球复制本身不违反 GDPR。任何试图写入错误区域的请求都会在路由层被拒绝，永远不会到达 shard。

One shop exhausts the DB connection pool — how do you cap per-shop connections?某个 shop 耗尽了数据库连接池——如何对单个 shop 的连接数设置上限？

Enforce per-shop connection quotas at the connection-proxy layer (ProxySQL or a custom middleware) sitting between the app servers and MySQL. Each shop is allocated a maximum concurrency budget — for example, a standard shop might be capped at 20 simultaneous DB connections, while a Shopify Plus merchant gets a higher limit. Requests that exceed the shop's quota are queued with a short timeout and returned as a retriable 429 Too Many Requests to the app layer; they never reach MySQL. This prevents a single shop from starving the entire shard of connections. Complement this with per-shop rate limiting at the application layer (before requests touch the DB) and fair scheduling so that large shops cannot indefinitely delay small shops in the queue. If a shop persistently saturates its quota, it is a signal to move it to a dedicated pod with a larger connection pool.在应用服务器和 MySQL 之间的连接代理层（ProxySQL 或自定义中间件）强制执行每 shop 的连接配额。每个 shop 分配最大并发预算——例如，标准 shop 上限为 20 个并发 DB 连接，Shopify Plus 商户可设置更高上限。超出配额的请求在代理层排队，超时后以可重试的 429 Too Many Requests 返回给应用层，永远不会触达 MySQL。这样可防止单个 shop 耗尽整个 shard 的连接资源。同时在应用层（请求触达 DB 之前）配合每 shop 速率限制和公平调度，确保大 shop 无法无限延迟小 shop 的排队请求。若某个 shop 持续打满配额，则视为将其迁移到具有更大连接池的专用 Pod 的信号。

How does a developer run a cross-shop analytical query safely?开发者如何安全地执行跨 shop 的分析查询？

The rule is absolute: never scatter-gather live MySQL shards in the hot transactional path. Cross-shop analytical queries go exclusively against the CDC-fed columnar store (e.g., ClickHouse or BigQuery). A CDC pipeline (Debezium reading each shard's binlog → Kafka topics → columnar consumer) continuously replicates transactional data into the analytics store with typical lag of 1–5 minutes. Developers query this store using standard SQL; full-table scans across all shops are cheap on columnar storage and completely isolated from the transactional pods. For shop-scoped near-real-time admin lookups ("why did this order fail?"), the developer routes directly to the specific shop's pod via the shard map — this is a single-shard, single-shop query, not a cross-shard scan, and is safe on the hot path. Any tooling that bypasses these two patterns (live scatter-gather) requires explicit approval and must run during off-peak hours with strict query timeouts.规则绝对明确：绝不在热事务路径上对实时 MySQL shard 进行散射收集（scatter-gather）。所有跨 shop 的分析查询只能针对 CDC 驱动的列式存储（如 ClickHouse 或 BigQuery）。CDC 管道（Debezium 读取每个 shard 的 binlog → Kafka topic → 列式消费者）持续将事务数据复制到分析存储，典型延迟为 1–5 分钟。开发者使用标准 SQL 查询该存储；在列式存储上跨所有 shop 的全表扫描成本低廉，且与事务 Pod 完全隔离。对于需要接近实时的 shop 级管理查询（"为什么这笔订单失败了？"），开发者通过 shard map 直接路由到目标 shop 的 Pod——这是单 shard、单 shop 的查询，不是跨 shard 扫描，在热路径上是安全的。任何绕过上述两种模式（即实时散射收集）的工具都需要明确审批，并且必须在非高峰时段运行，同时设置严格的查询超时。

A whole pod's primary DB is lost — what is the blast radius and how do you recover?某个 Pod 的主数据库完全丢失——影响范围是什么？如何恢复？

The blast radius is strictly bounded to the shops assigned to that pod — typically 1–5% of all shops depending on pod count, while all other pods continue serving normally. Recovery proceeds in three ordered steps: (1) Replica failover — a synchronous or semi-synchronous replica is promoted to primary within seconds (using MySQL Group Replication or an orchestrator like Orchestrator/Vitess). The shard map is unchanged; app servers automatically connect to the new primary via the proxy layer. (2) PITR from backups — if the replica is also unavailable or inconsistent, restore the shard from the most recent snapshot and replay the binary log up to the last committed transaction (Point-in-Time Recovery). (3) Shard-map status update — the pod is marked as degraded in the shard map so that health-check dashboards surface it and the SRE on-call is alerted. Shops remain offline only during the failover window (typically under 30 seconds for replica promotion). Once the primary is restored, the shop-mover can optionally redistribute shops from the recovered pod to balance capacity.影响范围严格限定于分配给该 Pod 的 shop——通常占全部 shop 的 1–5%（视 Pod 总数而定），其他所有 Pod 继续正常服务。恢复按三个有序步骤进行：(1) 副本故障转移——同步或半同步副本在数秒内提升为主库（使用 MySQL Group Replication 或 Orchestrator/Vitess 等编排工具）。shard map 无需改变；应用服务器通过代理层自动连接到新主库。(2) 从备份进行 PITR——若副本也不可用或数据不一致，则从最近的快照恢复 shard，并重放 binlog 直至最后一个已提交事务（时间点恢复）。(3) 更新 shard map 状态——在 shard map 中将该 Pod 标记为 degraded，使健康检查仪表板显示异常并告警值班 SRE。shop 仅在故障转移窗口内（副本提升通常不超过 30 秒）保持不可用。主库恢复后，shop mover 可选择性地将 shop 从恢复的 Pod 重新分配以平衡容量。

Staff-level summary — say these five thingsStaff 级总结——说出这五点
  1. Shard by shop_id, group shards into self-contained Pods — each Pod is an independent failure domain for blast-radius containment; a pod crash or bad deploy affects only its shops.以 shop_id 分片，将 shard 组织成自包含的 Pod——每个 Pod 是独立的故障域，用于限制爆炸半径；Pod 崩溃或错误发布只影响其内的 shop。
  2. Routing brain = HA edge-cached shard map: every request resolves shop_id → shard → pod from an edge-local cache; the global shard-map DB is the source of truth, queried only on cache miss.路由核心 = 高可用边缘缓存 shard map：每个请求从边缘本地缓存解析 shop_id → shard → pod；全局 shard-map DB 是权威来源，仅在缓存未命中时查询。
  3. Online shop move = snapshot + binlog-tail + freeze + verify + atomic flip: the freeze window is under 2 seconds; this is what makes rebalancing, GDPR pinning, and whale isolation operationally practical.在线 shop 迁移 = 快照 + binlog 追尾 + 冻结 + 验证 + 原子切换：冻结窗口不超过 2 秒；正是这一机制使得再平衡、GDPR 锁定和鲸鱼商户隔离在运维上切实可行。
  4. Noisy-neighbor protection = per-shop rate limits + connection-pool caps at app layer; for true whales, escalate to a dedicated pod with independent resource limits and deploy cadence.扰邻保护 = 应用层每 shop 速率限制 + 连接池上限；对于真正的鲸鱼商户，升级到拥有独立资源限制和发布节奏的专用 Pod。
  5. Keep the hot path single-shard: all transactional queries are shop-scoped and touch exactly one shard. Push cross-tenant work — analytics, admin reports — to a CDC-fed derived store that is fully isolated from the transactional pods.保持热路径单 shard：所有事务查询以 shop 为范围，只触达一个 shard。将跨租户工作——分析、管理报表——推送到 CDC 驱动的派生存储，与事务 Pod 完全隔离。
