Design a Shopping Cart Service设计购物车服务

Carts for both logged-in and anonymous buyers, merged on login, consistent across devices, and always available during traffic spikes. A cart that errors is an abandoned sale — availability beats strict consistency here, and inventory is never held in the cart.支持已登录用户与匿名用户的购物车，登录时自动合并，跨设备保持一致，并在流量峰值时始终保持可用。购物车出错即意味着丢失订单——这里可用性优先于强一致性，且库存不在购物车层预占。

API designAPI 设计

All endpoints accept an X-Shop-Domain header for multi-tenant routing. Anonymous callers present a signed cart token in the cookie; authenticated callers present a session/OAuth bearer token, and the Cart Service resolves their canonical cart_id server-side.所有接口均接受 X-Shop-Domain 请求头用于多租户路由。匿名调用方在 cookie 中携带签名购物车令牌；已认证调用方携带 session/OAuth Bearer token，Cart Service 在服务端解析其规范 cart_id。

GET/cartreturns the full cart document (header + line items)
POST/cart/items{variantId, qty} → adds or increments a line item
PUT/cart/items/{lineId}{qty} → sets absolute quantity (0 = delete)
DEL/cart/items/{lineId}removes a specific line item
POST/cart/merge{anonymousCartToken} → merges anon cart into the authenticated user's cart

Mutations return the updated cart document so the client does not need a follow-up GET. The /cart/merge endpoint is called immediately after login completes, before the user sees the cart page. All mutation endpoints are idempotent: callers supply a client-generated Idempotency-Key header to safely retry on network errors without duplicating items.变更操作返回最新购物车文档，客户端无需再发起额外的 GET 请求。/cart/merge 接口在登录完成后、用户看到购物车页面前立即调用。所有变更接口均为幂等：调用方提供客户端生成的 Idempotency-Key 请求头，以便在网络错误时安全重试而不重复添加商品。

① Identity & merge — anonymous to authenticated① 身份识别与合并——从匿名到已认证

An anonymous cart is created on first add-to-cart and keyed by a signed, opaque token stored in a browser cookie (HttpOnly, SameSite=Lax, short TTL). The token is signed with an HMAC key so the Cart Service can verify it without a database lookup on the authentication path. On login, the client sends POST /cart/merge {anonymousCartToken}. The merge logic runs in the Cart Service (or a worker):匿名购物车在首次加购时创建，以存储在浏览器 cookie（HttpOnly、SameSite=Lax、短 TTL）中的签名不透明令牌为键。令牌使用 HMAC 密钥签名，使 Cart Service 无需数据库查询即可在认证路径上完成验证。登录时，客户端发送 POST /cart/merge {anonymousCartToken}，合并逻辑在 Cart Service（或 Worker）中执行：

// Pseudocode: merge anonymous cart into user cart
function mergeCart(userCartId, anonCartId):
  anonCart = kv.get(anonCartId)
  userCart = kv.get(userCartId)

  for anonLine in anonCart.lines:
    existing = userCart.findByVariant(anonLine.variantId)
    if existing:
      // sum quantities, cap at per-variant limit
      existing.qty = min(existing.qty + anonLine.qty, MAX_QTY_PER_VARIANT)
      // keep the user cart's price_at_add (it's the older / verified one)
    else:
      userCart.lines.append(anonLine)  // new item from anon cart

  userCart.updated_at = now()
  kv.put(userCartId, userCart)
  kv.del(anonCartId)          // mark merged / delete anon cart
  emitEvent("cart.merged", {userCartId, anonCartId})

Conflict rules: same variant in both carts → sum and cap; price conflict → retain the user cart's price_at_add (re-validated at checkout anyway); new variants from anon cart → appended. The merge is idempotent — re-running on a stale retry produces the same result because the anon cart token is deleted after first success.冲突规则：两个购物车中有相同变体 → 累加数量并取上限；价格冲突 → 保留用户购物车的 price_at_add（无论如何都会在结账时重新验证）；匿名购物车中的新变体 → 追加。该合并是幂等的——因为匿名购物车令牌在首次成功后即被删除，重复执行陈旧的重试请求会产生相同结果。

② Storage choice — why KV beats a normalized RDBMS② 存储选型——为何 KV 优于规范化 RDBMS

A shopping cart has a simple, predictable access pattern: always accessed by its primary key (cart_id or user_id → cart_id). There are no ad-hoc queries, no aggregations, no foreign-key joins on the hot path. This makes a normalized SQL schema actively harmful — it would require a JOIN on every cart read.购物车的访问模式简单且可预测：始终通过主键访问（cart_id 或 user_id → cart_id）。热路径上没有临时查询、聚合或外键联表。这使得规范化 SQL 结构适得其反——每次购物车读取都需要 JOIN。

③ Cross-device consistency — LWW vs versioned③ 跨设备一致性——LWW vs 版本控制

For logged-in users, two devices can mutate the cart concurrently (e.g., laptop adds item while mobile removes one). The cart document has a version integer incremented on every write. Two strategies:对于已登录用户，两台设备可能并发修改购物车（如笔记本添加商品，同时手机删除商品）。购物车文档有一个 version 整数，每次写入时递增。有两种策略：

  • Last-Write-Wins (LWW) — whichever write arrives last overwrites the document. Simple to implement; acceptable for most carts because the stakes are low. Risk: a slow device can silently undo a recent mutation from a faster device. Mitigate by refreshing the local cart state after every mutation (the server returns the canonical doc).最后写入获胜（LWW）——最后到达的写入覆盖文档。实现简单；对大多数购物车可接受，因为风险较低。风险：慢设备可能悄悄撤销快设备的最新变更。缓解方法：每次变更后刷新本地购物车状态（服务端返回权威文档）。
  • Optimistic Concurrency (OCC) — client sends the version it last saw; server rejects with 409 Conflict if the stored version is higher. Client re-fetches and re-applies its mutation. Correct but adds a retry round-trip. Worth enabling for high-value shops or when the team reports lost-item complaints.乐观并发控制（OCC）——客户端发送其最后看到的 version；若存储版本更高，服务端拒绝并返回 409 Conflict。客户端重新获取并重放变更。结果正确，但增加了一次重试往返。适用于高价值店铺或团队收到丢失商品投诉时。

At Shopify scale, LWW is the right default — a lost cart item is annoying but not catastrophic, and the client always receives the current doc after each write. Reserve OCC for explicit requirements.在 Shopify 规模下，LWW 是正确的默认选择——丢失一个购物车商品令人恼火，但并非灾难性的，且每次写入后客户端总能收到最新文档。仅在有明确需求时才启用 OCC。

④ Price & inventory correctness — never hold stock in the cart④ 价格与库存正确性——购物车中永不持有库存

The price_at_add field is stored purely for display purposes — so the buyer sees the price they saw when they added the item. It is NOT authoritative. Both price and stock are re-validated at checkout against the live catalog and inventory service. This is a deliberate product decision:price_at_add 字段纯粹用于展示目的——让买家看到加购时的价格。它不具备权威性。价格和库存均在结账时对照实时商品目录和库存服务重新验证。这是一个有意为之的产品决策：

Never treat the cart as an inventory reservation永远不要将购物车视为库存预占 Holding inventory in the cart at platform scale would mean locking stock for 30 days for tens of millions of potentially abandoned carts. That would kill merchant availability — a merchant with 100 units in stock could see all 100 "locked" by abandoned carts, making the product appear sold-out to real buyers. The correct model: carts are soft — inventory is only committed at checkout. If an item goes out of stock between add and checkout, the checkout service surfaces the error and asks the buyer to remove it. This is expected UX, not a bug.在平台规模下将库存锁定在购物车中，意味着要为数千万个可能被废弃的购物车锁定库存长达 30 天。这将扼杀商家的可用性——一个拥有 100 件库存的商家，可能看到全部 100 件被废弃购物车"锁定"，导致商品对真实买家显示为缺货。正确模型：购物车是软状态——库存仅在结账时才提交。若某商品在加购到结账之间售罄，结账服务会提示错误并要求买家移除该商品。这是预期的用户体验，而非 Bug。

At checkout time: (1) re-fetch current prices from the Product/Pricing service; (2) check available inventory from the Inventory service; (3) show a diff to the buyer if anything changed; (4) only then decrement inventory atomically. The cart document's price_at_add is used only to highlight price increases to the buyer.结账时：(1) 从商品/定价服务重新获取当前价格；(2) 从库存服务检查可用库存；(3) 若有任何变化则向买家展示差异；(4) 仅在此时才原子性地扣减库存。购物车文档中的 price_at_add 仅用于向买家高亮显示价格上涨。

⑤ Availability during spikes & abandoned cart recovery⑤ 峰值期间的可用性与废弃购物车召回

Because the cart is AP, it must degrade gracefully. During a BFCM spike:因为购物车是 AP 系统，它必须能优雅降级。在 BFCM 峰值期间：

  if mergeLog.exists(sourceCartId):
    return kv.get(userCartId)          // already merged; no-op

    if existing == null:

      userCart.lines.append(anonLine)

Because the cart sits on the AP side of the CAP spectrum, the merge algorithm is deliberately conservative: when in doubt, keep the item. An out-of-stock line that stays in the cart is surfaced as a clear error at checkout — a recoverable UX moment. A line that is silently dropped is a lost sale and a support ticket. This asymmetry (false positives are tolerable; false negatives are not) drives every case in the conflict matrix. The checkout service is the correct enforcement point for hard constraints; the merge service should be as lossless as possible.

由于购物车处于 CAP 频谱的 AP 一侧，合并算法有意保守：有疑虑时，保留商品。留在购物车中的缺货行条目会在结账时以明确错误的形式呈现——这是可恢复的用户体验时刻。被静默删除的行条目则是损失的订单和客服工单。这种不对称性（假阳性可接受；假阴性不可接受）驱动了冲突矩阵中的每一个情况。结账服务是执行硬性约束的正确地方；合并服务应尽可能做到无损。

③ Storage engine — Redis vs DynamoDB (vs RDBMS)③ 存储引擎——Redis vs DynamoDB（vs RDBMS）

The tension: you need sub-millisecond reads, native TTL, horizontal scale, and durability — no single engine maximizes all four simultaneously.

矛盾点：你需要亚毫秒级读取、原生 TTL、水平扩展和持久化——没有单一引擎能同时将四者最大化。

Option A · Redis (hot cache)方案 A · Redis（热缓存）

The entire cart document is stored as a single JSON blob under one key. Reads and writes are atomic single-key operations; native TTL handles expiry automatically; Lua scripts enable conditional atomic mutations.

整个购物车文档以单个 JSON blob 存储在一个键下。读写是原子的单键操作；原生 TTL 自动处理过期；Lua 脚本支持条件原子变更。

+ Sub-millisecond latency (p50 <1 ms); single-threaded serialization with no locking; trivially scales reads with replicas; handles 50 GB of active cart data on a mid-size cluster.

+ 亚毫秒延迟（p50 <1 ms）；单线程串行化无需加锁；通过副本轻松扩展读取；中型集群轻松处理 50 GB 活跃购物车数据。

− Not durable by default — an unclean Redis failover with AOF everysec can lose up to ~1 s of writes. Memory is finite; at 50 GB active data you need careful capacity planning. No secondary indices, no ad-hoc queries.

− 默认不持久——采用 AOF everysec 的非正常 Redis 故障切换可能丢失约 1 秒的写入。内存有限；50 GB 活跃数据需要仔细做容量规划。无二级索引，无临时查询。

Option B · DynamoDB (durable KV)方案 B · DynamoDB（持久化 KV）

Fully managed, horizontally scaled, durable document store with native TTL. Single-digit ms latency on point lookups; no capacity pre-provisioning needed in on-demand mode.

全托管、水平扩展、持久化的文档存储，具备原生 TTL。点查询延迟个位数毫秒；按需模式下无需预置容量。

+ Durable (multi-AZ replication), no ops burden, autoscales to BFCM without pre-warming, native TTL, Global Tables for multi-region. Good default for cart at Shopify scale.

+ 持久化（多可用区复制），零运维负担，无需预热即可应对 BFCM，原生 TTL，Global Tables 支持多区域。Shopify 规模下购物车的优质默认选择。

− ~5 ms p50 vs Redis <1 ms — still fast enough for most flows, but noticeable under aggressive read amplification (e.g., storefront polling every page load). More expensive than Redis per GB for pure hot-cache workloads.

− p50 约 5 ms，而 Redis <1 ms——对大多数流程仍然足够快，但在激进的读放大场景下（如店面每次页面加载都轮询）会有感知。纯热缓存工作负载下每 GB 成本高于 Redis。

When to use which何时用哪个

Use both: Redis for the hot path, DynamoDB as the durable source of truth. Write-through pattern: every mutation writes to DynamoDB first (durable), then refreshes the Redis key (fast). On a Redis miss, fall through to DynamoDB and back-fill. This gives sub-millisecond reads on the hot path and zero data loss on failure. An RDBMS (PostgreSQL/MySQL) is actively wrong here — normalized rows require a JOIN on every cart read, and SQL can't TTL natively; only consider it if the cart grows into a complex query surface (wishlists, saved-for-later).

两者兼用：Redis 负责热路径，DynamoDB 作为持久化权威数据源。写透模式：每次变更先写入 DynamoDB（持久化），再刷新 Redis 键（快速）。Redis 未命中时降级到 DynamoDB 并回填。这样在热路径上获得亚毫秒级读取，同时在故障时零数据丢失。RDBMS（PostgreSQL/MySQL）在这里是错误的选择——规范化行在每次购物车读取时都需要 JOIN，且 SQL 不支持原生 TTL；仅当购物车演化为复杂查询面（心愿单、稍后购买）时才考虑。

④ Concurrent device writes — LWW vs OCC (version field)④ 并发设备写入——LWW vs OCC（version 字段）

The tension: a logged-in user can edit their cart from laptop and mobile simultaneously. How do you handle the write conflict without requiring complex distributed coordination?

矛盾点：已登录用户可以同时从笔记本和手机编辑购物车。如何在不需要复杂分布式协调的情况下处理写入冲突？

Option A · LWW — last write wins方案 A · LWW——最后写入获胜

Whichever write arrives at the KV store last atomically overwrites the document. No version bookkeeping, no client retry loop. The server always returns the canonical document after each mutation, so clients auto-reconcile on the next round-trip.

最后到达 KV store 的写入原子性地覆盖文档。无需版本簿记，无需客户端重试循环。服务端每次变更后总是返回权威文档，因此客户端在下一次往返时自动协调。

+ Zero operational complexity on the server side; no 409 handling needed; works correctly in the common case (one active session at a time for most users).

+ 服务端零操作复杂度；无需处理 409；在常见情况下（大多数用户一次只有一个活跃会话）工作正确。

− A slow device can silently undo a recent write from a faster device. If the laptop adds item A and the phone simultaneously removes item B, one of those changes can be lost — silently. This is the RYOW (read-your-own-writes) hazard in a multi-device world.

− 慢设备可能悄悄撤销来自快设备的最新写入。如果笔记本添加商品 A 而手机同时删除商品 B，其中一个变更可能悄无声息地丢失。这是多设备环境中的 RYOW（读己所写）风险。

Option B · OCC — optimistic concurrency via version方案 B · OCC——通过 version 字段实现乐观并发控制

Each cart document carries a version integer. The client reads the current version, sends it with its mutation, and the server rejects with 409 Conflict if the stored version is higher. The client re-fetches and re-applies its change on top of the winner.

每个购物车文档携带一个 version 整数。客户端读取当前版本，随变更一起发送，若存储版本更高则服务端拒绝并返回 409 Conflict。客户端重新获取文档并在获胜方版本之上重放变更。

+ Lossless — no mutation is ever silently discarded; both device changes are guaranteed to be reflected in the final document. Correct under concurrent multi-device edits.

+ 无损——任何变更都不会被静默丢弃；两台设备的变更都保证反映在最终文档中。在并发多设备编辑下结果正确。

− Adds a retry round-trip for every conflict; requires clients to implement re-fetch-and-replay logic (non-trivial for mobile apps); conflicts on the same cart are rare — OCC overhead is paid unconditionally for a rare failure mode.

− 每次冲突增加一次重试往返；要求客户端实现重新获取并重放的逻辑（移动应用实现不简单）；同一购物车上的冲突很少——OCC 开销无条件为罕见故障模式买单。

When to use which何时用哪个

LWW is the right default — simultaneous multi-device cart edits are rare, a lost item is annoying but not catastrophic, and the client always receives the authoritative doc after each mutation to self-correct. Enable OCC (as a feature flag, per-shop or per-tier) only when lost-item reports exceed a measurable threshold, or for high-value wholesale accounts where correctness matters more than simplicity.

LWW 是正确的默认选择——多设备同时编辑购物车很罕见，丢失一个商品令人恼火但非灾难性，且每次变更后客户端总能收到权威文档以自我修正。仅当丢失商品投诉超过可测量的阈值，或对正确性比简单性更重要的高价值批发账号，才启用 OCC（作为功能标志，按店铺或等级开放）。

⑤ Cart document shape — whole-document blob vs normalized rows⑤ 购物车文档结构——整体文档 blob vs 规范化行

The tension: should the cart header and all its line items be one document in one KV key, or spread across a relational schema with one row per line item?

矛盾点：购物车头信息和所有行条目应该作为一个文档放在一个 KV 键下，还是分散到关系型结构中，每个行条目一行？

Option A · Whole-cart document方案 A · 整体购物车文档

Cart header + all line items serialized as a single JSON blob, stored under one KV key. Every read and write is a single-key GET or PUT — one round-trip, no joins.

购物车头信息 + 所有行条目序列化为单个 JSON blob，存储在一个 KV 键下。每次读写都是单键 GET 或 PUT——一次往返，无需联表。

+ O(1) reads regardless of line item count; trivially cacheable; atomic at the document level; perfectly maps to the "give me the whole cart" access pattern that accounts for ~100% of hot-path traffic.

+ 读取复杂度与行条目数量无关为 O(1)；极易缓存；在文档级别原子；完美映射"给我整个购物车"的访问模式，该模式占热路径流量约 100%。

− Updating one line item reads and rewrites the whole document (read-modify-write); concurrent per-line updates need OCC or LWW at document level. Document size grows with cart size — a cart with 250 items at ~200 bytes/item is ~50 KB, manageable but needs a cap.

− 更新一个行条目需要读取并重写整个文档（读-改-写）；并发的逐行更新需要在文档级别使用 OCC 或 LWW。文档大小随购物车增长——250 个商品、每条约 200 字节的购物车约 50 KB，可管理但需要上限。

Option B · Normalized rows (cart + cart_line tables)方案 B · 规范化行（cart 表 + cart_line 表）

Cart header in a cart table; each line item in a separate cart_line row. SQL queries can aggregate, filter, or paginate across line items.

购物车头信息在 cart 表中；每个行条目在独立的 cart_line 行中。SQL 查询可以对行条目进行聚合、过滤或分页。

+ Updating one line item is a targeted single-row UPDATE; concurrent edits to different line items are automatically conflict-free; rich SQL queries (analytics, cross-cart aggregations) are possible.

+ 更新一个行条目是针对性的单行 UPDATE；对不同行条目的并发编辑天然无冲突；可以进行丰富的 SQL 查询（分析、跨购物车聚合）。

− Every cart read requires a JOIN between cart and cart_line — 2 round-trips minimum or 1 round-trip with a JOIN; far more expensive for the dominant hot-path access pattern. SQL can't TTL natively; needs a cron job to expire carts. RDBMS doesn't scale horizontally for 50M active rows without significant sharding work.

− 每次购物车读取都需要 cart 和 cart_line 之间的 JOIN——最少 2 次往返或一次带 JOIN 的往返；对主导性热路径访问模式代价高昂。SQL 不支持原生 TTL，需要定时任务过期购物车。RDBMS 在没有大量分片工作的情况下无法水平扩展 5000 万活跃行。

When to use which何时用哪个

Whole-document is the only right answer at this scale. The access pattern is "give me the entire cart" ~100% of the time; the SQL JOIN has no upside for this query shape. Normalized rows are appropriate only if the cart evolves into a feature with rich query requirements (e.g., "show all carts containing SKU X" for admin analytics) — and even then, maintain a separate denormalized query projection rather than switching the hot path to SQL.

整体文档是这一规模下唯一正确的答案。访问模式约 100% 的时间都是"给我整个购物车"；SQL JOIN 对这种查询形式没有任何好处。规范化行仅适用于购物车演化为具有丰富查询需求的功能时（如管理分析中"显示所有含 SKU X 的购物车"）——即便如此，也应维护一个独立的去规范化查询投影，而不是将热路径切换到 SQL。

⑥ Anonymous cart identity — signed cookie token vs server-side session⑥ 匿名购物车身份——签名 cookie 令牌 vs 服务端 session

The tension: how does the Cart Service know which anonymous cart belongs to which browser without asking a database on every request?

矛盾点：Cart Service 如何在不对每个请求查询数据库的情况下，知道哪个匿名购物车属于哪个浏览器？

Option A · Signed cookie token (HMAC)方案 A · 签名 cookie 令牌（HMAC）

On first add-to-cart, the Cart Service generates a cart_id, signs it with a shared HMAC key, and sets it as an HttpOnly, SameSite=Lax cookie. On subsequent requests, the service verifies the signature in O(1) — no DB lookup needed to authenticate the anonymous cart identity.

在首次加购时，Cart Service 生成一个 cart_id，用共享 HMAC 密钥签名，并将其设置为 HttpOnly、SameSite=Lax cookie。后续请求中，服务以 O(1) 验证签名——无需数据库查询即可认证匿名购物车身份。

+ Stateless verification — any Cart Service pod can validate the token without a session store lookup; survives load balancer rebalancing; CDN-friendly; no sticky sessions needed. Token rotation on HMAC key change invalidates all stale tokens without a DB migration.

+ 无状态验证——任何 Cart Service Pod 都能在不查询 session 存储的情况下验证令牌；在负载均衡器重新分配时依然有效；CDN 友好；无需会话粘性。HMAC 密钥更换时令牌轮换使所有过时令牌失效，无需数据库迁移。

− The token only proves "this is cart_id X" — it cannot carry additional state without increasing cookie size. Key rotation requires careful secret management (keep old key for grace period to avoid invalidating live carts mid-session). HMAC tokens can't be explicitly revoked without a denylist.

− 令牌只能证明"这是 cart_id X"——若不增加 cookie 大小则无法携带额外状态。密钥轮换需要谨慎的密钥管理（保留旧密钥一段宽限期，避免使进行中的 session 的购物车失效）。HMAC 令牌若无拒绝列表则无法显式吊销。

Option B · Server-side session store方案 B · 服务端 session 存储

A session ID in the cookie maps to a server-side session record (Redis or DB) that stores the cart_id and any other ephemeral state. The Cart Service looks up the session on every request to resolve the cart.

Cookie 中的 session ID 映射到服务端 session 记录（Redis 或 DB），其中存储 cart_id 和其他短暂状态。Cart Service 在每个请求上查询 session 来解析购物车。

+ Can store rich ephemeral state (device type, AB variant, referrer); explicit revocation by deleting the session record; easy to extend without changing the cookie format.

+ 可以存储丰富的短暂状态（设备类型、AB 变体、来源页面）；通过删除 session 记录显式吊销；无需更改 cookie 格式即可轻松扩展。

− Adds a session store hop on every anonymous request — extra latency + a new hot-path dependency. Session store becomes a single point of failure unless replicated; sticky sessions or a distributed store are needed for horizontal scaling.

− 每个匿名请求都多一次 session 存储查询——额外延迟 + 热路径上新增依赖。session 存储除非复制，否则成为单点故障；水平扩展需要会话粘性或分布式存储。

When to use which何时用哪个

Signed cookie token is the right default for anonymous cart identity. The Cart Service needs to know exactly one thing from the anonymous identity: the cart_id. An HMAC-signed cookie delivers this with zero server-side state and zero added latency. Use a server-side session only when the anonymous state grows complex enough to warrant the extra dependency — and even then, keep the cart identity in the KV store rather than in the session to preserve stateless cart access.

签名 cookie 令牌是匿名购物车身份的正确默认选择。Cart Service 从匿名身份只需要知道一件事：cart_id。HMAC 签名 cookie 以零服务端状态、零额外延迟实现这一点。仅当匿名状态变得足够复杂到值得增加额外依赖时，才使用服务端 session——即便如此，也要将购物车身份保存在 KV store 而非 session 中，以保持无状态的购物车访问。

Same item added at different quantities on two devices simultaneously同一商品在两台设备上同时以不同数量加入购物车

With LWW the last write wins, potentially discarding one device's change. The fix is to expose the version field: the losing device gets a 409 Conflict, re-fetches the current document, and replays its mutation on top. An alternative is item-level merge — store each line item as an independent entry with its own version rather than embedding them in a monolithic document. Then concurrent writes to different variants are automatically conflict-free; only writes to the same variant on two devices need arbitration (take the max, or last-write-wins per-line). Item-level storage adds indexing complexity but makes concurrent mutations safe without OCC retries.

Price of an item changed between add and checkout加购到结账之间商品价格发生变化

The cart displays price_at_add — the price at the moment the buyer added the item. At checkout, the Checkout Service fetches the current price from the Pricing Service. If it differs, the checkout surface shows the buyer the new price (with a callout: "price updated"). The buyer must confirm before proceeding. Whether the cart accepts a lower price silently or always prompts is a product decision. The key engineering invariant: the cart's stored price is never used to charge the buyer — only the live price from the authoritative Pricing Service is used at order creation.购物车展示 price_at_add——买家加购时的价格。结账时，Checkout Service 从定价服务获取当前价格。若有差异，结账界面向买家展示新价格（附提示："价格已更新"），买家须确认后方可继续。价格降低时是静默接受还是始终提示，属于产品决策。核心工程不变式：购物车中存储的价格绝不用于向买家收费——下单时始终使用权威定价服务的实时价格。

Item goes out of stock after being added to the cart商品在加购后售罄

Because carts do not hold inventory reservations, there is nothing to release. When the buyer reaches checkout, the Checkout Service calls the Inventory Service; if the variant is out of stock, the checkout surface shows an error ("Item no longer available") and asks the buyer to remove it before continuing. Optionally, the Cart Service can run a lazy availability check at cart view time — querying the Inventory Service and annotating line items with a soft availableForSale: false flag so the buyer sees the warning earlier in the funnel. This flag is advisory only and re-validated at checkout.因为购物车不持有库存预占，所以无需释放任何东西。当买家进入结账流程时，Checkout Service 调用库存服务；若该变体已售罄，结账界面显示错误（"商品已下架"）并要求买家在继续前将其移除。可选地，Cart Service 可在查看购物车时执行惰性可用性检查——查询库存服务并为行条目标注软性 availableForSale: false 标志，使买家在漏斗更早的环节看到提示。该标志仅供参考，结账时会重新验证。

Very large carts or abuse (thousands of line items)购物车商品极多或遭滥用（数千个行条目）

A cart with thousands of line items degrades KV performance (large document on every read/write) and can be a denial-of-service vector. Mitigations: (1) enforce a hard max line items cap (e.g., 500) at the Cart Service layer, returning a 422 if exceeded; (2) enforce a per-shop and per-account rate limit on add-to-cart mutations; (3) monitor the p99 cart document size and alert if it grows beyond a threshold. For legitimate bulk buyers (wholesale), consider a separate Quote or Draft Order flow that bypasses the consumer cart and is backed by a relational store with explicit pagination.拥有数千个行条目的购物车会降低 KV 性能（每次读写都是大文档），也可能成为拒绝服务攻击向量。缓解措施：(1) 在 Cart Service 层强制执行行条目数硬上限（如 500），超出时返回 422；(2) 对加购操作施加每店铺、每账户的速率限制；(3) 监控 p99 购物车文档大小，超过阈值时告警。对于合法的批量买家（批发商），考虑使用独立的报价或草稿订单流程，绕过消费者购物车，以关系型存储为后端并支持分页。

Guest-to-account edge cases (user logs in, then logs out, then in again)游客转账户的边界情况（用户登录后退出，再次登录）

On first login, the anonymous cart is merged into the user's account cart and the anon cart token is invalidated. If the buyer logs out, a new anonymous cart token is issued (fresh, empty). On re-login, the new anonymous cart (possibly empty) is merged into the existing account cart again — this is a no-op if the anon cart is empty, which is the common case. Edge: if the buyer shopped as a guest after logging out and added items to the new anon cart, those items are merged in on the next login. The merge is designed to be commutative and idempotent — running it twice on the same anon cart is safe because the anon cart is deleted after the first successful merge, and subsequent merges against a missing key are treated as merging an empty cart (no-op).首次登录时，匿名购物车合并到用户账户购物车，匿名购物车令牌作废。若买家退出登录，系统颁发一个新的匿名购物车令牌（全新、空购物车）。再次登录时，新的匿名购物车（可能为空）再次合并到已有账户购物车——若匿名购物车为空，则为空操作（最常见情况）。边界情况：若买家在退出登录后以游客身份购物并向新匿名购物车添加了商品，这些商品将在下次登录时合并进来。合并设计为可交换且幂等的——对同一匿名购物车执行两次是安全的，因为匿名购物车在首次成功合并后即被删除，后续对不存在键的合并被视为合并空购物车（空操作）。

Cross-region cart access and latency跨区域购物车访问与延迟

For a globally distributed merchant base, cart reads from a distant region add 100–200 ms of latency. Strategies: (1) replicate cart documents to the nearest region using DynamoDB Global Tables or a multi-master Redis cluster — writes go to the buyer's closest region, async replication propagates to others (eventual consistency; acceptable for carts). (2) Route authenticated users consistently to a home region based on their user_id hash — cross-region hops only happen on first login from a new geography. (3) For anonymous carts, the cookie carries the cart_id with a region hint in the token, so the API Gateway can route the request directly to the correct region without a lookup round-trip. Conflict resolution for multi-master: last-writer-wins by timestamp (e.g. DynamoDB Global Tables); the cart is low-stakes enough that a slight inconsistency window (seconds) is acceptable.对于全球分布的商家，从远端区域读取购物车会增加 100–200 ms 的延迟。策略：(1) 使用 DynamoDB Global Tables 或多主 Redis 集群将购物车文档复制到最近区域——写入发往买家最近的区域，异步复制传播到其他区域（最终一致性；对购物车可接受）。(2) 根据 user_id 哈希将已认证用户一致性地路由到归属区域——跨区域跳转仅在首次从新地理位置登录时发生。(3) 对于匿名购物车，cookie 中的令牌携带 cart_id 和区域提示，使 API Gateway 无需额外查询即可直接路由到正确区域。多主冲突解决：按时间戳的最后写入获胜（如 DynamoDB Global Tables）；购物车风险足够低，秒级的不一致窗口是可接受的。

Logged-in user edits the cart on web and mobile simultaneously — how do you reconcile?已登录用户同时在 Web 和移动端编辑购物车——如何合并冲突？

Two reconciliation strategies exist. Last-Write-Wins (LWW) on the whole cart document: each client reads the current version, applies its mutation, and writes back. The write that arrives at the KV store last wins; the losing client receives a 409 Conflict, re-fetches the canonical document, and re-applies its mutation. This is simple and correct for low-stakes carts. Per-line-item merge: store each line item as an independent key-value entry keyed by {cart_id}:{variant_id}. Writes to different variants are automatically conflict-free; only concurrent writes to the same variant need arbitration (take the last-writer or the max quantity). Per-line storage avoids most OCC retries but adds index complexity. For Shopify scale, LWW on the cart document is the right default — a brief inconsistency window is acceptable, and the client always receives the authoritative document after each mutation.有两种协调策略。整体文档 LWW（最后写入获胜）：每个客户端读取当前 version，应用变更后写回。最后到达 KV store 的写入获胜；落败的客户端收到 409 Conflict，重新获取最新文档并重放变更。此方案简单，对低风险购物车完全适用。逐行合并：将每个行条目以 {cart_id}:{variant_id} 为键独立存储。对不同商品的并发写入天然无冲突，仅对同一商品的并发写入需仲裁（取最后写入或最大数量）。逐行存储能减少大多数 OCC 重试，但会增加索引复杂度。在 Shopify 规模下，默认使用整体文档 LWW 即可——短暂的不一致窗口可接受，且每次变更后客户端都会收到权威文档。

How do you build abandoned-cart recovery without spamming users?如何在不骚扰用户的前提下实现废弃购物车召回？

The Cart Service emits a cart.abandoned event to Kafka after a configurable TTL of inactivity (typically 1 hour). A downstream marketing worker consumes this event and applies three guardrails before sending any notification: (1) deduplication — check whether a recovery message was already sent for this cart within the current abandonment window; (2) frequency caps — respect per-user caps (e.g., at most one recovery email per 24 hours); (3) opt-out / consent flags — verify the user has not unsubscribed from marketing emails. Only if all three pass does the worker enqueue the email or push notification. The cart document is retained for up to 7 days post-abandonment so that a recovery link click-through can restore the exact cart state.Cart Service 在一段可配置的不活跃 TTL（通常为 1 小时）后向 Kafka 发送 cart.abandoned 事件。下游营销 Worker 消费该事件，在发送任何通知前执行三道保护：(1) 去重——检查当前放弃窗口内是否已对该购物车发送过召回消息；(2) 频率上限——遵守每用户上限（如每 24 小时最多发送一封召回邮件）；(3) 退订/授权标志——确认用户未取消订阅营销邮件。三项全部通过后，Worker 才将邮件或推送通知入队。购物车文档在放弃后最多保留 7 天，以便用户通过召回链接点击后还原原有购物车状态。

A cart with 500 items or obvious abuse — what limits and protections do you add?购物车有 500 件商品或明显滥用——应设置哪些限制和保护？

An oversized cart document degrades KV performance and can be a denial-of-service vector. Defenses operate at three layers: (1) Max line-item count — enforce a hard cap (e.g., 250 line items) at the Cart Service, returning 422 Unprocessable Entity on violation. (2) Per-item quantity cap — enforce a per-variant quantity limit (e.g., 99 units) to prevent bulk-buy manipulation. (3) Rate limiting on add-to-cart — apply a per-user or per-session rate limit (e.g., 60 mutations/minute) at the API Gateway to blunt bot traffic and scripted abuse. (4) Payload size guard — reject requests where the cart document would exceed a byte threshold (e.g., 64 KB) even if the line count is within limits. For legitimate wholesale buyers, route them to a Draft Order or Quote flow backed by a relational store with explicit pagination, rather than stretching the consumer cart.过大的购物车文档会降低 KV 性能，也可能成为拒绝服务攻击向量。防御措施分三层：(1) 行条目数上限——在 Cart Service 层强制硬上限（如 250 个行条目），违规时返回 422 Unprocessable Entity。(2) 单品数量上限——限制每个商品变体的数量（如最多 99 件），防止批量购买操控。(3) 加入购物车的速率限制——在 API Gateway 对每用户或每会话设置速率上限（如每分钟 60 次变更），以遏制机器人流量和脚本滥用。(4) 载荷大小保护——即使行条目数在限制内，也拒绝购物车文档超过字节阈值（如 64 KB）的请求。对于合法的批发买家，将其路由到以关系型存储为后端、具备分页功能的草稿订单或报价流程，而不是滥用消费者购物车。

Promo codes and discounts — where are they validated?优惠码和折扣——在哪里验证？

Discount validation follows the same pattern as price and inventory: estimate at display time, authoritative validation at checkout. When a buyer enters a promo code, the Cart Service calls the Discount Service for a tentative evaluation — this computes the estimated discount and displays it in the cart UI. However, this result is explicitly advisory: the Cart Service never stores the discounted price as the authoritative price. At checkout, the Checkout Service re-validates the promo code against the Discount Service under the full set of constraints (expiry date, usage limits, eligibility, minimum order value). If the code is no longer valid, the checkout surfaces the error before payment. The invariant is simple: never trust a cart-stored price to charge the buyer — always re-compute from authoritative sources at order creation time.折扣验证遵循与价格、库存相同的模式：展示时估算，结账时权威验证。买家输入优惠码时，Cart Service 向 Discount Service 发起试算评估——计算预估折扣并在购物车 UI 中显示。但该结果仅供参考：Cart Service 绝不将折后价格存储为权威价格。结账时，Checkout Service 在完整约束条件下（有效期、使用限额、资格要求、最低订单金额）重新向 Discount Service 验证优惠码。若优惠码已不可用，结账流程在付款前提示错误。不变原则很简单：永远不要信任购物车中存储的价格来向买家收费——始终在创建订单时从权威来源重新计算。

How do you A/B test cart changes safely?如何安全地对购物车改动进行 A/B 测试？

Cart changes carry conversion risk — a bug that breaks add-to-cart costs real revenue. Safe rollout uses three levers: (1) Feature flags — gate the new behavior behind a flag evaluated at request time (e.g., by shop_id or a user cohort hash). This allows instant rollback without a code deploy. (2) Kill-switch aware of AP semantics — because the cart is AP, a flag outage must fail-open (keep serving the old behavior) rather than fail-closed (block all cart operations). Guard every flag read with a safe default. (3) Conversion monitoring — track add-to-cart rate, cart-to-checkout rate, and checkout completion rate separately for control vs. treatment cohorts. Wire alerts on relative degradation (e.g., >2% drop in conversion). Start with 1–5% of traffic, ramp slowly, and tie the ramp to the alert green-lighting. Never run a cart experiment at 50% without first validating at low traffic.购物车改动存在转化风险——破坏"加入购物车"的 Bug 会造成真实营收损失。安全发布使用三个手段：(1) 功能标志——将新行为置于请求时动态求值的标志后面（如按 shop_id 或用户分桶哈希）。这样无需代码部署即可即时回滚。(2) 具备 AP 语义意识的熔断开关——因为购物车是 AP 系统，标志服务故障时必须 fail-open（继续使用旧行为），而非 fail-closed（阻断所有购物车操作）。每次读取标志时都要设置安全默认值。(3) 转化率监控——分别跟踪对照组和实验组的加购率、购物车到结账率以及结账完成率。对相对降幅（如转化率下降 >2%）配置告警。从 1–5% 流量开始，缓慢扩量，并将扩量与告警绿灯挂钩。在低流量验证通过之前，切勿直接以 50% 流量运行购物车实验。

Guest → account: how does the cart carry over on signup or login?游客→账户：注册或登录时购物车如何迁移？

On signup or login, the client immediately calls POST /cart/merge {anonymousCartToken} before rendering the cart page. The merge logic in the Cart Service (or a synchronous merge worker) reads the anonymous cart by its token, reads the user's account cart (creating one if it does not exist), and applies the same conflict rules used elsewhere: same variant in both → sum quantities and cap; variant only in anon cart → append; variant only in user cart → keep untouched. After a successful merge, the anonymous cart is deleted and the token is invalidated (HMAC key rotation or a server-side revocation list). The operation is idempotent: if the client retries on a network error, the anon cart is already gone and the merge is a no-op. The user sees a unified cart with all items from both the guest and account sessions, and checkout proceeds normally against the merged user cart.注册或登录时，客户端在渲染购物车页面之前立即调用 POST /cart/merge {anonymousCartToken}。Cart Service（或同步合并 Worker）读取匿名令牌对应的购物车，读取用户的账户购物车（不存在则新建），并应用统一的冲突规则：两者都有同一商品变体→累加数量并取上限；仅匿名购物车有的变体→追加；仅账户购物车有的变体→保持不变。合并成功后，匿名购物车被删除，令牌被作废（HMAC 密钥轮换或服务端吊销列表）。该操作是幂等的：若客户端因网络错误重试，匿名购物车已不存在，合并为空操作。用户看到的是包含游客和账户会话所有商品的统一购物车，结账流程照常在合并后的用户购物车上进行。

Staff-level summary — say these five things in orderStaff 级总结——按顺序说出这五点
  1. Cart is AP, not money-critical — keep it available at all costs; consistency lives at checkout.购物车是 AP 系统，非金融关键——不惜一切保持可用；一致性由结账服务保证。
  2. Single-document KV storage — one key per cart, one round-trip per operation; no joins, no SQL scans.单文档 KV 存储——每个购物车一个键，每次操作一次往返；无联表，无 SQL 扫描。
  3. Merge on login with explicit conflict rules — sum quantities for duplicates, cap at limits, retain user cart's price, delete the anon cart after success.登录时合并并使用明确的冲突规则——重复商品累加数量并取上限，保留用户购物车价格，成功后删除匿名购物车。
  4. Never reserve inventory in the cart — validate price and stock at checkout only; reserving in the cart at scale starves merchants of available inventory.购物车中永不预占库存——仅在结账时验证价格和库存；大规模在购物车预占会耗尽商家可用库存。
  5. TTL + abandonment events — carts expire automatically; cart.abandoned Kafka events drive recovery emails and analytics without coupling the hot path to marketing systems.TTL + 废弃事件——购物车自动过期；cart.abandoned Kafka 事件驱动召回邮件和分析，无需将热路径与营销系统耦合。
