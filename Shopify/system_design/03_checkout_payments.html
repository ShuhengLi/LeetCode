Design a Multi-Region Checkout & Payment Processing System设计多地域结账与支付处理系统

A buyer clicks Pay. The system must never double-charge, must survive a PSP outage, must work across regions, and must not lose the order even if any single component fails mid-flight. Every failed or duplicated charge is a lost merchant sale or a furious customer.买家点击支付。系统必须永不重复扣款，必须在 PSP 故障时存活，必须跨地域正常运行，且在任意单一组件中途故障时都不能丢失订单。每一次失败或重复的扣款，都意味着商家损失一笔销售，或买家怒不可遏。

💳 PSP resilience + idempotency 🔒 PCI scope + tokenization ⏱ 60 min
Why Shopify loves this one为什么 Shopify 钟爱这道题 Checkout is the revenue-critical path for every merchant. It combines distributed transactions (inventory + payment + order in one saga), external dependency failures (PSPs are slow and flaky), no double-charge — idempotent retries (true exactly-once is impossible across an external gateway), and PCI compliance (minimize scope). Getting it right requires a staff engineer's breadth: idempotency, state machines, outbox, and circuit breakers all at once. 结账是每位商家的核心营收链路。它融合了分布式事务（库存 + 支付 + 订单合并为一个 saga）、外部依赖故障（PSP 既慢又不稳定）、禁止重复扣款——幂等重试（跨外部网关的真正 exactly-once 不可能实现），以及 PCI 合规（最小化范围）。做对这道题需要 Staff 工程师的宽度：同时处理幂等性、状态机、outbox 和断路器。

① Idempotency — the #1 thing the interviewer drills① 幂等性——面试官最常深挖的核心

The client supplies an Idempotency-Key header (a UUID they generate client-side) on every /complete call. Before touching any downstream, the server looks up the key:客户端在每次 /complete 调用时提供一个 Idempotency-Key 请求头（客户端生成的 UUID）。服务器在接触任何下游之前先查找该键：

  • Key not found → proceed, store {key, request_hash, status: PROCESSING} in Redis + DB, run the saga.键未找到 → 继续执行，在 Redis + DB 中存储 {key, request_hash, status: PROCESSING}，运行 saga。
  • Key found, same hash, status PROCESSING and lease still valid → return 202 Accepted — in flight, poll GET /checkouts/{id}.键已找到，哈希相同，状态为 PROCESSING 且租约仍有效 → 返回 202 Accepted——处理中，轮询 GET /checkouts/{id}。
  • Key found, status PROCESSING but lease expired (the original holder crashed mid-flight) → recover: query the PSP with our idempotency key for the true outcome, then finalize — never blind-retry.键已找到，状态为 PROCESSING 但租约已过期（原持有者中途崩溃）→ 恢复：用我们的 idempotency key 查询 PSP 获取真实结果，再完成状态终结——绝不盲目重试。
  • Key found, same hash, status COMPLETE → return the cached 200 response — never re-charge.键已找到，哈希相同，状态为 COMPLETE → 返回缓存的 200 响应——绝不重复扣款。
  • Key found, different hash → return 409 Conflict — client bug, reject immediately.键已找到，哈希不同 → 返回 409 Conflict——客户端 bug，立即拒绝。

Critically, we also forward our own server-generated idempotency key to the PSP (X-Idempotency-Key on the Stripe API). This means even if our server crashes after calling the PSP but before storing the result, a replay will ask the PSP for the exact same charge and receive the same response rather than a second charge.关键的一点：我们还会将服务端生成的 idempotency key 转发给 PSP（Stripe API 中为 X-Idempotency-Key）。这意味着即使我们的服务器在调用 PSP 后、存储结果前崩溃，重放时也会向 PSP 查询同一笔扣款并得到相同响应，而不会产生第二笔扣款。

// Pseudocode: /checkouts/{id}/complete handler
function handleComplete(idempotencyKey, requestBody):
  record = idempotencyStore.get(idempotencyKey)
  if record != null:
    if hash(requestBody) != record.requestHash: throw 409
    if record.status == 'COMPLETE': return record.response  // cached, no re-charge
    if record.status == 'PROCESSING' and not record.leaseExpired(): return 202  // in flight
    if record.status == 'PROCESSING': return reconcileWithPSP(idempotencyKey)  // stale lease → recover, never re-charge

  idempotencyStore.setProcessing(idempotencyKey, hash(requestBody), leaseSec=30)
  try:
    result = sagaOrchestrator.run(idempotencyKey, requestBody)
    idempotencyStore.setComplete(idempotencyKey, result)
    return result
  catch:
    idempotencyStore.setFailed(idempotencyKey)
    throw

② Payment state machine & async capture② 支付状态机与异步扣款

The payment state machine is INITIATED → AUTHORIZED → CAPTURED (happy path), plus FAILED, VOIDED, and REFUNDED. Capture may be asynchronous: many PSPs allow a separate capture call hours after authorization (e.g. ship-then-bill). In this model:支付状态机的正常路径为 INITIATED → AUTHORIZED → CAPTURED，另有 FAILED、VOIDED 和 REFUNDED。扣款可以异步发生：许多 PSP 允许在授权数小时后再单独调用扣款（如先发货后收费）。在此模型下：

  • Authorization happens synchronously at checkout — funds are reserved on the buyer's card.授权在结账时同步发生——买家银行卡上的资金被预留。
  • Capture is triggered by a fulfillment event (an async worker consuming order.fulfilled from Kafka).扣款由履单事件触发（异步 worker 消费 Kafka 中的 order.fulfilled）。
  • If the PSP webhook for CAPTURED never arrives, a reconciliation job polls the PSP's API by psp_ref to resolve ambiguity.如果 CAPTURED 的 PSP webhook 始终未到达，对账任务将按 psp_ref 轮询 PSP API 来消解不确定状态。
The most dangerous moment: network timeout after PSP call最危险的时刻：PSP 调用后网络超时 The server calls the PSP, the PSP charges the card, but the response never arrives (TCP timeout, pod restart, etc.). Did the charge succeed? Never blindly retry — that double-charges the buyer. Resolution: the idempotency key we sent to the PSP lets us call GET /charges/{idempotencyKey} on the PSP to retrieve the outcome, then write the correct terminal state. This is why forwarding the idempotency key to the PSP is non-negotiable. 服务器调用 PSP，PSP 完成扣款，但响应始终未到达（TCP 超时、Pod 重启等）。扣款是否成功？绝不能盲目重试——那会对买家重复扣款。解决方案：我们发给 PSP 的 idempotency key 允许我们调用 PSP 的 GET /charges/{idempotencyKey} 来获取真实结果，再写入正确的终态。这就是为什么将 idempotency key 转发给 PSP 是不可妥协的设计。

③ Saga orchestration with compensation③ 带补偿的 Saga 编排

The checkout completion is a distributed transaction across Inventory, Payment, and Order services. A saga breaks it into steps with compensating transactions:结账完成是跨库存、支付、订单服务的分布式事务。Saga 将其拆解为若干步骤，每步都有对应的补偿事务：

1 · Reserve inventory1 · 预留库存inventory.reserve(cartItems)inventory.release(reservationId)

Orchestration vs. choreography: An orchestrator (a durable workflow engine, or a simple state machine in the Saga Service DB) is preferred here because the failure modes are complex — we need to know exactly which step failed to choose the right compensation. Choreography (each service reacts to events) is simpler to implement but harder to reason about when debugging a partial failure.编排 vs. 编舞：此处优先选用编排器（持久化工作流引擎，或 Saga Service DB 中的简单状态机），因为失败模式复杂——我们需要精确知道哪一步失败了，才能选择正确的补偿操作。编舞（各服务对事件做出反应）实现更简单，但在调试部分失败时难以推断根因。

④ Outbox pattern — eliminating the dual-write problem④ Outbox 模式——消除双写问题

After creating an order, we must publish an order.created event to Kafka so fulfillment, notifications, and analytics can react. The naive approach writes to DB, then publishes to Kafka — but if the process dies between those two operations, the event is lost and fulfillment never starts.创建订单后，我们必须向 Kafka 发布 order.created 事件，以便履单、通知和数据分析能够响应。朴素做法是先写 DB，再发布到 Kafka——但如果进程在这两步之间崩溃，事件就会丢失，履单永远无法启动。

The outbox pattern solves this: the Order Service writes the order row and the outbox row in the same DB transaction. A separate relay process (or CDC via Debezium) polls WHERE published_at IS NULL, publishes to Kafka, and marks the row published. The event is guaranteed to be published exactly once relative to the DB commit — even if Kafka is down at commit time.Outbox 模式解决了这个问题：Order Service 在同一 DB 事务中同时写入 order 行和 outbox 行。单独的中继进程（或通过 Debezium 的 CDC）轮询 WHERE published_at IS NULL，发布到 Kafka，并将行标记为已发布。相对于 DB 提交，事件被保证精确发布一次——即使提交时 Kafka 宕机也不例外。

⑤ PSP outage resilience⑤ PSP 故障韧性

The PSP is the only external dependency Shopify cannot control. When it starts failing:PSP 是 Shopify 唯一无法控制的外部依赖。当它开始失败时：

  • Retry with exponential backoff + jitter (e.g., 0.5 s, 1 s, 2 s, 4 s) for transient errors. Cap at 3–4 attempts.对瞬时错误进行指数退避 + 抖动重试（如 0.5 s、1 s、2 s、4 s）。最多重试 3–4 次。
  • Circuit breaker per PSP: after 5 consecutive failures in 10 s, open the circuit (fail fast). After 30 s, half-open and probe. Prevents cascading timeouts from piling up.每个 PSP 独立断路器：10 秒内连续 5 次失败则断路（快速失败）。30 秒后半开探测。防止级联超时堆积。
  • Failover to secondary PSP: if the primary circuit is OPEN, route to the secondary adapter. A different idempotency key domain ensures no cross-PSP collision.故障转移至备用 PSP：若主 PSP 断路为 OPEN，则路由到备用适配器。不同的 idempotency key 域名空间确保跨 PSP 无碰撞。
  • Queue-and-retry UX: if all PSPs are unavailable, the checkout session enters a PAYMENT_PENDING state. The buyer sees "Your order is being processed — we'll email you within 5 minutes." A background worker retries when PSPs recover. The order is never dropped.排队重试的用户体验：如果所有 PSP 均不可用，结账会话进入 PAYMENT_PENDING 状态。买家看到"您的订单正在处理中——我们将在 5 分钟内通过邮件通知您。"后台 worker 在 PSP 恢复后重试。订单永远不会被丢弃。

Shopify routes buyers to the nearest region (GeoDNS / Anycast). Each region runs a full stack: Checkout, Payment, Order services, and regional Postgres shards. The key design decisions:Shopify 通过 GeoDNS / Anycast 将买家路由到最近的地域。每个地域运行完整技术栈：Checkout、Payment、Order 服务以及地域 Postgres 分片。关键设计决策：

  • Order SoT ownership: the order is created in the region that handled the checkout, tagged with region_id. That region is the canonical owner. Cross-region reads are served from async replicas (eventual, fine for order history).订单 SoT 归属：订单在处理该结账的地域创建，并打上 region_id 标记。该地域是规范所有者。跨地域读取由异步副本提供（最终一致性，对订单历史查询可接受）。
  • EU data residency: EU buyers' orders, payment records, and PII are written only to EU-region shards. The outbox relay stays within EU; Kafka topics for EU orders are EU-only partitions. Analytics pipelines anonymize before cross-region export.EU 数据驻留：EU 买家的订单、支付记录和 PII 仅写入 EU 地域分片。outbox 中继保持在 EU 境内；EU 订单的 Kafka topic 使用 EU 专属分区。分析流水线在跨地域导出前进行匿名化处理。
  • PSP routing: some PSPs have regional endpoints (e.g., Stripe EU). Route EU checkouts to the EU Stripe endpoint to satisfy data processing agreements.PSP 路由：部分 PSP 有地域端点（如 Stripe EU）。将 EU 结账路由到 Stripe EU 端点，以满足数据处理协议要求。
  • Inventory coordination: a globally distributed inventory service (see Q02) is consulted during the saga's reserve step. The reservation is durable in the inventory service; the checkout region only holds the saga state.库存协调：Saga 的预留步骤会咨询全局分布式库存服务（见 Q02）。预留状态在库存服务中持久化；结账地域仅持有 saga 状态。

⑦ The checkout saga timeline & compensation⑦ 结账 saga 时序与补偿

The checkout saga is a sequence of five forward steps, each with a corresponding compensating action. The key insight is that compensations must run in reverse order — you cannot void an authorization before you have tried to persist the order, and you cannot release inventory before you know the authorization failed. The orchestrator's durable state machine guarantees exactly-once progression and makes the right compensation choice based on which step last succeeded.

结账 saga 是五个正向步骤的序列，每个步骤都有对应的补偿操作。关键洞察是补偿必须以逆序运行——在尝试持久化订单之前不能作废授权，在知道授权失败之前不能释放库存。编排器的持久化状态机保证了精确一次的推进，并根据最后成功的步骤做出正确的补偿选择。

-- Happy path (left column) and compensating actions if a LATER step fails (right column)
-- Compensation runs in reverse: step N compensation fires before step N-1 compensation.

Step 1  reserve_inventory(cartItems)          → compensation: release_inventory(reservationId)
   if ok ↓
Step 2  authorize_payment(token, amount)        → compensation: void_authorization(authRef)
   if ok ↓
Step 3  persist_order(order + outbox, same txn)  → compensation: mark_order_CANCELLED (never DELETE)
   if ok ↓
Step 4  capture_payment(authRef)                → compensation: refund(captureRef)   [post-capture only]
   if ok ↓
Step 5  emit_order_confirmed(via outbox)         → compensation: emit_order_cancelled

-- Example: Step 3 fails after Step 2 succeeded → run in reverse: void_authorization, then release_inventory
-- Example: Step 4 fails after Step 3 succeeded → mark_order CANCELLED + void_authorization + release_inventory
-- Example: Step 4 succeeds but Step 5 relay is slow → outbox relay retries; emit is idempotent on orderId

Orchestration vs choreography for compensations: with orchestration, the saga orchestrator holds the current step in its own DB (saga_state row keyed by checkoutId). On failure it reads its own state, knows exactly which steps completed, and calls compensations in reverse with full context (the authRef, reservationId, etc. it captured earlier). With choreography, each service must react to a saga.failed event and infer whether its step ran from the event payload — fragile when the payload is incomplete or events arrive out of order. For checkout — where a compensation failure (e.g. void never confirmed) must be escalated to a human alert — orchestration is strongly preferred: the orchestrator's state row is the single source of truth for "where did this saga die and what still needs compensating."

补偿的编排 vs 编舞：使用编排时，saga 编排器将当前步骤保存在自己的 DB 中（以 checkoutId 为键的 saga_state 行）。失败时它读取自己的状态，精确知道哪些步骤已完成，并携带完整上下文（之前捕获的 authRef、reservationId 等）按逆序调用补偿。使用编舞时，每个服务必须对 saga.failed 事件做出反应，并从事件 payload 中推断它自己的步骤是否已运行——当 payload 不完整或事件乱序到达时非常脆弱。对于结账——补偿失败（如作废授权从未被确认）必须升级为人工告警——强烈推荐编排：编排器的状态行是"这个 saga 在哪里崩溃以及什么还需要补偿"的唯一事实来源。

Compensations must be idempotent and keyed by reservationId / orderId补偿必须是幂等的，并以 reservationId / orderId 为键

The saga orchestrator may retry a compensation if the first attempt times out — e.g., void_authorization may be called twice if the PSP response is lost. Each compensation must therefore be idempotent: void(authRef) on an already-voided authorization must return success, not an error. Use the reservationId or orderId as the idempotency key when calling downstream services, and forward it to the PSP just as you do for forward-path calls. A compensation that is not idempotent can refund or release inventory twice — which is a financial error in the opposite direction from oversell.

如果第一次尝试超时，saga 编排器可能会重试补偿——例如，如果 PSP 响应丢失，void_authorization 可能被调用两次。因此每个补偿必须是幂等的：对已作废授权调用 void(authRef) 必须返回成功，而非错误。在调用下游服务时使用 reservationId 或 orderId 作为幂等键，并像正向路径调用一样将其转发给 PSP。不幂等的补偿可能会重复退款或重复释放库存——这是与超卖方向相反的财务错误。

① Idempotency store durability — Redis-only vs DB-backed① 幂等存储持久性——仅 Redis vs DB 兜底

The tension: the idempotency lookup must be microsecond-fast on every checkout completion, but losing a key on a Redis crash means a retry can double-charge the buyer. Speed and durability are in direct conflict.

矛盾点：每次结账完成都要对幂等键做微秒级查找，但 Redis 崩溃导致键丢失，会让重试时对买家重复扣款。速度与持久性直接对立。

Option A · Redis only方案 A · 仅 Redis

Store the idempotency record exclusively in Redis with a 24-hour TTL; lookups are single-digit µs and impose no DB load.

将幂等记录独家存储在 Redis 中，设置 24 小时 TTL；查找延迟为个位数微秒级，对数据库无额外负载。

+ Blazing fast at any QPS; no extra DB round-trip; trivially horizontally scalable.

+ 任何 QPS 下都极快；不增加 DB 往返；水平扩展毫无压力。

− Redis is volatile: an unclean failover or a maxmemory eviction silently deletes the key. The next retry sees "not found" and proceeds to re-charge the buyer — a silent double-charge with no log trail. AOF/RDB reduce but do not eliminate the window.

− Redis 易失：非正常故障切换或 maxmemory 驱逐会静默删除键。下一次重试看到"未找到"便继续扣款——一次无日志记录的静默重复扣款。AOF/RDB 缩小但无法消除这一窗口。

Option B · DB only方案 B · 仅 DB

Write the idempotency_record row to Postgres before any downstream action; every lookup is a DB read (~5 ms).

在任何下游操作之前将 idempotency_record 行写入 Postgres；每次查找都是 DB 读取（约 5 ms）。

+ Durable and transactional; survives crashes, failovers, and evictions; auditable history for every idempotency decision.

+ 持久且事务性；能在崩溃、故障切换和驱逐后存活；每条幂等决策均有可审计历史记录。

− 5 ms added to every /complete call; at 30k checkout/s peak that is an extra ~150k DB reads/s — meaningful load increase; DB becomes a hot single point for fast-path idempotency.

− 每次 /complete 调用增加 5 ms；峰值 3 万结账/秒时约增加 15 万次/秒的 DB 读取——负载明显增加；DB 成为快速路径幂等性的热点单一依赖。

Use both, write DB first. Write the durable idempotency_record to the DB before starting the saga, then populate Redis as a fast cache. On lookup, check Redis first; on a miss, fall back to the DB. This way a Redis loss degrades performance (extra DB reads) but never silently enables a double-charge. The DB record is also the audit trail required by PCI DSS.

两者兼用，先写 DB。在启动 saga 之前先将持久化的 idempotency_record 写入 DB，再将 Redis 作为快速缓存填充。查找时先检查 Redis；未命中时回退到 DB。这样 Redis 丢失只会降低性能（额外 DB 读取），而永远不会静默地允许重复扣款。DB 记录也是 PCI DSS 要求的审计轨迹。

② Saga pattern — orchestration vs choreography② Saga 模式——编排 vs 编舞

The tension: a checkout involves at least four services (Inventory, Payment, Order, Fulfillment). How do you coordinate them — with a central conductor that knows every step, or by having each service react to the previous service's event?

矛盾点：结账涉及至少四个服务（库存、支付、订单、履单）。如何协调它们——用知道每个步骤的中央协调器，还是让每个服务对上一个服务的事件做出反应？

Option A · Orchestration方案 A · 编排

A Saga Orchestrator service drives the steps in order: reserve → authorize → create-order → capture → confirm. It knows the full state and owns all compensation logic.

Saga 编排器服务按顺序驱动各步骤：预留 → 授权 → 创建订单 → 扣款 → 确认。它知晓完整状态，并持有全部补偿逻辑。

+ Explicit, debuggable — you can query the orchestrator's DB to see exactly which step a saga is on; compensation is deterministic; operational visibility is clear; easy to add a new step.

+ 显式、可调试——可以查询编排器的 DB 来精确了解 saga 处于哪个步骤；补偿具有确定性；操作可见性清晰；新增步骤容易。

− The orchestrator is a shared coupling point — all services depend on it; adding a new service requires modifying the orchestrator; can become a bottleneck under very high throughput.

− 编排器是共享耦合点——所有服务都依赖它；新增服务需要修改编排器；在非常高的吞吐量下可能成为瓶颈。

Option B · Choreography方案 B · 编舞

Each service listens for an event from the previous step and emits its own event on completion. No central conductor: Inventory emits inventory.reserved, Payment picks it up and emits payment.authorized, and so on.

每个服务监听上一步骤的事件，完成后发出自己的事件。没有中央协调器：Inventory 发出 inventory.reserved，Payment 接收它并发出 payment.authorized，以此类推。

+ Services are loosely coupled and independently deployable; adding a new consumer requires no changes to existing services; naturally scales with Kafka partitions.

+ 服务松耦合且可独立部署；新增消费者不需要更改现有服务；随 Kafka 分区自然扩展。

− When step 2 fails mid-saga, which service owns the compensation? The answer is spread across multiple event handlers — very hard to trace a partial failure ("charged but no order") through distributed logs; difficult to prevent duplicate compensations racing; overall saga state is implicit, not queryable.

− 当第 2 步在 saga 中途失败时，谁负责补偿？答案分散在多个事件处理器中——通过分布式日志追踪部分失败（"已扣款但无订单"）非常困难；难以防止多个补偿操作竞争；总体 saga 状态是隐式的，无法直接查询。

When to use which何时用哪个

Orchestration for payment sagas. When real money is involved, you need to know exactly which step failed so you can compensate correctly. A stale Kafka event log is insufficient for debugging "we charged the customer but never created an order." Reserve choreography for read-side fan-out (notifications, analytics) where a missed event is low-stakes and retries are simple.

支付 saga 使用编排。涉及真实资金时，必须精确知道哪一步失败才能正确补偿。陈旧的 Kafka 事件日志不足以调试"我们对客户扣了款但从未创建订单"。编舞模式留给读侧扇出（通知、数据分析），那里遗漏事件风险低且重试简单。

③ Payment capture timing — synchronous vs async③ 扣款时机——同步 vs 异步

The tension: do you capture (debit the buyer's card) at the moment they click Pay, or hold an authorization and capture later when the item ships? The right answer varies by merchant type and has significant failure-mode implications.

矛盾点：是在买家点击支付的那一刻扣款（借记买家银行卡），还是先持有授权，在商品发货时再扣款？正确答案因商家类型而异，并对失败模式有重大影响。

Option A · Sync capture at checkout方案 A · 结账时同步扣款

Authorization and capture happen in the same PSP round-trip (or in two sequential calls with a negligible gap) at the moment the buyer confirms payment.

授权和扣款在买家确认付款的瞬间通过同一次 PSP 往返完成（或在两次连续调用中以可忽略的间隔完成）。

+ Simplest saga: no open authorizations to track or let expire; no async capture job to operate; the payment is finalized at the same moment the order is created.

+ Saga 最简单：没有需要跟踪或让其到期的开放授权；无需运行异步扣款任务；支付在订单创建的同一时刻完成终结。

− If fulfillment later fails (item out of stock, courier issue), you must issue a refund rather than simply voiding an auth — refunds take days and incur processing fees; poor UX for pre-orders or made-to-order goods.

− 如果履单后来失败（商品缺货、快递问题），你必须发起退款而非简单地作废授权——退款需要数天且产生手续费；对预售或定制商品的用户体验差。

Option B · Authorize now, async capture at fulfillment方案 B · 立即授权，履单时异步扣款

At checkout, authorize (reserve funds on the card) but do not yet capture. A worker triggers psp.capture(authRef) when the order.fulfilled event fires, typically hours or days later.

结账时授权（在银行卡上预留资金）但不立即扣款。当 order.fulfilled 事件触发时（通常数小时或数天后），worker 调用 psp.capture(authRef)。

+ If the item never ships, just void the auth — no money ever moved, no refund fees, instant for the buyer; ideal for pre-orders, ship-then-bill, and high-value physical goods.

+ 如果商品从未发货，只需作废授权——资金从未转移，无退款手续费，对买家即时生效；非常适合预售、先发货后收费和高价值实物商品。

− Card authorizations expire in 7–30 days (card network rules); if fulfillment is delayed, you must re-authorize which can fail if the buyer's card changed; adds an async capture job that must be durable, retryable, and monitored for stale auths.

− 银行卡授权在 7–30 天后过期（银行卡网络规则）；如果履单延迟，必须重新授权，可能因买家银行卡变更而失败；增加了一个必须持久化、可重试且需监控过期授权的异步扣款任务。

When to use which何时用哪个

Make it a per-merchant config. Default to sync capture for digital goods and instant-fulfillment merchants (simplest, no open-auth complexity). Use async capture for physical goods merchants who need ship-then-bill, pre-order merchants, and high-value items where avoiding refund fees matters. The saga orchestrator handles both by checking the merchant's capture mode before deciding whether to call psp.capture inline or emit a deferred capture event.

做成按商家可配置。对数字商品和即时履单商家默认使用同步扣款（最简单，无开放授权复杂性）。对需要先发货后收费的实物商品商家、预售商家以及需要避免退款手续费的高价值商品使用异步扣款。Saga 编排器在决定是内联调用 psp.capture 还是发出延迟扣款事件之前，先检查商家的扣款模式，从而同时处理两种情况。

④ Order write consistency — strong vs availability-first④ 订单写入一致性——强一致性 vs 可用性优先

The tension: the order row is the money source of truth — it must be durable. But waiting for synchronous replication acknowledgment doubles write latency. How much consistency overhead is justified?

矛盾点：订单行是资金的事实来源——它必须持久。但等待同步复制确认会使写入延迟翻倍。多大的一致性开销是合理的？

Option A · Strong consistency (sync replication ack)方案 A · 强一致性（同步复制确认）

The primary waits for at least one replica to acknowledge the write before returning success. Postgres synchronous standby or synchronous_commit = on.

主库在返回成功之前等待至少一个副本确认写入。Postgres 同步备库或 synchronous_commit = on。

+ Even if the primary crashes immediately after returning, the order row survives on the replica; zero data loss for committed orders; the financial ledger is never rolled back by a failover.

+ 即使主库在返回后立即崩溃，订单行也在副本上保存；已提交订单零数据丢失；财务账本永远不会因故障切换而回滚。

− ~2–4 ms added per write (cross-datacenter round-trip to replica); if the standby is slow or unreachable, writes stall; some availability sacrificed for durability.

− 每次写入增加约 2–4 ms（到副本的跨数据中心往返）；如果备库慢或不可达，写入会停顿；牺牲了部分可用性换取持久性。

Option B · Availability-first (async replication)方案 B · 可用性优先（异步复制）

Write to the primary only; replication to replicas is async. Return success as soon as the primary disk write completes.

仅写入主库；向副本的复制是异步的。主库磁盘写入完成后立即返回成功。

+ Lowest write latency; availability is unaffected by replica lag or network hiccups; fine for non-financial tables.

+ 写入延迟最低；可用性不受副本延迟或网络抖动影响；对非财务表完全适用。

− If the primary crashes between the COMMIT and the replica sync, the order row is lost on failover — the buyer was charged but there is no order; the worst possible inconsistency for a financial system.

− 如果主库在 COMMIT 与副本同步之间崩溃，故障切换时订单行丢失——买家已扣款但订单不存在；这是金融系统最糟糕的不一致情况。

When to use which何时用哪个

Strong consistency for order and payment writes; async replication for everything else. The 2–4 ms overhead on the money path is a small price to pay for never losing a committed order. For order history reads, event logs, analytics, and non-financial tables, async replication is fine — a buyer reading a slightly stale order history is not a correctness violation.

订单和支付写入使用强一致性；其他一切使用异步复制。资金路径上 2–4 ms 的额外开销是绝不丢失已提交订单的小代价。对于订单历史读取、事件日志、分析和非财务表，异步复制完全可以——买家读到略微过时的订单历史不是正确性违规。

⑤ PSP strategy — single PSP vs multi-PSP failover⑤ PSP 策略——单一 PSP vs 多 PSP 故障转移

The tension: a second PSP integration means extra engineering cost, routing logic, contract negotiation, and idempotency key namespace management. But a single PSP outage during BFCM is an existential revenue event. How much redundancy is worth building?

矛盾点：引入第二个 PSP 意味着额外的工程成本、路由逻辑、合同谈判以及 idempotency key 命名空间管理。但单个 PSP 在 BFCM 期间宕机是灾难性的营收事件。值得构建多大的冗余？

Option A · Single PSP方案 A · 单一 PSP

One PSP adapter, one contract, one idempotency key namespace. The Payment Service calls Shopify Payments (or Stripe) exclusively.

一个 PSP 适配器、一份合同、一个 idempotency key 命名空间。Payment Service 专门调用 Shopify Payments（或 Stripe）。

+ Simple integration, simple operations, no cross-PSP idempotency collision risk, single settlement report, lower engineering headcount to maintain.

+ 集成简单、运维简单、无跨 PSP 幂等碰撞风险、单份结算报告、维护所需工程人力更少。

− Full PSP outage kills checkout completely — during BFCM, even 5 minutes of downtime for a large merchant can mean millions in lost revenue; no leverage in contract negotiations; PSP rate changes have no alternative.

− PSP 完全宕机会彻底中断结账——在 BFCM 期间，对大型商家而言即使 5 分钟停机也意味着数百万的营收损失；合同谈判中没有筹码；PSP 费率变化没有替代选项。

Option B · Multi-PSP with circuit breaker方案 B · 多 PSP + 断路器

A primary PSP (Shopify Payments) backed by a secondary (PayPal, Adyen). A circuit breaker per PSP; when the primary circuit opens, route new checkouts to the secondary.

主 PSP（Shopify Payments）+ 备用 PSP（PayPal、Adyen）。每个 PSP 独立断路器；当主 PSP 断路打开时，将新的结账请求路由到备用 PSP。

+ Checkout remains available during a primary PSP outage; negotiating leverage; A/B routing for cost optimization; geographic routing for compliance (e.g. EU checkout → Stripe EU endpoint).

+ 主 PSP 宕机期间结账仍可用；具备谈判筹码；可进行成本优化的 A/B 路由；合规地理路由（如 EU 结账 → Stripe EU 端点）。

− Every PSP requires its own adapter, its own idempotency key prefix, its own settlement reconciliation lane, and its own webhook receiver config; routing logic adds a latency decision per checkout; two PSP contracts to negotiate and audit.

− 每个 PSP 都需要独立的适配器、独立的 idempotency key 前缀、独立的结算对账通道和独立的 webhook receiver 配置；路由逻辑为每次结账增加了决策延迟；需要谈判和审计两份 PSP 合同。

When to use which何时用哪个

Multi-PSP for any platform serving high-revenue merchants. The revenue cost of a PSP outage on a peak shopping day easily justifies the engineering investment. The circuit breaker is the key component: it gates the failover so routing overhead is zero on the happy path, and the switch is automatic. Start with single PSP for small merchants or MVP; add the secondary when checkout revenue justifies the extra integration complexity.

服务高营收商家的任何平台都应使用多 PSP。高峰购物日 PSP 宕机的营收损失轻易证明了工程投入的价值。断路器是关键组件：它控制故障转移，使正常路径的路由开销为零，且切换是自动的。从单一 PSP 开始用于小型商家或 MVP；当结账营收证明额外集成复杂度有价值时，再接入备用 PSP。

⑥ Event delivery semantics — at-least-once vs exactly-once⑥ 事件投递语义——至少一次 vs 精确一次

The tension: the outbox relay guarantees every committed order emits an event, but it can emit it more than once (if the relay crashes after publishing but before marking the row published). Exactly-once Kafka transactions avoid duplicates but add complexity. Which guarantee is right for money events?

矛盾点：outbox 中继保证每个已提交的订单都会发出一个事件，但它可能不止一次发出（如果中继在发布后、标记行已发布前崩溃）。精确一次 Kafka 事务避免重复但增加了复杂性。对资金事件而言，哪种保证是正确的？

Option A · At-least-once via outbox方案 A · outbox 实现的至少一次

The relay publishes the outbox row to Kafka, then marks it published. If the relay crashes between those two steps, it re-publishes on restart — consumers may see the same event twice.

中继将 outbox 行发布到 Kafka，然后将其标记为已发布。如果中继在这两步之间崩溃，重启后会重新发布——消费者可能看到同一事件两次。

+ Simple, broadly understood, works with any Kafka client version; no transactional producer overhead; the outbox itself is the atomicity guarantee — the event will always eventually be delivered.

+ 简单、广泛理解、适用于任何 Kafka 客户端版本；无事务性生产者开销；outbox 本身是原子性保证——事件始终最终会被投递。

− Every consumer must handle duplicates: fulfillment, notifications, analytics all need a deduplication key check before acting — adding defensive code to every consumer.

− 每个消费者都必须处理重复：履单、通知、数据分析在操作前都需要去重键检查——给每个消费者增加防御性代码。

Option B · Exactly-once via Kafka transactions方案 B · Kafka 事务实现的精确一次

Use Kafka's transactional producer API: the relay wraps publish + offset-commit in one atomic transaction. Combined with isolation.level=read_committed on consumers, each message is processed exactly once end-to-end.

使用 Kafka 的事务性生产者 API：中继将发布 + offset 提交包装在一个原子事务中。结合消费者端的 isolation.level=read_committed，每条消息端到端恰好处理一次。

+ Consumers need no deduplication logic; event-driven pipelines (fulfillment, accounting) are simpler and safer — no "did we already process this?" logic.

+ 消费者无需去重逻辑；事件驱动的流水线（履单、财务）更简单更安全——无需"我们已经处理过这个了吗？"的逻辑。

− Transactional producers require Kafka 0.11+, specific broker config, and exact client library support; transactions add ~10 ms latency per batch; fewer Kafka client languages support the full transactional API; much harder to reason about when debugging.

− 事务性生产者需要 Kafka 0.11+、特定的 broker 配置以及精确的客户端库支持；事务每批增加约 10 ms 延迟；支持完整事务 API 的 Kafka 客户端语言较少；调试时更难推断。

When to use which何时用哪个

At-least-once + idempotent consumers. The industry consensus for payment systems is to design every consumer to be idempotent (check a deduplication key — orderId, psp_ref — before acting) and accept at-least-once delivery. This approach is simpler, more portable across Kafka versions, and easier to test. Exactly-once is theoretically cleaner but imposes broker and client constraints that create operational fragility; in practice, Kafka transactions have enough edge cases that most teams at scale prefer defensive consumers.

至少一次 + 幂等消费者。支付系统的行业共识是将每个消费者设计为幂等（在操作前检查去重键——orderId、psp_ref），并接受至少一次投递。这种方法更简单、跨 Kafka 版本更可移植且更易测试。精确一次理论上更整洁，但对 broker 和客户端施加了约束，造成运维脆弱性；在实践中，Kafka 事务有足够多的边缘情况，以至于大多数大规模团队更偏好防御性消费者。

How do you reconcile against the PSP's ledger to make sure money ties out?如何与 PSP 账本对账以确保资金平衡？

Every PSP provides a settlement or transaction report (CSV or API). A nightly reconciliation job: (1) pulls all settled transactions from the PSP for the prior day; (2) joins against the payment table on psp_ref; (3) flags rows where our captured amount ≠ PSP settled amount, or where our DB has CAPTURED but the PSP doesn't show a settlement, or vice versa. Discrepancies are written to a reconciliation_alert table and paged to finance ops. FX rounding and multi-currency make this non-trivial — compare in the PSP's settlement currency, not our local currency. This process is the audit trail that satisfies PCI DSS requirement 12.3 and SOC2 financial integrity controls.每家 PSP 都提供结算或交易报告（CSV 或 API）。夜间对账任务：(1) 拉取 PSP 前一天的所有已结算交易；(2) 按 psp_ref 与 payment 表关联；(3) 标记我们的扣款金额 ≠ PSP 结算金额的行，或我们 DB 有 CAPTURED 但 PSP 不显示结算的行（反之亦然）。差异写入 reconciliation_alert 表并通过 PagerDuty 通知财务运营。FX 舍入和多币种使这并非小事——应以 PSP 的结算货币比较，而非本地货币。此流程是满足 PCI DSS 要求 12.3 和 SOC2 财务完整性控制的审计轨迹。

A card requires a 3-D Secure challenge — how does the async authorization flow work?银行卡需要 3-D Secure 验证——异步授权流程如何运作？

When the PSP signals that 3DS is required (via a redirect_url in its authorize response), the payment saga pauses and leaves the payment in PENDING_AUTH state. The buyer is redirected (or shown an in-page iframe) to the card issuer's authentication page for SCA (Strong Customer Authentication). After the buyer completes the challenge, the issuer posts a callback to the PSP, which then fires a payment.authorized webhook back to our PSP Webhook Receiver. The receiver drives the payment state machine from PENDING_AUTH → AUTHORIZED and resumes the saga (create order → capture). The checkout session must be kept alive with a generous TTL (~15 min) to accommodate the redirect round-trip. The idempotency key remains valid throughout — a replay after the webhook still resolves to the existing authorized charge.当 PSP 在授权响应中返回 redirect_url、表明需要 3DS 验证时，支付 saga 暂停，将支付状态置为 PENDING_AUTH。买家被重定向（或通过页内 iframe）至发卡行的 SCA 强认证页面。买家完成验证后，发卡行将回调发送给 PSP，PSP 再通过 payment.authorized webhook 通知我们的 PSP Webhook Receiver。Receiver 将支付状态从 PENDING_AUTH 推进到 AUTHORIZED，并恢复 saga（创建订单 → 扣款）。Checkout session 必须设置足够长的 TTL（约 15 分钟）以覆盖重定向往返时间。整个过程中 idempotency key 保持有效——webhook 到达后的重放仍会解析到已有的授权记录，不会产生重复扣款。

How do you reconcile your order/payment ledger against the PSP's daily settlement report?如何将订单/支付账本与 PSP 的每日结算报告对账？

Every PSP exposes a settlement report (CSV download or paginated API) for the prior business day. A nightly batch reconciliation job runs in three phases: (1) Ingest — pull the PSP report and load it into a staging table keyed on psp_ref. (2) Match — left-join the staging table against our payment table on psp_ref; rows that match with equal amounts are marked reconciled. (3) Alert — any unmatched or amount-mismatched rows are written to a reconciliation_alert table and paged to finance ops via PagerDuty. Common mismatch sources: FX rounding differences (always compare in PSP settlement currency), refunds that landed after the report cut-off, and chargebacks that reduced the net settlement. The process must be idempotent so that re-running it after a late report arrival does not create duplicate alerts. This is a PCI DSS requirement and a SOC2 financial integrity control.每家 PSP 都会提供前一个工作日的结算报告（CSV 或分页 API）。夜间批量对账作业分三个阶段运行：(1) 摄取——拉取 PSP 报告，以 psp_ref 为键加载到暂存表。(2) 匹配——暂存表与我们的 payment 表按 psp_ref 左连接；金额相符的记录标记为已对账。(3) 告警——未匹配或金额不符的行写入 reconciliation_alert 表，并通过 PagerDuty 通知财务运营团队。常见不匹配原因：FX 舍入差异（始终以 PSP 结算币种比较）、报告截止时间后才到账的退款，以及导致净结算金额减少的拒付。该作业必须是幂等的，以免在报告延迟到达后重跑时产生重复告警。此流程是 PCI DSS 合规要求，也是 SOC2 财务完整性控制项。

Partial refunds and chargebacks — what state transitions and events fire?部分退款与拒付——会触发哪些状态流转和事件？

Partial refund: POST /orders/{id}/refund with amount < original_capture creates a new payment row with type=REFUND and transitions its state INITIATED → REFUNDED. The receiver creates a Dispute record and moves the payment into a DISPUTED state (separate from the main CAPTURED/REFUNDED path). The event payment.disputed notifies the merchant to submit evidence. Tax/shipping calculation service fails mid-checkout — what happens?结账途中税费/运费计算服务失败——系统如何处理？

Tax and shipping totals must be finalized before authorization — authorizing the wrong amount creates a legal and accounting mess. If the tax/shipping service is unavailable during /checkouts/{id}/complete, the correct behavior is to fail the checkout step gracefully: return an error to the buyer, leave the checkout session in CREATED (not PROCESSING), and do not attempt PSP authorization. The client retries /complete after a short back-off; the idempotency key ensures no charge is attempted until totals are confirmed. To build resilience: (1) a short cached result (30 s TTL) covers transient blips during the checkout session; (2) a circuit breaker prevents cascading timeouts; (3) a fallback to a static tax table is acceptable only for known-simple jurisdictions as a last resort. The invariant to state explicitly: never authorize payment on stale or missing totals.税费和运费金额必须在授权之前确定——对错误金额授权会带来法律和会计上的混乱。如果在 /checkouts/{id}/complete 期间税费/运费服务不可用，正确做法是优雅地让该步骤失败：向买家返回错误，将 checkout session 保持在 CREATED（而非 PROCESSING），不尝试 PSP 授权。客户端在短暂退避后重试 /complete；idempotency key 确保在总金额确认之前不会发起扣款。韧性设计建议：(1) 短时缓存结果（30 秒 TTL）可覆盖结账期间的短暂抖动；(2) 断路器防止级联超时；(3) 仅作为最后手段，在已知简单税区可回退到静态税率表。需要明确陈述的不变量：永远不要对陈旧或缺失的总金额发起支付授权。

Multi-currency / FX: where is the rate computed and locked?多币种 / FX：汇率在哪里计算并锁定？

The FX rate must be locked at checkout creation (POST /checkouts), not at payment time — this prevents the buyer from seeing a different total if the rate shifts during the 30-minute session. The checkout session stores both the presentment currency (what the buyer sees, e.g. EUR) and the settlement currency (what the merchant gets paid in, e.g. USD), along with the locked rate and the timestamp. The PSP receives the charge in the presentment currency and handles FX on its end, or we charge in the settlement currency and display an equivalent — depending on the PSP's multi-currency capabilities. On retry, the idempotency key ensures the same locked rate is used; the idempotency record stores the totals object so a replay never recomputes FX. A new checkout session must be created if the buyer changes currency — there is no in-session rate update.FX 汇率必须在创建 checkout session 时（POST /checkouts）锁定，而不是在支付时——这样可以防止在 30 分钟的会话期间汇率波动导致买家看到不同的总金额。Checkout session 同时存储展示货币（买家看到的，例如 EUR）和结算货币（商家收款的，例如 USD），以及锁定汇率和时间戳。PSP 以展示货币收取费用并在其端处理 FX，或者我们以结算货币扣款并展示等值金额——取决于 PSP 的多币种能力。重试时，idempotency key 确保使用同一锁定汇率；幂等记录存储了 totals 对象，重放时永远不会重新计算 FX。如果买家切换货币，必须创建新的 checkout session——不支持会话内汇率更新。

How do you test idempotency and partial-failure paths?如何测试幂等性和部分失败路径？

Idempotency and partial failures cannot be verified by happy-path integration tests alone — they require deliberate fault injection. Concrete test cases: (1) Kill after PSP call, before DB write — inject a process crash immediately after the PSP authorize response; replay the same idempotency key; assert the PSP is queried (not re-charged) and the final order count is exactly one. (2) Duplicate concurrent requests — send two identical /complete requests with the same idempotency key simultaneously; assert exactly one charge and one order created. (3) Replay webhooks — deliver the same payment.captured webhook twice; assert the payment state transitions only once and no duplicate fulfillment events fire. (4) Stale idempotency lease — artificially expire the PROCESSING lease; assert the handler recovers via PSP query rather than re-charging. These tests should run in a staging environment against a PSP sandbox that supports idempotency key inspection (Stripe test mode works well). Property-based tests can fuzz request body hashes to verify 409 behavior.幂等性和部分失败路径仅靠正常路径的集成测试无法验证——必须进行刻意的故障注入。具体测试用例：(1) PSP 调用后、DB 写入前崩溃——在 PSP 授权响应返回后立即注入进程崩溃；用相同的 idempotency key 重放；断言 PSP 被查询（而非重复扣款），最终订单数量恰好为一。(2) 并发重复请求——同时发送两个携带相同 idempotency key 的 /complete 请求；断言恰好只有一次扣款和一个订单被创建。(3) 重放 webhook——两次投递同一个 payment.captured webhook；断言支付状态只流转一次，且不触发重复的履单事件。(4) 幂等租约过期——人为使 PROCESSING 租约过期；断言处理器通过 PSP 查询恢复，而非重新扣款。这些测试应在 Staging 环境中针对支持 idempotency key 查询的 PSP 沙箱运行（Stripe 测试模式效果良好）。基于属性的测试可以对请求体哈希进行模糊测试，以验证 409 行为。

⭐ Staff-level summary — say these five thingsStaff 级总结——务必说出这五点
  1. Idempotency key end-to-end: client → Checkout Service → PSP. The key must travel all the way to the PSP so that a crashed-and-replayed request resolves against an existing charge, never creates a new one.端到端 idempotency key：客户端 → Checkout Service → PSP。该键必须一路传到 PSP，这样崩溃后重放的请求会解析到已有扣款，永远不会创建新的扣款。
  2. Order is the durable source of truth; payment is a state machine hanging off it. The DB is the money ledger — never derive financial state from cache or event logs alone.订单是持久的事实来源；支付是挂靠在它上面的状态机。DB 是资金账本——永远不要仅从缓存或事件日志推导财务状态。
  3. Outbox eliminates dual-write loss: order + event in one DB transaction; relay publishes asynchronously. This is how you guarantee the fulfillment pipeline always starts.Outbox 消除双写丢失：订单 + 事件在同一 DB 事务中写入；中继异步发布。这是保证履单流水线始终启动的方式。
  4. Saga with explicit compensation: the orchestrator knows which step failed and runs the right compensation. Choreography is too hard to debug when real money is involved.带显式补偿的 Saga：编排器知道哪一步失败并执行正确的补偿。涉及真实资金时，编舞模式太难调试。
  5. PSP is an unreliable dependency: circuit-break, failover, reconcile. The three failure cases to name: (a) timeout after PSP call (query first, never blind retry), (b) webhook lost (reconciliation polling loop), (c) PSP fully down (queue-and-retry, never drop the order).PSP 是不可靠的依赖：断路、故障转移、对账。需要点名的三种失败场景：(a) PSP 调用后超时（先查询，绝不盲目重试），(b) webhook 丢失（对账轮询循环），(c) PSP 完全宕机（排队重试，永不丢弃订单）。
