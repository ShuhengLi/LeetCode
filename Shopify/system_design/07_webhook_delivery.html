Design a Webhook & Event Delivery System设计 Webhook 与事件投递系统

"Shopify's app ecosystem relies on webhooks: when an order is placed, inventory changes, or a product updates, deliver that event to thousands of third-party apps. A dropped webhook means a merchant's fulfillment or accounting app silently misses an order. Design at-least-once delivery with retries, isolation, and HMAC security." "Shopify 的应用生态系统依赖 Webhook：当订单创建、库存变动或商品更新时，将该事件投递给数千个第三方应用。一条丢失的 Webhook 意味着商家的履单或账务系统静默地漏掉了一笔订单。请设计一个支持 at-least-once 投递、重试、隔离和 HMAC 安全签名的系统。"

Seen: integration backbone / app partner framing常见场景：集成骨干 / 应用合作伙伴 Tests: async reliability + fan-out at scale考察：异步可靠性 + 大规模扇出 60 min
Why this question matters为什么这道题重要 Webhooks are the integration backbone of Shopify's partner ecosystem. The system must fan out one internal event to potentially thousands of subscribed endpoints, retry failures gracefully, isolate a single dead subscriber from affecting all others, and survive the event storm that a flash sale produces. The tricky parts — at-least-once semantics, head-of-line blocking, ordering vs throughput — are exactly the distributed-systems tensions interviewers probe at senior and staff level. Webhook 是 Shopify 合作伙伴生态的集成骨干。系统需要将一个内部事件扇出给潜在的数千个订阅端点，优雅地重试失败，隔离单个宕掉的订阅者使其不影响其他端点，并在抢购引发的事件风暴中保持稳定。其中的难点——at-least-once 语义、队头阻塞、顺序性 vs 吞吐量——正是面试官在 senior/staff 级别着重探查的分布式系统张力。

① At-least-once delivery and consumer idempotencyAt-least-once 投递与消费者幂等性

Shopify's honest contract is at-least-once: we guarantee every event is delivered at least once, and subscribers must deduplicate via X-Shopify-Webhook-Id. Exactly-once over HTTP to arbitrary third-party endpoints is impractical — it requires the subscriber to participate in a two-phase protocol (e.g. transactional outbox + subscriber-side idempotency key in a database), and we have no control over subscriber infrastructure. The correct frame is: Shopify retries until it gets a 2xx; the subscriber checks whether it has already processed this delivery ID before acting.Shopify 诚实的契约是 at-least-once：我们保证每个事件至少投递一次，订阅者必须通过 X-Shopify-Webhook-Id 自行去重。对任意第三方端点在 HTTP 上实现精确一次不现实——它要求订阅者参与两阶段协议（例如 transactional outbox + 订阅者侧的幂等键入库），而我们无法控制订阅者的基础设施。正确的表述是：Shopify 重试直到收到 2xx；订阅者在处理前检查是否已处理过该投递 ID。

Why exactly-once over HTTP is impractical为何 HTTP 上的精确一次不现实 Even with an idempotent HTTP method, network partitions mean a 2xx ACK can be lost after the subscriber has already processed the event. Without a distributed transaction that spans both sides of the HTTP call — which requires subscriber cooperation and infrastructure we cannot mandate — exactly-once is not achievable. At-least-once + subscriber-side deduplication is the industry-standard contract for webhook systems (Stripe, GitHub, Shopify all use it). 即使使用幂等的 HTTP 方法，网络分区也意味着订阅者已处理事件后 2xx ACK 可能丢失。如果没有跨越 HTTP 调用两端的分布式事务——而这需要订阅者配合和我们无法强制要求的基础设施——精确一次就无法实现。At-least-once + 订阅者侧去重是 Webhook 系统的行业标准契约（Stripe、GitHub、Shopify 均采用此方案）。

② Retry strategy with exponential back-off指数退避重试策略

Each failed delivery is scheduled for a retry after an exponentially increasing delay, plus random jitter to prevent synchronized retry storms when a subscriber comes back online after an outage. The retry schedule is stored as delivery.next_retry_at; a polling scheduler runs every few seconds to enqueue due deliveries.每次投递失败后，按指数递增的延迟安排重试，并加入随机抖动，以防止订阅者故障恢复上线时出现同步重试风暴。重试计划存储为 delivery.next_retry_at；轮询调度器每隔几秒运行一次，将到期的投递重新入队。

-- Retry schedule (attempts → delay before next try)
attempt 1  : immediately (first try)
attempt 2  : 1 min  + jitter(0–30s)
attempt 3  : 5 min  + jitter(0–60s)
attempt 4  : 15 min + jitter(0–120s)
attempt 5  : 1 hr   + jitter(0–5min)
attempt 6  : 3 hr   + jitter(0–15min)
...
attempt 19 : ~24 hr + jitter  → total window ~48 hr
attempt 20 : state = DLQ, merchant alerted

-- Formula: delay_i = min(cap, base × 2^i) + rand(0, jitter_cap)
-- base=60s, cap=86400s (1 day), jitter_cap=0.2×delay_i

Merchants can trigger manual redelivery from the dashboard at any point, including for DLQ entries, via POST /webhooks/{id}/deliveries/{deliveryId}/redeliver. This re-enqueues the task and resets the attempt counter.商家可随时从 Dashboard 触发手动重新投递，包括 DLQ 中的条目，通过 POST /webhooks/{id}/deliveries/{deliveryId}/redeliver。这会将任务重新入队并重置重试计数器。

③ Isolation — eliminating head-of-line blocking隔离——消除队头阻塞

The single most important architectural decision is per-endpoint queues. If all deliveries for all subscriptions share one queue, a subscriber whose endpoint is down or responding in 30 s will cause all deliveries behind it to wait — the classic head-of-line blocking problem.最重要的架构决策是采用 per-endpoint 队列。如果所有订阅的所有投递共用一个队列，某个端点宕机或响应需 30 秒，就会导致其后所有投递等待——这是经典的队头阻塞问题。

Danger: shared queue causes global backlog风险：共享队列导致全局积压 With a single delivery queue, one endpoint that takes 30 seconds to time out will consume worker threads and back up deliveries for all other healthy subscribers. During an event storm, this cascades: a single dead endpoint can cause the entire delivery pipeline to stall for minutes, impacting thousands of merchants whose subscribers are perfectly healthy. Per-endpoint queues are non-negotiable for isolation. 在单一投递队列中，一个超时需 30 秒的端点会占用 Worker 线程，并阻塞所有其他健康订阅者的投递。在事件风暴期间，这会产生级联效应：单个宕机端点可能导致整个投递管道停滞数分钟，影响数千个订阅者完全健康的商家。Per-endpoint 队列对于隔离而言是不可妥协的。

Additional isolation measures:额外的隔离措施：

  • Per-endpoint circuit breaker: after N consecutive failures, open the circuit and skip the endpoint for a cool-down period. Re-probe with a single request (half-open state) before resuming. Deliveries during the open state are queued normally but the worker short-circuits without attempting HTTP, preserving worker throughput.Per-endpoint 熔断器：连续 N 次失败后断开熔断，在冷却期内跳过该端点。恢复前用单次请求探测（半开状态）。断路期间投递正常入队，但 Worker 短路跳过 HTTP 请求，保持 Worker 吞吐量。
  • Per-endpoint rate limiting: prevent delivery workers from hammering a recovering subscriber with the backlog all at once. Drain the queue at a controlled rate after the circuit closes.Per-endpoint 速率限制：防止投递 Worker 在熔断恢复后将积压的请求一次性砸向正在恢复的订阅者。熔断关闭后以受控速率消费队列。
  • Worker pool partitioning: optionally dedicate a worker pool to high-volume topics to prevent low-volume endpoints from being starved during peaks.Worker 池分区：可选地为高流量主题分配专用 Worker 池，防止低流量端点在峰值期间被饿死。

④ Ordering — per-shop/per-topic vs. throughput顺序性——按店/按主题 vs. 吞吐量

Strict global ordering across all subscriptions is too expensive. The practical approach: use Kafka partitions keyed by shop_id for the event bus, giving coarse per-shop ordering at the ingestion layer. Within fan-out, enqueue delivery tasks in partition order. Delivery workers process a subscription's queue serially (one in-flight at a time) to maintain topic-level ordering for that endpoint.跨所有订阅的严格全局顺序代价太高。实际做法：事件总线使用以 shop_id 为键的 Kafka 分区，在摄入层实现粗粒度的按店有序。在扇出阶段，按分区顺序将投递任务入队。投递 Worker 串行处理订阅队列（同一时刻只有一条在途），以维护该端点的主题级顺序。

⑤ Security — HMAC signing and replay protection安全性——HMAC 签名与防重放攻击

Each subscription has a per-subscription secret (random 32-byte value, stored hashed in the DB, transmitted to the app owner once at registration). The delivery worker computes:每个订阅拥有一个按订阅独立的密钥（32 字节随机值，在数据库中存储其哈希值，在注册时一次性传给应用所有者）。投递 Worker 计算：

signature = base64( HMAC-SHA256( subscription.secret, request_body ) )
header:  X-Shopify-Hmac-SHA256: <signature>

Subscribers verify the signature against their stored secret before processing the payload. This authenticates origin (only Shopify knows the secret) and payload integrity (any tampering invalidates the HMAC).订阅者在处理 payload 前用其存储的密钥验证签名。这既验证了来源（只有 Shopify 知道密钥），也验证了 payload 完整性（任何篡改都会使 HMAC 失效）。

Replay protection: include X-Shopify-Delivered-At (ISO timestamp). Subscribers reject any delivery where the timestamp is more than 5 minutes old. Combined with the delivery ID in X-Shopify-Webhook-Id, this prevents both replay attacks and duplicate processing.防重放攻击：附带 X-Shopify-Delivered-At（ISO 时间戳）。订阅者拒绝时间戳超过 5 分钟的投递。结合 X-Shopify-Webhook-Id 中的投递 ID，可同时防止重放攻击和重复处理。

Additional security controls: HTTPS only (reject non-TLS endpoint addresses at registration); ownership verification at registration time via a challenge-response or DNS token (so apps cannot register a subscription pointing at a competitor's endpoint).额外安全控制：仅允许 HTTPS（注册时拒绝非 TLS 端点地址）；注册时通过挑战-响应或 DNS token 验证端点所有权（防止应用将订阅注册到竞争对手的端点）。

⑥ Event storms and back-pressure事件风暴与背压

⑦ The delivery state machine & DLQ replay投递状态机与 DLQ 重放

Every delivery record is a small state machine. Getting the transitions right is what makes at-least-once delivery safe without causing runaway retry storms or permanent data loss. There are three interleaved state machines at work: the per-delivery lifecycle, the per-endpoint circuit breaker, and the merchant-initiated replay flow. Each must be understood independently and then composed.

每条投递记录都是一个小型状态机。把状态转换做对，正是在不引发失控重试风暴或永久数据丢失的前提下安全实现 at-least-once 投递的关键。这里有三个交织的状态机：单条投递的生命周期、per-endpoint 熔断器，以及商家发起的重放流程。每个都需要独立理解，再组合使用。

Per-delivery state machine: a delivery starts PENDING. The worker picks it up (IN_FLIGHT) and POSTs to the subscriber. A 2xx response transitions it to DELIVERED — terminal. Any non-2xx or connection error returns it to a scheduled retry (PENDING with an updated next_retry_at), incrementing the attempt counter. After the maximum attempt count is exhausted the delivery moves to DLQ — not deleted, but parked for merchant inspection and replay. Note: a 4xx response (subscriber intentionally rejected the payload) is not retried — it is immediately DLQ'd with a CLIENT_REJECTION reason, since retrying a payload the subscriber has already rejected is wasteful and potentially harmful.

单条投递状态机：投递以 PENDING 状态开始。Worker 拾取后变为 IN_FLIGHT，并向订阅者发起 POST。收到 2xx 响应则转为 DELIVERED——终态。非 2xx 或连接错误则返回到定时重试状态（PENDING 并更新 next_retry_at），同时递增重试计数。重试次数耗尽后，投递转为 DLQ——不是删除，而是停放供商家检查和重放。注意：4xx 响应（订阅者有意拒绝 payload）不触发重试——立即以 CLIENT_REJECTION 原因进入 DLQ，因为对订阅者已明确拒绝的 payload 重试既浪费又可能有害。

Per-endpoint circuit breaker: the circuit breaker runs orthogonally to individual delivery state. It tracks consecutive failure counts across all deliveries to an endpoint. After N consecutive failures (CLOSED → OPEN), the circuit opens: delivery workers short-circuit without making an HTTP connection, preserving worker-thread capacity for healthy endpoints. This is the mechanism that prevents one dead subscriber from causing head-of-line blocking. Deliveries during the open window are still queued normally — they are not dropped — they just aren't dispatched until the circuit probes. After a cool-down interval the circuit enters HALF_OPEN: a single probe request is sent. A 2xx closes the circuit (HALF_OPEN → CLOSED) and the worker begins draining the queue at a rate-limited pace. A failure re-opens it (HALF_OPEN → OPEN) and the cool-down resets.

Per-endpoint 熔断器：熔断器与单条投递状态正交运行。它跟踪对一个端点所有投递的连续失败次数。连续失败 N 次后（CLOSED → OPEN），熔断器断开：投递 Worker 短路，不发起 HTTP 连接，为健康端点保留 Worker 线程容量。这正是防止一个宕机订阅者造成队头阻塞的机制。断路期间投递仍正常入队——不是丢弃——只是不发出，直到熔断器探测。冷却间隔后熔断器进入 HALF_OPEN：发送一次探测请求。收到 2xx 则关闭熔断（HALF_OPEN → CLOSED），Worker 开始以限速节奏消费队列。失败则重新断开（HALF_OPEN → OPEN），冷却计时重置。

Merchant-initiated replay: merchants can re-enqueue any subset of deliveries — including DLQ entries — via the replay API. The replay flow queries the durable event log (the append-only event table) by topic and time range, then creates new delivery rows for each matching event against the current active subscriptions. Critically, new delivery.id values are generated — the subscriber receives a fresh X-Shopify-Webhook-Id. Idempotent subscribers detect that they have already processed the underlying event.idempotency_key and skip re-processing. Non-idempotent subscribers will double-process — which is why the contract always requires subscriber-side idempotency. The replay enqueue rate is capped to avoid thundering-herd on a recently recovered endpoint.

商家发起的重放：商家可通过重放 API 将任意子集的投递——包括 DLQ 条目——重新入队。重放流程通过主题和时间范围查询持久化事件日志（仅追加的 event 表），然后为匹配事件针对当前活跃订阅创建新的 delivery 行。关键在于：会生成新的 delivery.id——订阅者收到新的 X-Shopify-Webhook-Id。幂等订阅者检测到已处理过底层 event.idempotency_key 后跳过重处理。非幂等订阅者则会重复处理——这正是契约始终要求订阅者侧幂等性的原因。重放入队速率受上限约束，避免对刚恢复的端点造成惊群效应。

Every path through this state machine — retries on transient errors, circuit breaker probes, and especially merchant-initiated replay — can deliver the same event more than once. ① Delivery guarantee — at-least-once vs. exactly-once① 投递保证——at-least-once vs. exactly-once

The tension: subscribers want zero duplicates, but guaranteeing exactly-once over an HTTP boundary you don't own requires the subscriber to cooperate in a distributed transaction — something Shopify cannot mandate.

矛盾点：订阅者希望零重复，但在你无法掌控的 HTTP 边界上保证精确一次，需要订阅者参与分布式事务——这是 Shopify 无法强制要求的。

Option A · At-least-once方案 A · At-least-once

Shopify retries until it receives a 2xx; each retry carries the same X-Shopify-Webhook-Id. Subscribers are responsible for checking this ID against a seen-set before acting.

Shopify 重试直到收到 2xx；每次重试携带相同的 X-Shopify-Webhook-Id。订阅者负责在处理前核对已处理 ID 集合。

+ No cross-boundary distributed transaction required; scales to arbitrary third-party infrastructure. Simple retry loop on our side. Industry standard (Stripe, GitHub, PagerDuty all use it).

+ 不需要跨边界分布式事务；可扩展到任意第三方基础设施。我方重试逻辑简单。行业标准（Stripe、GitHub、PagerDuty 均采用此方案）。

− Duplicates are possible — a retry after a network partition where the subscriber already processed the event. Subscriber must implement idempotency logic, which increases app developer burden.

− 重复投递是可能的——在订阅者已处理事件后发生网络分区时仍会重试。订阅者必须实现幂等逻辑，增加了应用开发者的负担。

Option B · Exactly-once方案 B · Exactly-once

Requires a two-phase protocol spanning both sides of the HTTP call: Shopify writes to a transactional outbox, subscriber writes an idempotency key atomically with its business logic, and both sides participate in acknowledgment tracking.

需要横跨 HTTP 调用两端的两阶段协议：Shopify 写入事务性 outbox，订阅者将幂等键与业务逻辑原子写入，双方共同参与确认跟踪。

+ Zero duplicate processing — every event is acted on exactly once, which simplifies subscriber logic for non-idempotent operations (e.g. financial ledger entries).

+ 零重复处理——每个事件恰好被处理一次，简化了非幂等操作的订阅者逻辑（如财务账本条目）。

− Impossible to enforce without subscriber cooperation and compatible infrastructure. Even with an idempotent HTTP method, a 2xx ACK can be lost after the subscriber already processed — no way to distinguish "processed and ACK lost" from "not yet processed" without a shared transaction log. Complexity explodes; onboarding any third-party app becomes a protocol negotiation.

− 没有订阅者配合和兼容基础设施就无法强制实施。即使使用幂等的 HTTP 方法，2xx ACK 也可能在订阅者处理后丢失——不借助共享事务日志无法区分"已处理但 ACK 丢失"与"尚未处理"。复杂度爆炸；引入任何第三方应用都变成协议谈判。

The tension: operational simplicity of one queue vs. isolation correctness of one queue per subscriber. A single dead endpoint behind a shared queue can silently poison deliveries to every healthy subscriber.

矛盾点：单队列的运维简洁性 vs. 按订阅者独立队列的隔离正确性。共享队列中一个宕机端点会静默地毒害所有健康订阅者的投递。

每个订阅拥有自己的逻辑队列。投递 Worker 独立消费；一个队列的积压对其他队列的消费速率零影响。

− 队列激增：拥有数百万订阅的平台需要精心的队列管理基础设施（惰性创建、清理空队列、元数据存储）。监控扇出更复杂——需要跨所有队列聚合指标。

所有投递任务进入一个（或少数几个）全局队列，由共享 Worker 池消费。

+ Operationally simple — one queue to monitor, one worker pool to scale, trivial to reason about total throughput. Easy to get started.

+ 运维简单——只需监控一个队列，扩容一个 Worker 池，总吞吐量易于推理。快速上手。

No isolation guarantee — SLA for healthy subscribers degrades with the worst subscriber on the platform.

− 队头阻塞在规模下是灾难性的。一个 30 秒超时的订阅者占用 Worker 线程 30 秒；在黑五事件风暴期间，少数宕机端点就能阻塞数千个健康应用的投递。无隔离保证——健康订阅者的 SLA 随平台上最差订阅者的状态而降级。

Per-endpoint queues are non-negotiable at Shopify's app ecosystem scale. The isolation requirement is a correctness property, not a performance optimization. A shared queue is only appropriate for very low-volume, internal-only webhook systems where all subscribers are trusted and well-behaved.

在 Shopify 应用生态的规模下，per-endpoint 队列不可妥协。隔离需求是正确性属性，而非性能优化。共享队列仅适用于极低流量、仅供内部使用的 Webhook 系统，且所有订阅者可信且行为良好。

③ Fan-out style — synchronous vs. asynchronous③ 扇出方式——同步 vs. 异步

The tension: the simplest fan-out happens inline — when an order is created, immediately POST to all subscribers. But this couples the order pipeline's latency directly to every subscriber's response time.

矛盾点：最简单的扇出是内联完成——订单创建时立即 POST 给所有订阅者。但这将订单管道的延迟与每个订阅者的响应时间直接耦合。

Option A · Synchronous fan-out方案 A · 同步扇出

Fan-out happens inline during event handling — the order service calls all subscriber endpoints before returning a response or committing the order.

扇出在事件处理时内联发生——订单服务在返回响应或提交订单之前调用所有订阅者端点。

+ Simple to reason about; no intermediate queue to manage; delivery confirmation is immediate within the same transaction boundary.

+ 逻辑简单易懂；无中间队列需要管理；在同一事务边界内立即确认投递。

− Any slow or failing subscriber directly increases order latency. At 20 subscribers × 500 ms each, an order takes 10 s just for webhooks. Fan-out amplification (one order event → 5,000 POSTs during BFCM) makes checkout unusable. Entire order pipeline fails if a subscriber is unreachable.

− 任何慢速或失败的订阅者都会直接增加订单延迟。20 个订阅者 × 每个 500 毫秒，一笔订单光 Webhook 就要 10 秒。扇出放大效应（一个订单事件 → 黑五期间 5000 次 POST）使结账不可用。若有订阅者不可达，整个订单管道就会失败。

Option B · Async fan-out via Kafka方案 B · 经由 Kafka 的异步扇出

Domain services emit events to Kafka and immediately return. A dedicated Fan-out Service consumes from Kafka and enqueues delivery tasks at its own pace.

领域服务向 Kafka 发出事件后立即返回。专属 Fan-out Service 从 Kafka 消费，并按自身节奏将投递任务入队。

+ Order pipeline latency is completely decoupled from webhook delivery. Kafka buffer absorbs any spike. Fan-out consumer can scale independently. Failed deliveries don't affect the order success path at all.

+ 订单管道延迟与 Webhook 投递完全解耦。Kafka 缓冲吸收任何尖峰。Fan-out 消费者可独立扩容。投递失败完全不影响订单成功路径。

− Adds operational complexity (Kafka cluster, consumer lag monitoring, offset management). Delivery is no longer synchronous with the originating transaction — a slight delay (seconds to minutes under load) is expected and must be communicated to app developers.

− 增加运维复杂度（Kafka 集群、消费者 lag 监控、offset 管理）。投递不再与来源事务同步——在负载下预期会有轻微延迟（秒到分钟级），必须告知应用开发者。

When to use which何时用哪个

Async via Kafka is mandatory for any production webhook system at significant scale. The order pipeline must not wait for webhook delivery. Synchronous fan-out is only viable for very low-volume internal notifications where all subscribers are on the same network with sub-millisecond RTT.

在任何有一定规模的生产 Webhook 系统中，经由 Kafka 的异步扇出是必须的。订单管道绝不能等待 Webhook 投递。同步扇出仅适用于极低流量、所有订阅者在同一网络且 RTT 亚毫秒级的内部通知场景。

④ Ordering vs. throughput — serial per-subscription vs. unordered parallel④ 顺序性 vs. 吞吐量——按订阅串行 vs. 无序并行

The tension: guaranteeing that orders/create arrives before orders/updated at a subscriber requires serial per-subscription delivery, which caps throughput at one-in-flight-at-a-time per subscriber. Most subscribers don't actually need this.

矛盾点：保证 orders/create 在 orders/updated 之前到达订阅者，需要按订阅串行投递，这将每个订阅者的吞吐量上限卡在同时只有一条在途。而大多数订阅者实际上并不需要这一保证。

Option A · Per-subscription serial delivery方案 A · 按订阅串行投递

Each subscription's delivery worker processes one task at a time in Kafka-offset order. The next delivery is not dispatched until the current one ACKs or fails.

每个订阅的投递 Worker 按 Kafka offset 顺序每次处理一个任务。下一条投递在当前条确认或失败之前不会发出。

+ Strict event ordering at the subscriber — order.created is guaranteed to land before order.updated. Safe for order-sensitive operations like inventory ledgers or state machines.

+ 订阅者端严格事件有序——保证 order.created 在 order.updated 之前到达。对顺序敏感的操作（如库存账本或状态机）是安全的。

− Throughput ceiling = 1 / (delivery latency per event). A subscriber averaging 200 ms response time tops out at 5 events/sec regardless of how many workers you throw at it. One slow delivery head-of-line-blocks the entire event stream for that subscription.

− 吞吐上限 = 1 / 每事件投递延迟。平均 200 毫秒响应的订阅者吞吐上限为 5 事件/秒，无论投入多少 Worker。一条慢投递会队头阻塞该订阅的整个事件流。

Option B · Unordered parallel delivery方案 B · 无序并行投递

Multiple workers process the same subscription's queue concurrently; events may arrive at the subscriber out of emission order.

多个 Worker 并发处理同一订阅的队列；事件可能以非发出顺序到达订阅者。

+ Maximum throughput — scales linearly with worker count. No head-of-line blocking within the subscription. Jitter from network variability doesn't accumulate as backlog.

+ 最大吞吐量——随 Worker 数量线性扩展。订阅内无队头阻塞。网络抖动不会累积为积压。

− Events may arrive out of order. Subscribers must handle an order.updated arriving before order.created — usually solved by including a full snapshot in every payload (so ordering doesn't matter) rather than delta events. Apps that require ordering (rare) cannot use this mode safely.

− 事件可能乱序到达。订阅者必须处理 order.updated 先于 order.created 到达的情况——通常通过在每次 payload 中包含完整快照（而非增量事件）来解决，使顺序无关紧要。需要有序的应用（少数）无法安全使用此模式。

When to use which何时用哪个

Default to unordered parallel — most webhook payloads carry full resource snapshots, making ordering irrelevant. Use Kafka partition-by-shop_id for coarse per-shop ordering at the bus level (nearly free). Enable per-subscription serial delivery only when the app contract explicitly requires strict event ordering and the throughput cost is acceptable.

默认使用无序并行——大多数 Webhook payload 携带完整资源快照，使顺序无关紧要。在总线层使用 Kafka 按 shop_id 分区实现粗粒度按店有序（几乎免费）。仅在应用契约明确要求严格事件有序且可接受吞吐代价时，才启用按订阅串行投递。

⑤ Push vs. pull — webhooks vs. polling API / managed bus⑤ 推送 vs. 拉取——Webhook vs. 轮询 API / 托管消息总线

The tension: push webhooks give low-latency, zero-polling delivery but require the subscriber to be publicly reachable. Pull lets the subscriber control consumption rate and works behind firewalls, but introduces polling overhead and higher latency.

矛盾点：推送 Webhook 实现低延迟、零轮询投递，但要求订阅者可被公开访问。拉取让订阅者控制消费速率，也可在防火墙后运行，但引入了轮询开销和更高延迟。

Option A · Push webhooks方案 A · 推送 Webhook

Shopify POSTs to the subscriber's registered URL as soon as the event is enqueued for delivery.

一旦事件入队投递，Shopify 立即 POST 到订阅者的已注册 URL。

+ Sub-second delivery latency. No wasted polling. No subscriber-side polling infrastructure. The ecosystem standard — all major Shopify app partners expect it.

+ 亚秒级投递延迟。无浪费性轮询。订阅者侧无需轮询基础设施。生态标准——所有主要 Shopify 应用合作伙伴都期待此方式。

− Subscriber must expose a public HTTPS endpoint (impossible behind firewalls / NAT without a tunnel). Shopify carries the retry/backoff complexity and must handle SSRF risk. Delivery rate is driven by Shopify, not the subscriber — a slow subscriber builds a queue on our side.

− 订阅者必须暴露公开 HTTPS 端点（在防火墙/NAT 后不借助隧道无法实现）。Shopify 承担重试/退避复杂度，且必须处理 SSRF 风险。投递速率由 Shopify 驱动，而非订阅者——慢速订阅者在我们这边积累队列。

Option B · Pull API / managed bus方案 B · 拉取 API / 托管消息总线

Events are retained in Shopify's event log; subscriber polls a GET /events API or subscribes to a managed bus (Amazon EventBridge, Google Pub/Sub) and pulls at its own rate.

事件保留在 Shopify 事件日志中；订阅者轮询 GET /events API，或订阅托管消息总线（Amazon EventBridge、Google Pub/Sub）并按自身速率拉取。

+ Subscriber controls consumption rate — no thundering-herd on resume. Works behind firewalls and VPNs. No public endpoint required — better security posture for enterprise apps.

+ 订阅者控制消费速率——恢复时无惊群效应。可在防火墙和 VPN 后运行。不需要公开端点——对企业应用安全姿态更好。

− Higher delivery latency (bound by poll interval, typically 30 s–5 min). Polling overhead wastes resources when events are infrequent. Shopify must retain events long enough for the subscriber to pull (storage cost). Operational complexity on the subscriber side increases.

− 投递延迟更高（受轮询间隔限制，通常 30 秒到 5 分钟）。事件稀少时轮询开销浪费资源。Shopify 必须保留足够长时间的事件供订阅者拉取（存储成本）。订阅者侧运维复杂度增加。

When to use which何时用哪个

Push is the default for the vast majority of Shopify app developers. Offer pull as an opt-in for enterprise merchants and partners who operate behind VPNs or need guaranteed consumption-rate control (e.g. integration platforms that batch-process events). A hybrid — push for real-time, pull for bulk backfill / missed-event replay — is the right long-term architecture.

推送是绝大多数 Shopify 应用开发者的默认选项。为在 VPN 后运营或需要保证消费速率控制的企业商家和合作伙伴提供可选拉取模式（例如批量处理事件的集成平台）。混合模式——实时用推送，批量回填/漏发事件重放用拉取——是正确的长期架构。

⑥ Retry aggressiveness — exponential back-off + jitter vs. aggressive retries⑥ 重试激进程度——指数退避+抖动 vs. 激进重试

The tension: fast retries minimize delivery delay after a transient failure, but when an endpoint comes back online after an outage, all its backed-up retries fire simultaneously — a thundering herd that can immediately re-knock the recovering subscriber offline.

矛盾点：快速重试可最小化瞬时失败后的投递延迟，但端点在中断后恢复上线时，所有积压的重试同时触发——这波惊群效应可能立即将正在恢复的订阅者再次打垮。

Option A · Aggressive retries方案 A · 激进重试

Short back-off delays (e.g. retry every 60 s for the first few attempts); large number of retries before DLQ; no rate limit on resume.

短退避延迟（如前几次重试每 60 秒一次）；进入 DLQ 前重试次数多；恢复时无速率限制。

+ Fast recovery from transient failures — a 2-minute outage results in at most ~2 min of delivery delay rather than hours.

+ 瞬时故障恢复快——2 分钟中断最多导致约 2 分钟投递延迟，而非数小时。

− Thundering herd on resume — a subscriber recovering from a 1-hour outage gets hit simultaneously by all queued retries. This can cascade: the overload causes more failures, which trigger more retries. Also amplifies load on Shopify's own retry infrastructure and Kafka consumer lag increases as queued tasks pile up.

− 恢复时惊群效应——从 1 小时中断恢复的订阅者同时收到所有排队重试。这可能产生级联：过载导致更多失败，触发更多重试。也会放大 Shopify 自身重试基础设施的负载，排队任务堆积导致 Kafka 消费者 lag 增大。

Option B · Conservative back-off + rate-limited resume方案 B · 保守退避 + 限速恢复

Exponential back-off with jitter (e.g. min(cap, base × 2^attempt) + rand(0, 0.2 × delay)); per-endpoint rate limiter on queue drain when circuit closes.

指数退避加抖动（如 min(cap, base × 2^attempt) + rand(0, 0.2 × delay)）；熔断关闭时对队列消费施加 per-endpoint 速率限制。

+ Jitter spreads retries across time — no synchronized storm. Rate-limited resume gives a recovering subscriber time to warm up. Exponential growth means a truly dead endpoint stops consuming retry capacity quickly.

+ 抖动将重试分散到时间上——无同步风暴。限速恢复给正在恢复的订阅者预热时间。指数增长意味着真正宕机的端点会快速停止消耗重试容量。

− Slower recovery for transient failures — a 2-minute outage may result in deliveries that are delayed up to 15–30 min (the 3rd or 4th retry slot). For time-sensitive operations this matters; the merchant may have already taken action based on stale data before the delivery arrives.

− 瞬时故障恢复更慢——2 分钟中断可能导致投递延迟长达 15–30 分钟（第 3 或第 4 次重试槽）。对于时间敏感的操作，这一点很重要；在投递到达之前，商家可能已基于过期数据采取了行动。

When to use which何时用哪个

Exponential back-off + jitter + per-endpoint rate-limited resume is always the right answer for a multi-tenant webhook platform. The key tuning parameters are: base delay (60 s is industry-standard), jitter cap (20% of computed delay), and the per-endpoint drain rate after circuit close (e.g. 10 req/s initially, ramping up). Aggressive retries are only reasonable for low-volume, trusted internal systems where thundering-herd risk is negligible.

指数退避 + 抖动 + per-endpoint 限速恢复始终是多租户 Webhook 平台的正确答案。关键调参参数为：基础延迟（60 秒是行业标准）、抖动上限（计算延迟的 20%）、熔断关闭后 per-endpoint 消费速率（例如初始 10 req/s，逐步提升）。激进重试仅在低流量、受信任的内部系统中合理，那里惊群效应风险可以忽略不计。

A subscriber endpoint is down for several hours — what happens to its deliveries?订阅者端点宕机数小时——其投递会怎样？

Delivery workers hit the circuit breaker after N consecutive failures; the circuit opens and the endpoint is skipped for a cool-down period. Deliveries are queued in the per-endpoint queue during this window (not dropped). The circuit probes with a single request every cool-down interval; when a 2xx is received, the circuit closes and the worker drains the queue at a controlled rate (rate-limited resume) to avoid a thundering-herd on the recovering server.投递 Worker 在连续 N 次失败后触发熔断器；熔断打开，在冷却期内跳过该端点。此窗口期间投递在 per-endpoint 队列中排队（不丢弃）。熔断器每个冷却间隔用单次请求探测；收到 2xx 后熔断关闭，Worker 以受控速率（限速恢复）消费队列，避免对正在恢复的服务器造成惊群效应。

If the endpoint is still unreachable after 48 hours and 19 retry attempts, deliveries enter the DLQ. The merchant is notified via dashboard alert and email. How do you handle poison or oversized payloads?如何处理毒丸（poison）或超大 payload？

Enforce a payload size cap (e.g. 5 MB) at the Fan-out Service before enqueuing. Payloads that exceed the cap are truncated or the delivery is immediately DLQ'd with a PAYLOAD_TOO_LARGE reason — the merchant is alerted. For "poison" payloads (syntactically valid but semantically rejected by all subscribers with 4xx), distinguish: a 400/422 from the subscriber means the payload was received and rejected intentionally, so no retry should occur. Only 5xx and connection errors trigger retries. This prevents retry loops on payloads the subscriber will never accept.在 Fan-out Service 入队前强制限制 payload 大小（例如 5 MB）。超出上限的 payload 被截断或以 PAYLOAD_TOO_LARGE 原因直接进入 DLQ——并通知商家。对于"毒丸" payload（语法合法但被所有订阅者以 4xx 语义拒绝），需加以区分：订阅者返回 400/422 表示已收到但有意拒绝，不应重试。只有 5xx 和连接错误才触发重试。这可防止对订阅者永远不会接受的 payload 陷入重试死循环。

How do you guarantee order.created is delivered before order.updated for the same order?如何保证同一订单的 order.created 在 order.updated 之前投递？

Within the Kafka event bus, both events for the same shop_id land on the same partition (keyed by shop_id), so they are consumed by the Fan-out Service in order. The Fan-out Service enqueues delivery tasks with a monotonically increasing seq derived from the Kafka offset. The delivery worker for a given subscription processes tasks in seq order (one in-flight at a time) to maintain the ordering guarantee end-to-end.在 Kafka 事件总线中，同一 shop_id 的两个事件落在同一分区（以 shop_id 为键），因此 Fan-out Service 按顺序消费它们。Fan-out Service 用从 Kafka offset 派生的单调递增 seq 为投递任务编号。给定订阅的投递 Worker 按 seq 顺序处理任务（同时只有一条在途），从而端到端维护顺序保证。

The tradeoff: ordering requires serial processing per subscription, which reduces throughput. If the subscriber does not require strict ordering (most do not), the delivery worker can process in parallel and the constraint is lifted.权衡：有序性要求按订阅串行处理，这会降低吞吐量。如果订阅者不要求严格有序（大多数不要求），投递 Worker 可并行处理，去掉此约束。

How do you scale fan-out for a popular app subscribed by thousands of shops?如何为被数千个店铺订阅的热门应用扩展扇出？

A popular app (e.g. a major fulfillment provider) may have subscriptions in 50,000 shops for the orders/create topic. During BFCM, every one of those shops' order events must be fanned out to that app's endpoint. The fan-out is bounded by the number of active subscriptions per (shop, topic) pair, not globally. For a popular app, the deliveries go to a single endpoint URL — so they share one circuit breaker but can be delivered in parallel (no ordering requirement across different shops).一个热门应用（如主要履单服务商）可能在 5 万个店铺订阅了 orders/create 主题。在黑五期间，这些店铺的每一条订单事件都必须扇出到该应用的端点。扇出量由每个 (shop, topic) 对的活跃订阅数决定，而非全局。对于热门应用，所有投递指向同一个端点 URL——它们共享一个熔断器，但可以并行投递（不同店铺之间无顺序要求）。

Scale by: (a) partitioning the per-endpoint queue for the popular app into multiple sub-queues (by shop_id range) with parallel workers, (b) batching multiple deliveries into one HTTP call if the app supports it (reduces connection overhead 10–100×), and (c) negotiating a pull model for very high-volume apps so they control consumption rate.扩展方式：(a) 将热门应用的 per-endpoint 队列按 shop_id 范围分拆为多个子队列并行消费；(b) 若应用支持，将多条投递合并为一次 HTTP 调用（减少连接开销 10–100 倍）；(c) 对超高流量应用协商拉取模式，让其自行控制消费速率。

How do you monitor delivery SLA and alert merchants?如何监控投递 SLA 并告警商家？

Key metrics to track per subscription: delivery latency P50/P95/P99 (time from event creation to first 2xx); success rate (delivered / attempted); DLQ entry rate; per-endpoint queue depth; circuit breaker state.按订阅跟踪的关键指标：投递延迟 P50/P95/P99（从事件创建到首次 2xx 的时间）；成功率（已投递 / 已尝试）；DLQ 进入速率；per-endpoint 队列深度；熔断器状态。

SLA alerts: if a subscription's P95 delivery latency exceeds a threshold (e.g. 5 minutes) for more than N minutes, alert the merchant via dashboard notification and email. If a subscription enters DLQ, immediately notify. Shopify's status page should aggregate delivery health across the platform (not per-tenant) to surface systemic issues.SLA 告警：如果某订阅的 P95 投递延迟超过阈值（例如 5 分钟）持续超过 N 分钟，通过 Dashboard 通知和邮件告警商家。若订阅进入 DLQ，立即通知。Shopify 状态页应聚合全平台（而非按租户）的投递健康状况，以便暴露系统性问题。

How do you prevent one tenant's event storm from starving others (fairness)?如何防止单个租户的事件风暴饿死其他租户（公平性）？

At the Fan-out Service, apply a per-shop enqueue rate limit: if a single shop produces more than its fair share of fan-out tasks (e.g. based on their subscription count × event rate × a cap), excess tasks are spooled to a lower-priority queue and drained after the burst subsides. This is weighted fair queuing — each shop gets a fair share of the delivery infrastructure, with larger merchants getting proportionally more capacity based on their plan tier.在 Fan-out Service 处应用按店入队速率限制：若单个店铺产生的扇出任务超过其公平份额（例如基于其订阅数 × 事件速率 × 上限计算），超出的任务被存入低优先级队列，待突发平息后再消费。这是加权公平队列——每个店铺获得公平的投递基础设施份额，大商家根据其套餐等级获得按比例更多的容量。

At the worker layer, use a work-stealing scheduler that fills idle worker capacity from any shop's queue, but caps the fraction of workers any single shop can monopolize. This prevents a single shop running a 100,000-item flash sale from consuming all delivery workers and delaying a small merchant's single checkout confirmation.在 Worker 层，使用工作窃取调度器，从任意店铺队列填充空闲 Worker 容量，但限制单个店铺可独占的 Worker 比例上限。这可防止一个运行 10 万件商品抢购的店铺消耗所有投递 Worker，从而延迟小商家的单笔结账确认。

A subscriber returns HTTP 200 but is silently failing internally — how do you detect and handle it?订阅者返回 HTTP 200 但内部静默失败——如何检测和处理？

Shopify can only observe the HTTP response code — a 200 is treated as a successful delivery by definition. The system cannot introspect what the subscriber does with the payload after acknowledging it. The correct contract is: Shopify guarantees delivery to the endpoint; the subscriber is responsible for deduplication and internal processing. Expose full delivery logs (attempt timestamps, status codes, payload hash) via the dashboard and API so merchants and app developers can audit whether their system processed each delivery. Offer a verification/echo endpoint that re-sends a test payload on demand, letting developers confirm their handler is actually executing. For critical integrations, recommend subscribers implement an independent reconciliation job that periodically cross-checks Shopify's event log against their own state.Shopify 只能观察 HTTP 响应码——200 按定义即视为投递成功，系统无法感知订阅者在确认后对 payload 做了什么。正确的契约是：Shopify 保证将事件投递到端点，由订阅者负责去重和内部处理。通过 Dashboard 和 API 暴露完整的投递日志（尝试时间戳、状态码、payload 哈希），让商家和开发者审计每次投递是否被处理。提供验证/回显端点，按需重新发送测试 payload，方便开发者确认处理程序确实在执行。对于关键集成，建议订阅者实现独立的对账作业，定期将 Shopify 事件日志与自身状态进行交叉核验。

How do you let a merchant replay missed webhooks after their downtime?如何让商家在故障恢复后重放错过的 Webhook？

Maintain a durable event log — the event table is append-only and never pruned within the retention window (e.g. 30 days). Expose a replay API that accepts a topic filter and a time range, then re-enqueues delivery tasks for all matching events against active subscriptions. The replay sets new delivery.id values so subscribers receive fresh X-Shopify-Webhook-Id headers; idempotent subscribers simply check whether they have already processed the underlying event.idempotency_key and skip re-processing if so. Rate-limit the replay enqueue rate to avoid overwhelming a subscriber that just came back online.维护一个持久化事件日志——event 表仅追加写入，在保留窗口期内（例如 30 天）不删除。暴露一个重放 API，接受主题过滤条件和时间范围，然后将匹配事件重新入队投递到当前活跃的订阅。重放时生成新的 delivery.id，订阅者收到新的 X-Shopify-Webhook-Id 请求头；幂等订阅者只需检查是否已处理底层 event.idempotency_key，若已处理则跳过。对重放入队速率进行限流，避免刚恢复上线的订阅者被瞬间涌入的请求压垮。

An app needs strict per-resource ordering — how do you support it?某应用需要严格的按资源排序——如何支持？

Partition the Kafka topic (or per-endpoint queue) by resource ID (e.g. order_id or product_id) rather than just shop_id. Assign a single ordered consumer per partition key so events for the same resource are processed serially. Stamp each delivery task with a monotonic sequence number derived from the Kafka partition offset, and have the delivery worker enforce in-order delivery by blocking on the previous sequence before dispatching the next. The tradeoff is real: serial per-resource processing reduces parallelism for that subscription's workers, increases latency under load, and introduces head-of-line blocking within that resource's stream if the subscriber is slow. Only enable this mode when the app contract explicitly requires it (e.g. an inventory ledger that cannot tolerate out-of-order adjustments).将 Kafka 主题（或 per-endpoint 队列）按资源 ID（例如 order_id 或 product_id）而非仅 shop_id 进行分区。为每个分区键分配单一有序消费者，使同一资源的事件串行处理。为每个投递任务打上来自 Kafka 分区偏移量的单调递增序列号，投递 Worker 在发送下一条前须确认上一条的顺序。权衡是真实存在的：按资源串行处理会降低该订阅 Worker 的并发度、在高负载下增加延迟，并在订阅者响应慢时在该资源流内引入队头阻塞问题。仅在应用契约明确要求时（如不能容忍乱序调整的库存账本）才启用此模式。

How do you prevent SSRF and protect against malicious subscriber URLs?如何防止 SSRF 并防范恶意订阅者 URL？

At registration time, validate the subscriber URL through multiple layers: (1) scheme allowlist — only https:// is permitted; (2) DNS resolution + IP block list — resolve the hostname and reject if it maps to RFC-1918 private addresses, loopback (127.x), link-local (169.254.x — AWS metadata endpoint), or any other internal IP range; (3) DNS rebinding protection — re-resolve and re-check the IP at delivery time, not just at registration, because DNS TTLs allow an attacker to switch the DNS record to an internal IP after passing the initial check; (4) route all outbound delivery traffic through a dedicated egress proxy with a strict allowlist of external IP ranges, so even if a validation bypass occurs, the proxy acts as a second defense layer. Log all blocked attempts for security audit.在注册时通过多层校验对订阅者 URL 进行验证：(1) 协议白名单——仅允许 https://；(2) DNS 解析 + IP 封锁列表——解析主机名，如指向 RFC-1918 私有地址、回环地址（127.x）、链路本地地址（169.254.x，即 AWS 元数据端点）或其他内部 IP 段则拒绝；(3) DNS 重绑定防护——在每次投递时而非仅在注册时重新解析并检查 IP，因为 DNS TTL 允许攻击者在通过初始检查后将 DNS 记录切换为内部 IP；(4) 将所有出站投递流量通过专用出口代理路由，该代理维护严格的外部 IP 段白名单，即使验证被绕过，代理也能作为第二道防线。记录所有被拦截的尝试以供安全审计。

How do you version webhook payloads without breaking existing subscribers?如何对 Webhook payload 进行版本管理而不破坏现有订阅者？

Pin each subscription to the API version active at registration time (e.g. 2024-01). When the subscriber registers, record the version; the Fan-out Service serializes the payload using that version's schema, not the current platform schema. Apply only additive, backward-compatible changes within a version (new optional fields are safe; removing or renaming fields is a breaking change that requires a new version). Announce a deprecation window (typically 12–24 months) before retiring an old version, giving app developers time to migrate. Provide a migration guide and a test mode that lets developers preview the new payload format before cutting over. Never silently change payload structure for an active subscription.将每个订阅绑定到注册时有效的 API 版本（例如 2024-01）。订阅者注册时记录版本号；Fan-out 服务使用该版本的 Schema 序列化 payload，而非当前平台的最新 Schema。在版本内只允许向后兼容的追加式变更（新增可选字段是安全的；删除或重命名字段属于破坏性变更，需要引入新版本）。在弃用旧版本前公告废弃窗口期（通常 12–24 个月），给开发者留出迁移时间。提供迁移指南和测试模式，让开发者在切换前预览新 payload 格式。绝不在不通知的情况下更改活跃订阅的 payload 结构。

A subscriber is slow — how do you rate-limit deliveries to it without backing up everyone else?某订阅者响应慢——如何对其限速同时不阻塞其他订阅者？

The per-endpoint queue architecture already provides the core isolation: a slow subscriber only backs up its own queue, not shared infrastructure. Within that queue, add three additional controls: (1) a per-endpoint concurrency cap — limit the number of in-flight deliveries to that endpoint at any moment (e.g. 5 concurrent requests); if it is slow, workers naturally stop pulling from its queue once the cap is hit, preventing connection-thread exhaustion on Shopify's side; (2) a per-endpoint delivery rate limit — a token-bucket limiter that controls requests/sec to that endpoint, configurable per subscriber tier; (3) a circuit breaker that opens when error rate or latency exceeds thresholds, temporarily halting deliveries and queuing them for later. Together these ensure a slow subscriber is isolated and degraded gracefully without consuming delivery worker threads that could serve healthy endpoints.per-endpoint 队列架构已经提供了核心隔离：慢速订阅者只会使自己的队列积压，而不会影响共享基础设施。在此基础上，为该队列增加三项额外控制：(1) per-endpoint 并发上限——限制同一时刻对该端点的并发飞行投递数（例如 5 个并发请求）；若响应慢，Worker 在达到上限后自然停止从其队列取任务，防止 Shopify 端的连接线程耗尽；(2) per-endpoint 投递速率限制——令牌桶限流器控制对该端点的 QPS，可按订阅者等级配置；(3) 断路器——当错误率或延迟超过阈值时断开，临时停止投递并将任务排队等待后续处理。三者共同作用，确保慢速订阅者被优雅地隔离降级，而不占用原本可以服务健康端点的投递 Worker 线程。

Staff-level summary — say these six thingsStaff 级别总结——这六点必须说
  1. At-least-once + subscriber idempotency is the honest contract. Exactly-once over HTTP to third parties is impractical; document the contract and provide a delivery ID for deduplication.At-least-once + 订阅者幂等性才是诚实的契约。对第三方进行 HTTP 精确一次不现实；明确契约文档，并提供投递 ID 用于去重。
  2. Per-endpoint queues kill head-of-line blocking. A single shared queue is the fastest way to make one dead subscriber stall deliveries for everyone.Per-endpoint 队列消除队头阻塞。单一共享队列是让一个宕机订阅者阻塞所有人投递的最快方式。
  3. Exponential back-off + jitter → DLQ with replay. Never retry on 4xx (subscriber rejected intentionally). Rate-limit on resume to avoid thundering-herd.指数退避 + 抖动 → DLQ 可重放。4xx 绝不重试（订阅者有意拒绝）。恢复时限速避免惊群效应。
  4. HMAC-SHA256 + timestamp + HTTPS + replay protection. Each subscription has its own secret; a compromised secret is scoped to that subscription, not the platform.HMAC-SHA256 + 时间戳 + HTTPS + 防重放。每个订阅有独立密钥；密钥泄露仅影响该订阅，不波及整个平台。
  5. Partition for ordering only where required. Kafka partition-by-shop gives coarse ordering for free; strict per-subscription ordering costs throughput and is rarely needed.仅在必要时用分区保序。Kafka 按店分区免费提供粗粒度有序；严格按订阅有序消耗吞吐量且极少需要。
  6. Buffer events in Kafka + autoscale workers + per-shop fairness for storms. The event bus absorbs spikes; per-shop enqueue caps prevent one storming merchant from starving others.Kafka 缓冲事件 + Worker 自动扩容 + 按店公平性应对风暴。事件总线吸收尖峰；按店入队上限防止一个风暴商家饿死其他人。
