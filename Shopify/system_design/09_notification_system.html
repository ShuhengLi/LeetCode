where staff signal livesStaff 级信号所在

① Async fan-out and spike absorption① 异步扇出与峰值吸收

Kafka decouples producers from provider rate limits. At BFCM, tens of millions of order.confirmed events arrive in minutes; the queue buffers them and workers drain toward providers at the negotiated rate. Workers autoscale based on consumer-group lag. Key design choice: separate topics for transactional vs marketing so a campaign blast — even a misconfigured one sending 100 M messages — cannot consume all consumer group capacity and delay order confirmations.Kafka 将生产者与供应商速率限制解耦。BFCM 期间，数千万 order.confirmed 事件在数分钟内涌入；队列缓冲这些事件，Worker 以协商好的速率向供应商输出。Worker 根据消费者组积压量自动扩缩。关键设计决策：事务性通知与营销通知使用独立 topic，即使一次发送 1 亿条的错误配置的营销推送，也无法耗尽所有消费者组容量而拖延订单确认。

Transactional vs marketing isolation事务性通知与营销通知隔离 Transactional notifications (order confirmed, shipped) are business-critical and latency-sensitive: a buyer expects an email within seconds of purchase. Marketing blasts are best-effort with flexible timing. Mixing them on one queue means a bulk send can fill the queue and delay order confirmations by minutes. Use separate Kafka topics with separate consumer groups and separate provider rate-limit pools. Transactional consumers get higher replica count and priority scheduling.事务性通知（订单确认、已发货）业务关键且对延迟敏感：买家期望在购买后数秒内收到邮件。营销群发则是尽力而为，时间灵活。混合在同一队列意味着群发可能填满队列，使订单确认延迟数分钟。应使用独立的 Kafka topic、独立的消费者组和独立的供应商速率限制池；事务性消费者分配更高副本数和调度优先级。

② Idempotency and deduplication② 幂等性与去重

Producers are retried (e.g., the order service retries the HTTP call if it times out). Without deduplication, a buyer gets two order-confirmation emails. The dedupeKey (caller-supplied, e.g., order_9999:confirmed:email) is the anchor. The Notification Service does an atomic Redis SET NX EX 86400 — if the key already exists, the notification is silently dropped and an idempotent 200 is returned.生产者会重试（例如订单服务在 HTTP 调用超时时重试）。若没有去重，买家会收到两封订单确认邮件。dedupeKey（由调用方提供，如 order_9999:confirmed:email）是锚点。通知服务执行原子 Redis SET NX EX 86400——若键已存在，则静默丢弃该通知并返回幂等的 200。

-- dedupe check in Notification Service (pseudocode)
def accept_notification(req):
    key = f"dedupe:{req.dedupe_key}"
    if not redis.set(key, 1, nx=True, ex=86400):
        # already seen — idempotent no-op
        return existing_notification_id(req.dedupe_key)
    notification = persist(req)
    enqueue(notification)
    return notification.id
Dedupe window edge case去重窗口边界情况 A 24-hour TTL covers most retry storms. However: if the same logical event should produce a new notification after 24 h (e.g., a repeated low-stock alert), the caller must use a time-scoped dedupeKey. Document this contract clearly. Also, if the Notification Service crashes after writing to Redis but before persisting to DB, the key exists but no notification record does — a background reconciler can detect and replay these orphan keys.24 小时 TTL 覆盖了大多数重试风暴。但是：若同一逻辑事件需要在 24 小时后再次产生通知（如重复的低库存提醒），调用方必须使用带时间范围的 dedupeKey。务必清晰记录此合约。另外，若通知服务在写入 Redis 后、持久化到 DB 前崩溃，键存在但无通知记录——后台协调任务可检测并重放这些孤儿键。

③ Multi-provider failover and circuit breakers③ 多供应商故障转移与熔断器

Each channel has a primary and one or more secondary providers, each with a health score tracked in Redis. The provider adapter maintains a circuit breaker per provider: after N consecutive failures or an error-rate threshold, the circuit opens and traffic routes to the secondary. A half-open probe after a cool-down period allows recovery.每个渠道配置一个主供应商和一个或多个备用供应商，各自的健康分数在 Redis 中追踪。供应商适配器为每个供应商维护一个熔断器：在 N 次连续失败或错误率超过阈值后，熔断器打开，流量路由至备用供应商。冷却期后通过半开探测允许恢复。

④ Templating, localization, and versioning④ 模板、本地化与版本控制

Templates are stored per (channel, locale, version). The Template Service renders the body by injecting the render_data JSON blob. Versioning is critical: a broken template deployment must not invalidate all in-flight notifications. Workers always render at send time using the version pinned at enqueue, so a template update does not retroactively corrupt queued messages.模板按 (channel, locale, version) 存储。模板服务通过注入 render_data JSON 块来渲染正文。版本控制至关重要：一次错误的模板部署不得使所有正在处理中的通知失效。Worker 始终使用入队时固定的版本在发送时渲染，因此模板更新不会追溯性地损坏已入队的消息。

  • Fallback chain: pt-BR → pt → en — never send a raw template key as buyer-visible text.语言兜底链：pt-BR → pt → en——绝不将原始模板键作为买家可见的文本发送。
  • Preview/test endpoint lets merchants proof a notification before activating a template version.预览/测试端点让商户在激活模板版本前进行审核。
  • For merchant-customizable templates (e.g., "you made a sale!" branding), keep a merchant_id override layer on top of the global defaults.对于商户可定制模板（如"您成交了！"品牌定制），在全局默认模板之上保留一个 merchant_id 覆盖层。

⑤ Preferences, compliance, and suppression⑤ 偏好设置、合规与抑制名单

The Preference Service is checked before enqueue. Key rules:偏好服务在入队前进行检查。核心规则：

  • Transactional vs marketing legal distinction: under CAN-SPAM and most GDPR interpretations, transactional notifications (order confirmed, shipped) are exempt from opt-out requirements. Marketing blasts require explicit consent. The system must tag every notification with its type and enforce this rule in the preference check.事务性通知与营销通知的法律区分：根据 CAN-SPAM 和大多数 GDPR 解释，事务性通知（订单确认、已发货）免于退订要求；营销群发则需要明确同意。系统必须为每条通知标注类型，并在偏好检查中执行此规则。
  • Quiet hours: SMS and push notifications have legal and UX quiet hours (e.g., 9 PM–8 AM in the recipient's timezone). Workers must check the recipient's timezone and either delay or drop depending on notification type.免打扰时段：SMS 和推送通知存在法律和用户体验层面的免打扰时段（如接收者时区晚 9 点至早 8 点）。Worker 必须检查接收者时区，并根据通知类型决定延迟发送或丢弃。
  • Suppression lists: bounced addresses and spam complainants are added to a suppression list (updated via provider webhooks). Every send checks this list before calling the provider to protect sender reputation.抑制名单：退信地址和垃圾邮件投诉者被加入抑制名单（通过供应商 webhook 更新）。每次发送在调用供应商前都会检查此名单，以保护发件人信誉。
  • GDPR deletion: a right-to-erasure request must purge notification history and preferences. Implement via a soft-delete + async scrub worker.GDPR 删除：被遗忘权请求必须清除通知历史和偏好数据。通过软删除 + 异步清理 Worker 实现。

⑥ Ordering semantics and delivery guarantees⑥ 消息顺序语义与投递保证

For a given order, "Order Confirmed" must not arrive after "Order Shipped". Guaranteeing strict ordering while maintaining high throughput requires intentional design: partition Kafka by recipient_id + order_id. All notifications for one order land on one partition, consumed sequentially by one worker instance. This trades throughput for ordering per recipient.对于同一订单，"订单确认"不得在"订单已发货"之后送达。在保持高吞吐的同时保证严格顺序需要精心设计：按 recipient_id + order_id 对 Kafka 进行分区。一个订单的所有通知都落在同一分区，由同一 Worker 实例按顺序消费。这以牺牲部分吞吐量换取了每个接收者维度的顺序保证。

At-least-once delivery (from the queue) plus the Redis dedupe gives effectively-once delivery to the provider. Delivery to the end device (e.g., an email reaching the inbox) depends on the provider and is tracked asynchronously via webhooks — not synchronously on the send call.来自队列的至少一次投递加上 Redis 去重，实现了对供应商的实际上的恰好一次投递。消息到达终端设备（如邮件进入收件箱）取决于供应商，通过 webhook 异步追踪——并非在发送调用时同步确认。

-- effectively-once delivery contract
-- 1. Queue guarantees: at-least-once (worker may re-consume on crash)
-- 2. Provider call may retry on network failure (idempotency key passed)
-- 3. Redis dedupe prevents the same dedupeKey from being sent twice
-- 4. Result: at most one provider API call per (dedupeKey, window)
-- 5. Delivery to device tracked async via provider webhook → status update

⑦ The provider failover state machine⑦ 供应商故障转移状态机

Each provider adapter maintains a per-provider circuit breaker whose state is stored in Redis (key: provider:{id}:circuit). The breaker has three states and transitions driven by both consecutive error counts and a sliding health score, so a provider that is slow-but-not-failing can also be routed away from proactively.

每个供应商适配器维护一个熔断器，其状态存储在 Redis 中（键：provider:{id}:circuit）。熔断器有三个状态，由连续错误计数和滑动健康分数共同驱动状态转换——因此响应慢但未报错的供应商也可以被主动路由绕开。

-- Circuit-breaker state machine (per provider, per channel)

CLOSED -- normal operation; all sends go to the primary provider
  health_score = 1.0  -- decays on errors, recovers on successes (EWMA)
  -- transitions to OPEN when:
  --   consecutive_errors >= THRESHOLD (e.g. 5)  OR
  --   health_score < FLOOR (e.g. 0.6, ~40% error rate over window)

OPEN -- tripped; primary is unreachable or unhealthy
  -- all sends routed immediately to secondary (SES→Mailgun, Twilio→SNS)
  -- no calls to primary; Redis key carries open_until timestamp
  -- transitions to HALF_OPEN when: now() >= open_until (cool-down elapsed)

HALF_OPEN -- probe state; testing whether primary has recovered
  -- exactly ONE probe request allowed through to primary
  --   probe success  → CLOSED (reset consecutive_errors, health_score = 1.0)
  --   probe failure  → OPEN again (cool-down doubles: exponential back-off)
  -- remaining sends route to secondary while probe is in-flight

Health-based routing adds a second dimension on top of binary open/close. Each outbound call records its outcome in a Redis sliding window (provider:{id}:errs via INCR + EX, or a time-bucketed counter). The health score is an exponentially-weighted moving average (EWMA) of the success rate; the circuit opens not only on hard consecutive failures but also when the health score drops below a configured floor — catching slow-burn degradation that retries alone would mask.

基于健康分数的路由在简单的开/关二元状态之上增加了第二个维度。每次出站调用将结果记录在 Redis 滑动窗口中（通过 INCR + EX 或时间桶计数器实现 provider:{id}:errs）。健康分数是成功率的指数加权移动平均（EWMA）；熔断器不仅在连续硬性失败时触发，也在健康分数降至配置阈值以下时触发——从而能捕获单靠重试会掩盖的缓慢降级现象。

Delivery status is reconciled asynchronously via provider webhooks. After a failover, some messages were sent via the secondary; their delivery receipts, bounces, and spam complaints arrive on the POST /provider/webhook endpoint referencing the secondary's provider message ID. The Status Writer matches these to the notification record using the provider_msg_id column and updates the status. Crucially, bounced or complained addresses update the suppression list regardless of which provider sent the message — the suppression list is provider-agnostic.

投递状态通过供应商 webhook 异步核对。故障转移后，部分消息经由备用供应商发送；其投递回执、退信和垃圾邮件投诉通过 POST /provider/webhook 端点到达，引用的是备用供应商的消息 ID。Status Writer 使用 provider_msg_id 列将这些回调与通知记录匹配，并更新状态。关键点：退信或投诉地址无论经由哪个供应商发送，都会更新抑制名单——抑制名单与供应商无关。

The queue buffers during failover — no notification is lost, only delayed队列在故障转移期间缓冲——通知不会丢失，只会延迟

When the circuit opens, the worker immediately reroutes to the secondary — but the Kafka message is not dropped. Any notification that was mid-flight at the moment of tripping is retried via the secondary on the next poll cycle. Messages that arrive while the circuit is OPEN are sent directly to the secondary. The entire delay is bounded by Kafka's retention window (configured to 7 days for this service) and the secondary provider's acceptance rate. A message is only at risk of expiry if both the primary and secondary are simultaneously unavailable for the full retention window — an extreme scenario that should trigger a P0 incident response, not silent data loss.

当熔断器打开时，Worker 立即将流量重路由到备用供应商——但 Kafka 消息不会被丢弃。熔断触发瞬间正在处理中的任何通知，在下一个轮询周期通过备用供应商重试。熔断器处于 OPEN 状态期间到达的消息直接发往备用供应商。所有延迟都受限于 Kafka 的保留窗口（该服务配置为 7 天）和备用供应商的接受速率。消息面临过期风险，仅当主备供应商在整个保留窗口内同时不可用——这是极端场景，应触发 P0 事故响应，而非静默数据丢失。

① Delivery guarantee — at-least-once + dedupe vs exactly-once (2PC)① 投递保证——至少一次 + 去重 vs 精确一次（2PC）

The tension: how strongly do you guarantee that a notification is sent exactly once? The stronger the guarantee, the heavier the machinery required.

矛盾点：你对"通知恰好发送一次"的保证强度有多高？保证越强，所需的机制越重。

Option A · At-least-once + Redis dedupe方案 A · 至少一次 + Redis 去重

The queue delivers at-least-once; the Notification Service does an atomic Redis SET NX EX on the dedupeKey before persisting. A duplicate event is silently dropped and a 200 is returned.

队列提供至少一次语义；通知服务在持久化前对 dedupeKey 做原子 Redis SET NX EX。重复事件被静默丢弃并返回 200。

+ Horizontally scalable — Redis NX is a single atomic op; no cross-service coordination; workers are completely stateless; dedupe window (e.g. 24 h) covers virtually all retry storms without any distributed transaction.

+ 水平可扩展——Redis NX 是单个原子操作；无需跨服务协调；Worker 完全无状态；去重窗口（如 24 小时）无需任何分布式事务即可覆盖几乎所有重试风暴。

− Not strictly durable: if the service crashes after setting the Redis key but before writing the DB record, the notification is silently lost (an orphan key). Needs a background reconciler to detect and replay these gaps.

− 不是严格持久：若服务在设置 Redis 键后、写入 DB 记录前崩溃，通知会静默丢失（孤儿键）。需要后台协调任务来检测并重放这些空缺。

Option B · Exactly-once via 2PC方案 B · 通过 2PC 实现精确一次

Wrap the DB write and queue publish in a two-phase commit (or outbox pattern): the notification row and the outbox event are written atomically; a relay polls and publishes; acks confirm end-to-end.

将 DB 写入和队列发布包装在两阶段提交中（或发件箱模式）：通知行和发件箱事件原子写入；中继轮询并发布；确认端到端完成。

+ Formally correct — no orphan keys; the DB and queue are always in sync; easier to reason about at audit time.

+ 形式上正确——无孤儿键；DB 和队列始终同步；审计时更易推理。

− Kills throughput — distributed transactions add latency and serialization; the outbox relay adds an extra hop per notification; throughput collapses under the 30k/s BFCM load; adds operational complexity (distributed lock, relay lag monitoring).

− 严重降低吞吐——分布式事务增加延迟和串行化；发件箱中继为每条通知增加一跳；在 BFCM 3 万/秒的负载下吞吐崩溃；增加运维复杂度（分布式锁、中继延迟监控）。

When to use which何时用哪个

At-least-once + dedupe is the right default for notification systems at scale. The Redis NX dedupe gives effectively-once semantics without 2PC overhead, and a background reconciler patches the rare orphan-key gap. Reserve exactly-once (outbox pattern) for financial ledger writes where a duplicate or missing event has monetary consequences — not for notifications where a brief gap is acceptable.

至少一次 + 去重是规模化通知系统的正确默认选择。Redis NX 去重在无需 2PC 开销的情况下提供实际上的恰好一次语义，后台协调任务修补极少出现的孤儿键缺口。将精确一次（发件箱模式）留给金融账本写入——那里重复或缺失事件有货币影响——而非通知系统（短暂空缺可接受）。

② Send path — synchronous vs async via queue② 发送路径——同步 vs 通过队列异步

The tension: should the caller block while the notification is dispatched to the provider, or should it return immediately and let a background worker do the send?

矛盾点：调用方是否应阻塞等待通知被分发至供应商，还是应立即返回并由后台 Worker 执行发送？

Option A · Synchronous send方案 A · 同步发送

The request handler calls the provider API inline; the caller's latency is coupled to the provider's response time and error behavior.

请求处理器直接内联调用供应商 API；调用方的延迟与供应商的响应时间和错误行为强耦合。

+ Simple to reason about — success means the provider accepted the message; easy to surface provider errors synchronously to the caller.

+ 推理简单——成功即代表供应商已接受消息；易于将供应商错误同步返回给调用方。

− Provider latency (SES p99 ≈ 150 ms, Twilio p99 ≈ 300 ms) is added to every POST /notifications call. A provider outage or rate-limit pause blocks callers and blocks the hot-path (order checkout). At BFCM, 30k/s of provider calls cannot be handled synchronously — the thread pool saturates in seconds.

− 供应商延迟（SES p99 ≈ 150 ms，Twilio p99 ≈ 300 ms）叠加到每次 POST /notifications 调用上。供应商故障或速率限制暂停会阻塞调用方和热路径（订单结账）。BFCM 期间 30k/s 的供应商调用无法同步处理——线程池数秒内就会饱和。

Option B · Async via Kafka queue方案 B · 通过 Kafka 队列异步

The Notification Service validates, dedupes, and enqueues the notification; per-channel workers pull from Kafka and call providers independently.

通知服务验证、去重并将通知入队；各渠道 Worker 从 Kafka 拉取并独立调用供应商。

+ Decouples caller from provider — the order service's p99 is not affected by SES latency. The queue absorbs the BFCM burst; workers drain at provider rate. Provider outages cause queue lag, not caller errors. Retry and circuit-breaker logic lives in workers, not scattered across callers.

+ 将调用方与供应商解耦——订单服务的 p99 不受 SES 延迟影响。队列吸收 BFCM 峰值；Worker 以供应商速率平稳输出。供应商故障导致队列积压，而非调用方错误。重试和熔断逻辑集中在 Worker 中，而非分散在各调用方。

− Caller gets QUEUED, not SENT — the notification may still fail after acknowledgment; caller must poll or webhook for delivery confirmation. More moving parts (Kafka, worker fleet, consumer-group lag monitoring).

− 调用方获得的是 QUEUED，而非 SENT——通知在被确认后仍可能失败；调用方必须轮询或通过 webhook 确认投递。更多活动部件（Kafka、Worker 集群、消费者组积压监控）。

When to use which何时用哪个

Async always, for any notification system with non-trivial volume. Provider latency and failure modes must not bleed into the order checkout path. The queue also lets you add retries, priority lanes, and dead-letter handling without changing a single producer. Synchronous send is only acceptable for very low-volume internal tooling where simplicity outweighs everything.

对任何有一定规模的通知系统，始终使用异步。供应商延迟和故障模式绝不能渗入订单结账路径。队列还允许在不改变任何生产者的情况下添加重试、优先级通道和死信处理。同步发送仅适用于量极小的内部工具，且只有在简单性压倒一切时才合理。

③ Provider strategy — single provider with retry vs multi-provider failover③ 供应商策略——单供应商加重试 vs 多供应商故障转移

The tension: how much availability do you need from your external sending provider, and what are you willing to pay in cost and complexity to get it?

矛盾点：你对外部发送供应商的可用性需求有多高，愿意为此在成本和复杂度上付出多少？

Option A · Single provider with retry方案 A · 单供应商加重试

One provider per channel (e.g., SES for email, Twilio for SMS); failed sends retry up to N times with exponential back-off.

每个渠道一个供应商（如邮件用 SES，SMS 用 Twilio）；失败发送以指数退避重试最多 N 次。

+ Operationally simple — one API contract, one credential, one dashboard; retries handle transient blips.

+ 运维简单——一个 API 合同、一套凭证、一个看板；重试可处理瞬时故障。

− A sustained provider outage (SES has had multi-hour incidents) means zero notifications delivered until it recovers. Retries pile up in the dead-letter queue; some age out. There is no way to self-heal without a second provider.

− 供应商持续故障（SES 曾有过数小时事故）意味着零通知送达，直到其恢复。重试积压在死信队列中，部分消息超时。没有第二供应商，系统无法自愈。

Option B · Multi-provider with circuit-breaker failover方案 B · 多供应商加熔断器故障转移

Primary + secondary per channel (SES→Mailgun for email, Twilio→SNS for SMS, FCM/APNs are already multi-provider for push). A circuit breaker trips on consecutive failures and routes to the secondary.

每个渠道主备各一（邮件 SES→Mailgun，SMS Twilio→SNS，推送 FCM/APNs 本身已是多供应商）。熔断器在连续失败后触发，将流量路由至备用供应商。

+ A provider outage is a degradation, not an outage — the secondary takes over within seconds (the circuit-breaker cool-down). Notifications continue during the failover; the queue buffers the gap. Protects sender reputation: if SES is soft-failing (timeouts, rate errors), the circuit opens before reputation damage accumulates.

+ 供应商故障是降级，而非全面中断——备用供应商在数秒内（熔断器冷却期内）接管。通知在故障转移期间持续发送；队列缓冲过渡期。保护发件人信誉：若 SES 软故障（超时、速率错误），熔断器在信誉损害积累前就已打开。

− Two provider contracts to manage (cost, credential rotation, API differences). Circuit-breaker state must be shared across workers (via Redis). Secondary may have different deliverability characteristics; warm-up if using a cold IP.

− 两套供应商合同需要管理（成本、凭证轮换、API 差异）。熔断器状态必须在 Worker 间共享（通过 Redis）。备用供应商可能有不同的投递特性；若使用冷 IP 需要预热。

When to use which何时用哪个

Multi-provider is the right default at any meaningful scale. Provider incidents are real and unpredictable — SES, Twilio, and FCM/APNs have all had production outages. The circuit-breaker + adapter pattern is the engineering investment; the second provider contract is the business investment. Use single provider only if volume is very low and manual failover (update an env var, redeploy) is acceptable within your SLA. At BFCM scale, "manual failover" means tens of millions of missed notifications.

在任何有意义的规模下，多供应商是正确的默认选择。供应商事故是真实且不可预测的——SES、Twilio 和 FCM/APNs 均有过生产故障。熔断器 + 适配器模式是工程投入；第二供应商合同是业务投入。只有在流量极低且手动故障转移（更新环境变量、重新部署）可接受时，才考虑单供应商。在 BFCM 规模下，"手动故障转移"意味着数千万条丢失的通知。

④ Queue topology — single queue vs priority lanes④ 队列拓扑——单一队列 vs 优先级通道

The tension: how do you prevent a low-priority marketing blast from starving the high-priority transactional notifications that buyers are actively waiting for?

矛盾点：如何防止低优先级营销群发"饿死"买家正在等待的高优先级事务性通知？

Option A · Single shared queue方案 A · 单一共享队列

All notifications — transactional and marketing — go onto one Kafka topic; workers consume in arrival order.

所有通知——事务性和营销——都进入同一个 Kafka topic；Worker 按到达顺序消费。

+ Simplest topology — one topic, one consumer group, one set of offset metrics to watch.

+ 拓扑最简单——一个 topic、一个消费者组、一组 offset 指标。

− A marketing campaign blasting 100 M messages floods the topic; transactional confirmations queue behind it and arrive minutes late. There is no mechanism to skip ahead even though the order confirmation is infinitely more urgent than the promotional code.

− 一次发送 1 亿条消息的营销活动会淹没该 topic；事务性确认排在其后，延迟数分钟才能到达。即使订单确认远比促销码紧急，也没有机制让其插队。

Option B · Separate topics per type and channel方案 B · 按类型和渠道分开 topic

Two or more Kafka topics: notifications.transactional (high priority, more consumers) and notifications.marketing (lower priority, throttled). Optional: per-channel topics for independent rate-limit tuning.

两个或更多 Kafka topic：notifications.transactional（高优先级，更多消费者）和 notifications.marketing（低优先级，限速）。可选：每渠道独立 topic 以独立调整速率限制。

+ Transactional consumers are never starved — they have dedicated consumer group capacity and their own provider rate-limit pool. Marketing throughput can be throttled at the consumer level without touching transactional. Each lane can be independently scaled and monitored.

+ 事务性消费者永不被饿死——它们拥有专属消费者组容量和独立供应商速率限制池。营销吞吐可在消费者层面限速，而不影响事务性通知。每条通道可独立扩缩和监控。

− More Kafka topics to manage; producers must classify notifications before enqueue; consumer group configuration becomes more complex. Small operational overhead compared to the latency protection gained.

− 需要管理更多 Kafka topic；生产者必须在入队前对通知分类；消费者组配置变得更复杂。与所获得的延迟保护相比，运维开销很小。

When to use which何时用哪个

Priority lanes from day one. The cost is minimal (a second Kafka topic and consumer group) but the protection is large. An order confirmation delayed by five minutes due to a marketing blast is a support ticket, a potential chargeback query, and an erosion of buyer trust. Always separate transactional from marketing at the queue layer; the per-channel split is optional and driven by rate-limit tuning needs.

从第一天起就使用优先级通道。成本极小（第二个 Kafka topic 和消费者组），但保护作用巨大。因营销群发而延迟五分钟的订单确认会产生工单、潜在的退款争议和买家信任侵蚀。始终在队列层将事务性通知与营销通知分开；渠道级别的分割是可选的，由速率限制调整需求驱动。

⑤ Template engine — build in-house vs buy⑤ 模板引擎——自研 vs 购买

The tension: building a full templating and localization stack gives you control and multi-channel parity; buying a managed solution (SendGrid dynamic templates, Braze) gets you there faster but creates provider coupling.

矛盾点：构建完整的模板与本地化栈能给你控制权和多渠道一致性；购买托管方案（SendGrid 动态模板、Braze）能更快落地，但会产生供应商耦合。

Option A · Build in-house方案 A · 自研

Own the Template Service: store templates per (channel, locale, version) in a DB; render by injecting render_data JSON; support merchant overrides; version-pin at enqueue.

自建模板服务：按 (channel, locale, version) 在 DB 中存储模板；通过注入 render_data JSON 渲染；支持商户覆盖；在入队时固定版本。

+ Full control of versioning, merchant customization, multi-channel rendering parity (same template logic for email/SMS/push), GDPR data residency, and locale fallback chain. No per-message billing for rendering.

When the Notification Service accepts a request, it resolves the current active template version and records that version ID alongside the notification record. Workers always render using the pinned version, so a subsequent template deployment does not retroactively corrupt queued messages. Old versions are retained (soft-deleted, not purged) for at least the queue retention window. This means a broken template push only affects notifications enqueued after the deployment — existing in-flight ones are safe. A rollback simply activates the previous version for new enqueues.对模板进行版本控制，并在入队时（而非渲染时）固定版本号。通知服务接受请求时，解析当前活跃模板版本并将该版本 ID 与通知记录一起存储。Worker 始终使用固定版本进行渲染，因此后续的模板部署不会影响已入队的消息。旧版本至少在队列保留窗口期内被保留（软删除，不立即清除）。这意味着一次错误的模板部署只影响部署之后入队的通知——正在处理中的通知是安全的。回滚只需将上一版本重新设为活跃状态，供新入队通知使用即可。

How do you prevent a notification storm (e.g., 10k low-stock alerts to one merchant)?如何防止通知风暴（例如向同一商户发送 1 万条低库存提醒）？

Apply multiple layers of protection. First, coalesce duplicate events at the Notification Service: if the same (merchant, topic, reference) tuple arrives multiple times within a window, deduplicate via the dedupeKey and emit only one notification. Second, rate-limit per recipient per channel: enforce a maximum notification count per hour (configurable per topic), queuing excess behind a leaky-bucket or token-bucket limiter. Third, apply per-merchant digest for low-priority alert types — aggregate all low-stock events in a rolling window into a single "You have N low-stock SKUs" digest message instead of N individual ones. Fourth, circuit-break on the publisher side: if the Inventory Service triggers more than M events/min for one merchant, the Notification Service routes them to a digest queue rather than the immediate lane. This prevents a misconfigured inventory sync or a runaway cron job from flooding a merchant's inbox.采用多层防护。第一，在通知服务层合并重复事件：若相同的（商户、主题、引用）元组在一个时间窗口内多次到达，通过 dedupeKey 去重，只发出一条通知。第二，对每位接收者每个渠道进行限速：按每小时最大通知数（可按主题配置）执行限制，将超出的通知排在漏桶或令牌桶限流器之后。第三，对低优先级告警类型应用商户维度的摘要：将一个滚动窗口内的所有低库存事件聚合为一条"您有 N 个 SKU 库存不足"的摘要消息，而不是 N 条单独的消息。第四，在发布方侧熔断：若库存服务在一分钟内为同一商户触发超过 M 个事件，通知服务将其路由至摘要队列而非即时通道。这可以防止配置错误的库存同步或失控的定时任务淹没商户的收件箱。

Staff-level summary — the six things to sayStaff 级总结——必须说清楚的六点
  1. Async queue absorbs spikes and decouples producers from provider rate limits — synchronous send cannot survive BFCM.异步队列吸收峰值并将生产者与供应商速率限制解耦——同步发送无法撑过 BFCM。
  2. dedupeKey gives effectively-once semantics: at-least-once queue + Redis NX dedupe = no duplicate emails on retry storms, without the cost of 2PC.dedupeKey 实现实际上的恰好一次语义：至少一次队列 + Redis NX 去重 = 重试风暴中不重复发送邮件，且无需 2PC 的代价。
  3. Multi-provider failover with circuit breakers: a single provider outage must never stop all notifications; name the adapter pattern and the circuit states.多供应商故障转移加熔断器：单一供应商故障绝不能停止所有通知；说清楚适配器模式和熔断器状态。
  4. Priority lanes keep transactional ahead of marketing: separate Kafka topics, separate consumer groups, separate rate-limit pools — never let a campaign blast delay an order confirmation.优先级通道保证事务性通知先于营销通知：独立的 Kafka topic、独立的消费者组、独立的速率限制池——绝不让营销群发拖延订单确认。
  5. Preferences and compliance are first-class concerns, not afterthoughts: transactional/marketing type distinction, quiet hours, and suppression lists must be modeled explicitly.偏好设置和合规是一等关注点，而非事后补救：事务性/营销通知类型区分、免打扰时段和抑制名单必须显式建模。
  6. Track delivery via provider webhooks: the send call tells you the provider accepted the message, not that it reached the device — close the loop with async webhook ingestion and status updates.通过供应商 webhook 追踪投递状态：发送调用只告诉你供应商接受了消息，而非消息已到达设备——通过异步 webhook 摄入和状态更新闭合这个环路。
