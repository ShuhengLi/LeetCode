System Design Interview Prep系统设计面试准备

Ten real, recurring Shopify system-design prompts — each worked end-to-end at staff level: requirements → estimation → API → data model → architecture diagram → deep dives → trade-offs → follow-ups. Shopify's round is unusual: it is e-commerce at planetary scale, not generic distributed systems. Every design is judged through one lens — does it protect the merchant's sale? 十道真实、反复出现的 Shopify 系统设计题，每道题均以 staff 级 完整展开：需求 → 估算 → API → 数据模型 → 架构图 → 深挖 → 权衡 → 追问。Shopify 面试的与众不同之处在于：它考察的是行星级电商，而非泛化的分布式系统。每个设计都以同一标准评判 —— 它能保住商家的成交吗？

⭐ Staff signal — separate the three flowsStaff 信号 —— 三流分开画 Shopify interviewers explicitly want to see request flow, data flow, and event flow drawn separately. Synchronous read/write paths, the source-of-truth data path, and the async event path each have different consistency and failure properties. Mixing them on one tangled diagram reads as senior-minus. Shopify 面试官明确希望看到请求流、数据流和事件流分开绘制。同步读写路径、权威数据路径和异步事件路径各自有不同的一致性与故障属性。把它们混在一张乱图上，会被评为 senior 以下水平。

What Shopify rewards (and what sinks candidates)Shopify 加分项（及常见失分点）

Rewards加分项
  • Merchant obsession — frame every decision as "how does this protect a small merchant from losing a sale?"
  • 商家至上 —— 把每个决策都框定为"这如何保护小商家不丢失成交？"
  • Correctness where money lives — inventory, payments, orders get strong consistency; storefront reads can be eventual.
  • 金钱所在处的正确性 —— 库存、支付、订单要强一致；店面读取可以最终一致。
  • Spike thinking — BFCM is 100× normal; flash sales are 1000× on one product. Design for the spike, not the average.
  • 峰值思维 —— BFCM 是正常流量的 100 倍；某商品抢购是 1000 倍。为峰值设计，而非平均值。
  • Multi-tenant fairness — one merchant's flash sale must not starve another's checkout.
  • 多租户公平性 —— 一个商家的抢购活动不得饿死另一个商家的结账流程。
Sinks candidates常见失分点
  • Treating it like FAANG "design Twitter" — ignoring the e-commerce domain.
  • 把它当成 FAANG 的"设计 Twitter" —— 忽视电商领域的特殊性。
  • Hand-waving inventory: "just decrement a counter" → overselling.
  • 对库存轻描淡写："减个计数器就好了" → 超卖。
  • One global DB / no tenancy story at Shopify's scale.
  • 单一全局数据库 / 在 Shopify 的规模下没有多租户方案。
  • Designing only the happy path; no payment-gateway-outage or partial-failure story.
  • 只设计顺利路径，没有支付网关故障或局部失败的应对方案。
  • No numbers — can't estimate the hot-key QPS that breaks the design.
  • 没有数字 —— 无法估算会压垮设计的热点 key QPS。

Operational curveball运维突袭题

sometimes replaces the design prompt有时会取代设计题

A few candidates report a debugging-flavored prompt instead of a greenfield design: "Checkout p99 latency just spiked 5×. Walk me through how you find and fix it — live." It tests operational maturity, not box-drawing. A staff answer moves top-down through a mental dependency tree: 部分候选人反映收到的是调试类题目，而非从零开始的设计题： "结账 p99 延迟刚刚飙升了 5 倍。现场带我走一遍你的排查和修复过程。" 这道题考察的是运维成熟度，而非画框框。Staff 级回答会自上而下逐层遍历脑海中的依赖树：

  • Scope & blast radius — all shops or one pod? all regions? started when? correlate with a deploy / flag flip / marketing event.范围与爆炸半径 —— 所有店铺还是单个 pod？所有区域？从何时开始？与发布 / 功能开关切换 / 营销活动相关联。
  • RED/USE metrics — Rate, Errors, Duration per service; Utilization, Saturation, Errors per resource. Find the layer where latency is introduced.RED/USE 指标 —— 每个服务的请求率、错误率、耗时；每个资源的利用率、饱和度、错误数。找出延迟被引入的那一层。
  • Usual suspects — DB connection-pool exhaustion, a hot shard, cache stampede after a flush, a slow downstream (payment gateway), GC pauses, a noisy-neighbor tenant.常见嫌疑人 —— 数据库连接池耗尽、热分片、缓存刷新后的缓存踩踏、慢下游（支付网关）、GC 停顿、"吵闹邻居"租户。
  • Mitigate before root-cause — roll back, shed non-critical load, raise pool limits, fail open on a non-essential dependency. Stop the bleeding, then investigate.先缓解再溯源 —— 回滚、卸掉非关键负载、提高连接池上限、对非核心依赖采用失败放行。先止血，再排查。
  • Follow-up — add an SLO + alert, a load-shedding guard, and a postmortem action item so it can't silently regress.后续跟进 —— 添加 SLO + 告警、负载卸除保护，以及复盘行动项，防止问题静默复现。
⭐ Staff signalStaff 信号 Name the mitigation before the root cause, and quantify customer impact in dollars/conversions, not just milliseconds. That framing — protect the merchant first — is the whole interview in miniature. 先说缓解措施，再说根因，并用美元 / 转化率而非毫秒来量化客户影响。这个框架 —— 先保住商家 —— 正是整场面试的缩影。
