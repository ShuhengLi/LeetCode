Design a Global Inventory Management System设计全球库存管理系统

"Track stock for products across hundreds of warehouses and retail stores, synced to every sales channel — online, POS, Amazon, eBay — in near-real-time. Never oversell. Never phantom-out-of-stock. This is the correctness problem at the heart of Shopify." "跨数百个仓库与门店追踪商品库存,近实时同步到所有销售渠道——线上商店、POS、Amazon、eBay。绝不超卖,绝不虚假缺货。这是 Shopify 核心的正确性问题。"

📍 Seen: staff + senior eng loops出现于：Staff / Senior 面试轮次 🎯 Tests: consistency models + audit考察：一致性模型 + 审计追踪 ⏱ 60 min
Why Shopify loves this one为什么 Shopify 特别喜欢这道题 Inventory is where money meets reality. Every sale, return, transfer, and marketplace sync touches this system. The duality interviewers probe: protect merchants from overselling (angry customers, chargebacks, cancellations) and from phantom out-of-stock (a cache says "0" but the shelf has 20, losing sales). Getting both right simultaneously — under high read QPS, multi-channel concurrency, and millions of multi-tenant shops — is the whole challenge. 库存是金钱与现实交汇的地方。每一笔销售、退货、调拨和渠道同步都经过这个系统。面试官考察的两难困境是：既要保护商家不超卖（避免客户投诉、退款、取消订单），又要防止虚假缺货（缓存显示"0"但货架上还有 20 件，白白损失销售额）。在高读取 QPS、多渠道并发以及数百万多租户商店的条件下同时做对两件事——这就是全部挑战所在。

Clarify requirements澄清需求

~7 min · ask, don't assume多问，不要假设

Functional功能性需求

  • Query available quantity per product variant per location.按商品变体、按仓库位置查询可售数量。
  • Adjust stock: receive goods, process sales, handle returns, manual edits.调整库存：收货、处理销售、退货处理、手动编辑。
  • Reserve / commit / release lifecycle for checkout holds.结账预留的 预留 / 提交 / 释放 生命周期。
  • Transfer inventory between locations (warehouse → store).跨位置调拨库存（仓库 → 门店）。
  • Multi-channel sync: online store, POS, Amazon, eBay push/pull.多渠道同步：线上商店、POS、Amazon、eBay 推/拉。
  • Full audit trail — every change must be traceable to a reason and actor.完整审计追踪——每次变更必须能溯源到原因和操作者。

Non-functional非功能性需求

  • Never oversell — strong consistency on the decrement path.绝不超卖——扣减路径强一致性。
  • High availability for reads — storefront PDPs must never 503.读取高可用——店面商品详情页绝不能 503。
  • Near-real-time propagation — changes reflect across channels in < a few seconds.近实时传播——变更在数秒内同步到所有渠道。
  • Multi-tenant scale — millions of shops, highly skewed (a few giants, millions of smalls).多租户规模——数百万商店，高度倾斜（少数巨头，海量小店）。
  • Full auditability — every stock movement traceable; supports reconciliation and replay.完整可审计性——每次库存变动可追溯；支持对账和重放。
Clarifying questions to actually ask out loud面试时应大声提出的澄清问题
  • Is overselling ever acceptable? (backorders? pre-orders?) — changes whether available can go negative.超卖是否任何时候都不可接受？（支持缺货预订或预购吗？）——这决定 available 能否为负数。
  • How many locations per merchant? A boutique has one; a large retailer may have thousands.每个商家有多少个仓库位置？精品店可能只有一个；大型零售商可能有数千个。
  • Which external channels must be supported, and do they pull (poll our API) or get pushed (webhooks)? Affects fan-out cost.需要支持哪些外部渠道，它们是拉取（轮询我们的 API）还是接收推送（webhook）？影响扇出成本。
  • Does a cart reserve stock, or only a confirmed checkout? This is the single biggest design fork.加购物车时是否预留库存，还是只在确认结账时才预留？这是最关键的设计分叉点。
  • What is the return / restock flow — does a return immediately increment available, or go to a "quarantine" bin?退货/补货流程是怎样的——退货后是否立即增加 available，还是先进"隔离区"等待验货？
  • Accuracy SLA: is "available within 5 seconds" acceptable for external channels? Is it 99.9% or 99.99% for the own-store checkout?精度 SLA：外部渠道"5 秒内可用"是否可接受？自家结账路径是 99.9% 还是 99.99% 的可用性要求？

API designAPI 设计

GET/inventory/{variantId}/levels?locationId=…Returns on_hand, committed, reserved, available per location
POST/inventory/{variantId}/adjust{locationId, delta, reason, ref} — receive / sell / return / manual edit
POST/inventory/reserve{variantId, locationId, qty, ttl} → {reservationId, expiresAt}
POST/inventory/commit{reservationId} — converts reservation to a fulfilled sale
POST/inventory/release{reservationId} — cancels hold (abandoned cart / failed payment)
POST/inventory/transfer{variantId, fromLocationId, toLocationId, qty} — in-transit ledger

All mutating endpoints accept an idempotency-key header — the adjust, reserve, and commit operations must be safe to retry without double-counting. The GET endpoint reads from cache first (Redis) with a DB fallback; the cache is the display truth, the DB is the commit truth.所有变更接口均接受 idempotency-key 请求头——调整、预留和提交操作必须可安全重试而不重复计数。GET 接口优先读取缓存（Redis），未命中时回退到数据库；缓存是展示真相，数据库是提交真相。

-- Materialized current state; PK is composite
inventory_level(
  variant_id   BIGINT  -- FK to product variant,
  location_id  BIGINT  -- warehouse / store,
  on_hand      INT     -- physically present,
  committed    INT     -- placed orders not yet shipped,
  reserved     INT     -- checkout holds not yet committed,

-- Checkout hold; TTL enforced by expiry worker
reservation(
  id           UUID PRIMARY KEY,
  variant_id   BIGINT,
  location_id  BIGINT,
  qty          INT,
  status       ENUM('active','committed','released','expired'),
  expires_at   TIMESTAMP,
  created_at   TIMESTAMP
)

-- Append-only audit log; never UPDATE, never DELETE
inventory_ledger(
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  variant_id   BIGINT,
  location_id  BIGINT,
  delta        INT     -- signed: +recv, -sell, +return,
  reason       ENUM('receive','sale','return','manual','transfer_out','transfer_in'),
  ref          VARCHAR(128) -- order_id / PO number / transfer_id,
  actor        VARCHAR(64)  -- user / system / channel,
  created_at   TIMESTAMP
  -- partitioned by MONTH(created_at) for archival
)

① The three-counter model: on_hand / committed / reserved / available① 三计数器模型：on_hand / committed / reserved / available

A naive inventory system has one number: "stock". Shopify's real model has three explicit counters because each represents a different promise:朴素的库存系统只有一个数字："库存"。Shopify 的真实模型有三个显式计数器，因为每个代表不同的承诺：

  • on_hand — physical units present at the location (what the warehouse scanner says).on_hand——该位置实际存在的实物单位（仓库扫描器显示的数量）。
  • committed — units claimed by placed orders not yet shipped. The merchant has promised these; they cannot be sold again.committed——已下单但尚未发货的订单占用的单位。商家已承诺这些；不能再次销售。
  • reserved — units held by active checkout sessions (cart holds, in-flight payments). Temporary; released if checkout is abandoned or times out.reserved——活跃结账会话持有的单位（购物车预留、支付中）。临时性的；如果结账被放弃或超时则释放。
  • available = on_hand − committed − reserved — what can be sold right now. This is a derived value, never stored directly (avoids drift).available = on_hand − committed − reserved——当前可销售的数量。这是一个派生值，永远不直接存储（避免数据漂移）。

Why not one counter? Because conflating committed and reserved makes it impossible to answer "how many units are actually sellable right now" vs. "how many are leaving the building soon". A merchant restocking a committed unit (return) is different from a customer abandoning a cart (release a reservation). The model encodes these transitions explicitly.为什么不用一个计数器？因为混淆 committed 和 reserved 后，就无法回答"现在实际可卖多少件"与"有多少件即将离库"。商家补充 committed 单位（退货）与客户放弃购物车（释放预留）是两种不同的状态转换。该模型明确编码了这些转换。

Three counters vs. one available counter三计数器 vs. 单一 available 计数器 A single "available" counter is simpler to implement but loses the audit trail. If a customer disputes "you said you had stock," you cannot reconstruct whether the unit was committed, reserved, or genuinely available at the moment of dispute. The three-counter model pays a small complexity tax for full traceability — worth it at Shopify's trust-and-safety requirements. 单一"available"计数器实现更简单，但会丢失审计追踪。如果客户投诉"你说有货"，你无法重建争议时刻该单位是处于 committed、reserved 还是真正 available 状态。三计数器模型用少量复杂度换取完整可追溯性——在 Shopify 的信任与安全要求下完全值得。

The recommended path is optimistic concurrency: attempt a conditional SQL update; if 0 rows affected, the stock is gone — return a graceful "just sold out" to the caller. No locks held, no serialization bottleneck for normal SKUs.推荐路径是乐观并发：尝试条件 SQL 更新；如果影响 0 行，库存已售罄——向调用方返回优雅的"刚刚售罄"。无需持有锁，普通 SKU 无串行化瓶颈。

-- Conditional decrement (the oversell guard)
UPDATE inventory_level
SET
  reserved  = reserved  + :qty,
  version   = version   + 1,
  updated_at = NOW()
WHERE
  variant_id  = :variant_id
  AND location_id = :location_id
  AND (on_hand - committed - reserved) >= :qty
  AND version = :expected_version;   -- optional; omit for simpler path

-- 0 rows affected → sold out or version conflict → retry / reject
-- 1 row affected → reservation created; write to reservation table
The version-conflict retry loop — bound it版本冲突重试循环——必须限制次数 Under sustained hot-key contention (BFCM, flash sale) optimistic retries can spin. Bound retries to 2–3 with exponential jitter and fall back to a "sold out" response. For extreme hot SKUs, escalate to the Redis-counter approach from Q01: Redis is the gate, DB is the durable backstop. 在持续热点键争用（黑五、抢购）下，乐观重试可能空转。将重试次数限制在 2–3 次，加指数退避抖动，最终回退为"售罄"响应。对于极端热点 SKU，升级到 Q01 的 Redis 计数器方案：Redis 作为闸门，数据库作为持久化后盾。

③ Reservation with TTL — preventing abandoned-cart lockup③ 带 TTL 的预留——防止弃单导致库存锁死

When a buyer starts checkout, a reservation holds qty units for N minutes (typically 10–15). The reservation expiry worker polls SELECT … WHERE status='active' AND expires_at < NOW() every 30 seconds, releases expired rows, and fires the reverse adjustment: decrement reserved, restoring availability for other buyers.当买家开始结账时，预留会为 N 分钟（通常 10–15 分钟）锁定 qty 个单位。预留到期 worker 每 30 秒轮询 SELECT … WHERE status='active' AND expires_at < NOW()，释放过期行，并触发反向调整：减少 reserved，为其他买家恢复可用量。

This pattern mirrors the flash-sale compensation loop (Q01). Key correctness property: a release is idempotent — the expiry worker may run multiple times due to at-least-once delivery; the WHERE status='active' guard ensures double-releases are no-ops. The ledger records every release with reason='release_expired' for auditability.此模式与抢购补偿循环（Q01）相同。关键正确性属性：释放操作是幂等的——由于至少一次投递，到期 worker 可能多次运行；WHERE status='active' 条件保证重复释放是无操作。流水账记录每次释放，reason='release_expired'，用于审计。

Trade-off: reserve-at-cart vs. reserve-at-checkout. Reserving at cart-add reduces "item disappeared at checkout" surprises for the buyer but increases held inventory and requires shorter TTLs (5 min vs. 15 min). Reserve-at-checkout-start is simpler and reduces phantom holds from window-shoppers.权衡：加购时预留 vs. 结账时预留。加购时预留可减少买家"结账时商品消失"的意外，但会增加被锁定的库存，且需要更短的 TTL（5 分钟 vs. 15 分钟）。结账开始时预留更简单，并减少浏览者产生的幽灵预留。

④ Event-sourced ledger — audit truth and reconciliation④ 事件溯源流水账——审计真相与对账

The inventory_ledger is the authoritative history: every stock movement is a signed delta row. The inventory_level table is a materialized view of the ledger's running sum. This separation is powerful:inventory_ledger 是权威历史：每次库存变动都是一行带符号的增量记录。inventory_level 表是流水账累计求和的物化视图。这种分离非常强大：

  • Audit: "Why does this SKU show 3 units when I expected 5?" — query the ledger for the variant, find two unexplained sale deltas, trace to order IDs.审计："为什么这个 SKU 显示 3 件，我预期是 5 件？"——查询该变体的流水账，找到两条不明销售增量，追溯到订单 ID。
  • Reconciliation: Recompute SUM(delta) from the ledger and compare to on_hand in the level table. Any mismatch is a bug — alert and investigate.对账：从流水账重新计算 SUM(delta) 并与 level 表中的 on_hand 比较。任何不一致都是 bug——报警并调查。
  • Replay: If a bug corrupts the level table, replay the ledger to rebuild it from scratch.重放：如果 bug 损坏了 level 表，重放流水账从头重建。

⑤ Multi-channel and multi-location sync⑤ 多渠道与多仓库同步

Shopify's own checkout path receives strong consistency — the conditional UPDATE is the arbiter. ⑥ Reconciliation in depth — detecting & correcting drift between Redis, the level table, and the ledger⑥ 深入对账 —— 检测并纠正 Redis 缓存、inventory_level 表与流水账之间的漂移

At any moment three stores hold a view of the same physical stock: the Redis available-count cache, the inventory_level row (on_hand, committed, reserved), and the append-only inventory_ledger. The ledger is the audit truth — it is never updated in place, only appended to. The inventory_level row is a materialized view: on_hand = SUM(ledger.delta WHERE reason IN ('receipt','return_restock',…)), committed = SUM(…), reserved = SUM(…). The Redis cache is a further derived read-optimisation — it holds the computed available = on_hand - committed - reserved with a TTL. Because the level is derived and the cache is derived-from-derived, drift can accumulate through bugs, partial failures, or missed CDC events, and the system must detect and correct it without ever rewriting ledger history.

任何时刻，三个存储持有同一实物库存的视图：Redis available-count 缓存、inventory_level 行（on_hand、committed、reserved）以及仅追加的 inventory_ledger。流水账是审计真相——它从不原地更新，只追加。inventory_level 行是一个物化视图：on_hand = SUM(ledger.delta WHERE reason IN ('receipt','return_restock',…))，committed、reserved 同理。Redis 缓存是进一步派生的读优化——持有计算出的 available = on_hand - committed - reserved 并带有 TTL。由于 level 是派生的，缓存是派生的派生，漂移可能通过 bug、部分失败或遗漏的 CDC 事件积累，系统必须在不重写流水账历史的情况下检测并纠正它。

-- Step 1: re-derive level from ledger (ground truth)
SELECT
  variant_id, location_id,
  SUM(CASE WHEN bucket = 'on_hand'    THEN delta ELSE 0 END) AS derived_on_hand,
  SUM(CASE WHEN bucket = 'committed'  THEN delta ELSE 0 END) AS derived_committed,
  SUM(CASE WHEN bucket = 'reserved'   THEN delta ELSE 0 END) AS derived_reserved
FROM  inventory_ledger
GROUP BY variant_id, location_id;

-- Step 2: compare to stored level; detect drift
-- If derived_on_hand != stored on_hand → drift detected

-- Step 3: post a COMPENSATING ledger entry (never edit history)
INSERT INTO inventory_ledger
  (variant_id, location_id, bucket, delta, reason,         created_at)
VALUES
  (:vid,       :lid,         'on_hand', :drift, 'reconciliation_correction', NOW());
-- drift = derived_on_hand - stored on_hand (can be negative)

-- Step 4: update inventory_level to match
UPDATE inventory_level
SET   on_hand = derived_on_hand,   -- or committed / reserved as needed
      version = version + 1
WHERE variant_id = :vid AND location_id = :lid;

-- SET inv:{vid}:{lid}  (on_hand - committed - reserved)  EX 60

The reconciliation job runs on a schedule — every few minutes for high-velocity variants (flag set when daily adjustments > threshold), hourly for cold variants. On detecting a mismatch it: (1) pages on-call with the magnitude and the affected (variant, location); (2) inserts the compensating ledger entry so the history remains complete and auditable — the correction is visible and attributed, not silently overwritten; (3) updates inventory_level to the recomputed values; (4) force-invalidates (DEL) the Redis key so the next read repopulates from the corrected level. The cache is never the reference — it is always rebuilt from inventory_level, which is always rebuilt from the ledger. This three-tier cascade means a cache bug is trivially fixed (DEL + repopulate), a level bug requires a compensating ledger entry, but a ledger corruption is a P0 incident — the ledger must be append-only and its rows must be immutable.

对账作业按计划运行——高频变体（当日调整次数超过阈值时设置标志）每几分钟一次，冷变体每小时一次。检测到不匹配时：(1) 附带偏差幅度和受影响的（变体、位置）呼叫值班人员；(2) 插入补偿流水账条目，使历史保持完整且可审计——纠正是可见且有归属的，不会被静默覆盖；(3) 将 inventory_level 更新为重新计算的值；(4) 强制失效（DEL）Redis 键，使下次读取从纠正后的 level 重新填充。缓存永远不是参考——它总是从 inventory_level 重建，后者总是从流水账重建。这种三层级联意味着：缓存 bug 可以简单修复（DEL + 重新填充），level bug 需要补偿流水账条目，而流水账损坏是 P0 事故——流水账必须是仅追加的，其行必须不可变。

Why the ledger, not the level, is the source of truth为什么流水账（而非 level 表）才是真相来源 The inventory_level row is convenient but it is a cached aggregate. It can be reconstructed from the ledger at any point; the reverse is not true — you cannot reconstruct the ledger from the level alone. This asymmetry is the key: the ledger records why a unit moved (sale, return, manual edit, reconciliation correction), which is essential for merchant disputes, regulatory audits, and root-cause debugging. If a bug causes the level and the ledger to diverge, the ledger wins — the level is corrected to match the ledger, never the other way around. Keeping the ledger immutable and append-only is the non-negotiable invariant that makes the whole audit model trustworthy. inventory_level 行虽然方便，但它是一个缓存聚合。它可以在任何时候从流水账重建；反之则不然——你无法仅从 level 表重建流水账。这种不对称性是关键：流水账记录了单位为何移动（销售、退货、手动编辑、对账纠正），这对商家争议、监管审计和根因调试至关重要。如果 bug 导致 level 表与流水账出现分歧，流水账胜出——level 表被纠正以匹配流水账，绝不反过来。保持流水账不可变和仅追加，是使整个审计模型可信的不可妥协的不变式。

① Consistency model per channel — strong everywhere vs. hybrid① 各渠道一致性模型 —— 全部强一致 vs. 混合

The tension: Shopify's own checkout path must never oversell, which demands strong consistency on the decrement. 矛盾点：Shopify 自有结账路径绝不能超卖，因此扣减需要强一致性。但 Shopify 同时还要向 Amazon、eBay 和 POS 扇出——若强迫所有渠道走同一条同步 DB 路径，写入延迟会成倍增加，并将关键路径与缓慢的外部 webhook 耦合在一起。

Option A · Strong consistency everywhere方案 A · 全部强一致性

Every channel — own storefront, POS, Amazon, eBay — reads and writes through the same serialized conditional UPDATE. No channel can see stale stock.

每个渠道——自有店面、POS、Amazon、eBay——都通过同一条串行化条件 UPDATE 读写库存。没有渠道能看到陈旧库存。

+ True single source of truth; cross-channel oversell is mathematically impossible because every decrement acquires the same row-level serialization.

+ 真正的单一真相来源；跨渠道超卖在数学上不可能，因为每次扣减都获得同一行级串行化。

− Every external webhook must wait for the DB write to confirm before returning; a slow Amazon API call is now on the Shopify checkout critical path. DB connection pool becomes a bottleneck across all channels simultaneously.

− 每个外部 webhook 都必须等 DB 写入确认才能返回；慢速 Amazon API 调用现在进入了 Shopify 结账关键路径。DB 连接池同时成为所有渠道的瓶颈。

Option B · Strong for own checkout; eventual for marketplaces方案 B · 自有结账强一致；第三方平台最终一致

The conditional SQL UPDATE is the only authority for the Shopify checkout path. After it succeeds, a Kafka CDC event fans out to a webhook worker that delivers inventory corrections to external channels asynchronously — typically within seconds.

条件 SQL UPDATE 仅对 Shopify 结账路径具有权威性。成功后，Kafka CDC 事件扇出到 webhook worker，异步向外部渠道推送库存纠正——通常在数秒内完成。

+ Own checkout stays fast and decoupled; external channels absorb lag they already expect (Amazon SLA for inventory sync is seconds, not µs). DB write path is unaffected by external channel availability.

+ 自有结账保持快速且解耦；外部渠道接受它们本就预期的滞后（Amazon 库存同步 SLA 是秒级，不是微秒级）。DB 写路径不受外部渠道可用性影响。

− A race window exists: Amazon and Shopify can both sell the "last" unit simultaneously because Amazon's cache is seconds stale. The conditional UPDATE is the arbiter — the losing channel gets 0 rows affected and must accept a correction webhook. This is a known and intentional design; the oversell guard still holds.

− 存在竞争窗口：Amazon 和 Shopify 可能同时卖出"最后一件"，因为 Amazon 的缓存有秒级陈旧。条件 UPDATE 是仲裁者——失败渠道得到 0 行受影响并必须接受纠正 webhook。这是已知且有意的设计；防超卖守卫依然成立。

Hybrid is the right answer for Shopify's reality. Own-checkout is the money path and demands the DB's serialization guarantee. External channels already operate on eventual consistency and have their own buffers; coupling them to the synchronous path would be an architectural mistake. The conditional UPDATE acting as global arbiter prevents oversell even in the hybrid model.

混合方案是 Shopify 现实情况下的正确答案。自有结账是核心收入路径，需要 DB 的串行化保证。外部渠道本就在最终一致性下运作并有自己的缓冲区；将它们耦合到同步路径将是架构上的错误。条件 UPDATE 作为全局仲裁者，即使在混合模型中也能防止超卖。

② Concurrency on hot SKU — pessimistic lock vs. optimistic conditional UPDATE② 热点 SKU 并发 —— 悲观锁 vs. 乐观条件 UPDATE

The tension: you need to ensure "never decrement below zero" atomically. The two classical tools for this — locking the row pessimistically before reading vs. checking the condition inside the UPDATE — have very different performance profiles under concurrent load.

矛盾点：你需要原子性地保证"永不减到零以下"。两种经典工具——读之前悲观锁住行，还是在 UPDATE 内部做条件检查——在并发负载下有截然不同的性能特征。

Option A · Pessimistic lock (SELECT FOR UPDATE)方案 A · 悲观锁（SELECT FOR UPDATE）

Transaction opens, reads the row with SELECT … FOR UPDATE (acquires an exclusive lock), checks available in application code, then writes the decrement; lock is released on commit.

事务开启，用 SELECT … FOR UPDATE 读取行（获取排他锁），在应用代码中检查 available，然后写入扣减；提交时释放锁。

+ Correct by construction: the lock guarantees no other writer can observe the row between the read and the write. Application logic can do complex multi-step checks before writing.

+ 设计上正确：锁保证读写之间没有其他写者能观察到该行。应用逻辑在写入前可做复杂的多步检查。

− Every concurrent writer queues behind the exclusive lock on the same row. For a hot SKU with thousands of concurrent reservations the row becomes a hard serialization bottleneck — throughput collapses, lock wait times spike, and DB connection pool exhaustion is a real risk.

− 每个并发写者都在同一行的排他锁后面排队。对于有数千并发预留的热点 SKU，该行成为硬性串行化瓶颈——吞吐崩溃，锁等待时间飙升，DB 连接池耗尽是真实风险。

Option B · Optimistic conditional UPDATE方案 B · 乐观条件 UPDATE

UPDATE inventory_level SET reserved=reserved+qty WHERE variant_id=? AND location_id=? AND (on_hand-committed-reserved) >= qty; the database engine evaluates the condition atomically inside the write, no separate lock acquisition.

UPDATE inventory_level SET reserved=reserved+qty WHERE variant_id=? AND location_id=? AND (on_hand-committed-reserved) >= qty；数据库引擎在写操作内部原子地评估条件，无需单独获取锁。

+ No long-held lock: the DB row is locked only for the duration of the single UPDATE statement (microseconds), not for the application-round-trip time. Concurrency is far higher; writers don't block each other waiting for application logic.

+ 无长时间锁持有：DB 行仅在单个 UPDATE 语句执行期间（微秒级）被锁定，而非在应用往返时间内。并发度大幅提高；写者不会因等待应用逻辑而互相阻塞。

− Under extreme contention (thousands of concurrent attempts on one row) even the short-lived write-lock can pile up. At the absolute limit, escalate to the Redis atomic counter pattern from Q01. Also: cannot express complex cross-table checks inside a single UPDATE predicate.

− 在极端竞争下（单行数千并发尝试），即使短暂的写锁也会堆积。在绝对极限时，升级到 Q01 的 Redis 原子计数器模式。另外：无法在单个 UPDATE 谓词内表达跨表的复杂检查。

When to use which何时用哪个

Use optimistic conditional UPDATE as the default. For the normal inventory workload (hundreds of concurrent reservations at most), the single-statement approach is correct, fast, and requires no retry infrastructure. Reserve pessimistic locking only when the application must inspect and conditionally branch across multiple tables before writing — and even then, keep the transaction short. For extreme hot-SKU bursts (flash-sale scale), escalate to the Redis atomic counter from Q01: Redis gate absorbs the million-concurrent-attempt fan-in; the DB conditional UPDATE becomes the durable backstop with reconciliation.

乐观条件 UPDATE 作为默认选择。对于正常库存工作负载（最多数百并发预留），单语句方案正确、快速，无需重试基础设施。仅当应用必须在写入前跨多张表检查并条件分支时，才使用悲观锁——即便如此，也要保持事务短暂。对于极端热点 SKU 爆发（抢购规模），升级到 Q01 的 Redis 原子计数器：Redis 闸门吸收百万并发尝试的汇聚；DB 条件 UPDATE 成为带对账的持久化后盾。

③ Cache freshness vs. DB load — short TTL vs. CDC invalidation③ 缓存新鲜度 vs. DB 负载 —— 短 TTL vs. CDC 失效

The tension: the Redis available-count cache serves millions of PDP reads per second and must never reflect phantom out-of-stock (or phantom in-stock). The question is how you keep it synchronized with the DB after every inventory write, and at what cost.

矛盾点：Redis available-count 缓存每秒为数百万次 PDP 读提供服务，绝不能反映幽灵缺货（或幽灵有货）。问题是如何在每次库存写入后保持它与 DB 同步，以及代价如何。

Option A · Short TTL (5 s) only方案 A · 仅短 TTL（5 秒）

Cache expires every 5 seconds; on miss the caller fetches from DB and repopulates. No explicit invalidation logic needed.

缓存每 5 秒过期；未命中时调用方从 DB 取值并重新填充。无需显式失效逻辑。

+ Simplest possible implementation: no producer-side write-through, no Kafka consumer, no invalidation race; if cache goes down, fallback to DB is automatic.

+ 最简单的实现：无生产侧写透、无 Kafka 消费者、无失效竞争；缓存宕机时自动降级到 DB。

− Up to 5 s stale: during a flash event or rapid sell-through the storefront can show "in stock" for 5 s after the last unit sold, generating frustrating "sold out at checkout" surprises. If the SKU is read millions of times in those 5 s, each miss hits the DB simultaneously (thundering herd on cache expiry).

− 最多 5 秒陈旧：在抢购活动或快速售罄期间，店面可能在最后一件售出后 5 秒内仍显示"有货"，造成"结账时售罄"的不满意外。若 SKU 在这 5 秒内被读取数百万次，每次未命中都会同时访问 DB（缓存过期时的惊群效应）。

Option B · Long TTL + CDC invalidation on every write方案 B · 长 TTL + 每次写入时 CDC 失效

Cache TTL is set long (e.g. 60 s); a Kafka CDC consumer listens for inventory_level row changes and immediately calls DEL key or SET key newValue in Redis after every DB write.

缓存 TTL 设置较长（如 60 秒）；Kafka CDC 消费者监听 inventory_level 行变更，在每次 DB 写入后立即在 Redis 中调用 DEL key 或 SET key newValue。

+ Cache staleness is bounded by the CDC propagation lag (typically <1 s), not the TTL. Under a rapid sell-through, PDP readers see "sold out" within ~1 s of the last conditional UPDATE. Long TTL eliminates thundering herds on cold items since they almost never expire spontaneously.

+ 缓存陈旧度受 CDC 传播延迟（通常 <1 秒）限制，而非 TTL。快速售罄时，PDP 读者在最后一次条件 UPDATE 约 1 秒内看到"售罄"。长 TTL 消除了冷商品上的惊群效应，因为它们几乎不会自发过期。

− Adds infrastructure: a running Kafka CDC pipeline and consumer. There is a small window between the DB commit and the CDC consumer processing the event where cache and DB can disagree. Write-after-invalidation races require careful handling (e.g. invalidation after a crash must not leave cache in an indefinitely stale state — the TTL acts as the final safety net).

− 增加基础设施：需要运行中的 Kafka CDC 管道和消费者。DB 提交与 CDC 消费者处理事件之间存在小窗口，缓存与 DB 可能不一致。失效后写入的竞争需要仔细处理（例如崩溃后的失效不能让缓存永久陈旧——TTL 充当最终安全网）。

When to use which何时用哪个

CDC invalidation + fallback TTL is the production answer. Short-TTL-only is acceptable for low-velocity SKUs (seasonal items rarely sold). The moment you have high-velocity SKUs or flash events, a 5 s staleness window is customer-visible. The right design layers both: CDC invalidation provides near-real-time freshness; the TTL is the safety net that prevents indefinitely stale cache entries if the CDC consumer falls behind or crashes.

CDC 失效 + 兜底 TTL 是生产环境的正确答案。仅短 TTL 对低频 SKU（很少销售的季节性商品）可接受。一旦有高频 SKU 或抢购活动，5 秒陈旧窗口就会被用户感知。正确设计是两者叠加：CDC 失效提供近实时新鲜度；TTL 是安全网，防止 CDC 消费者滞后或崩溃时缓存条目永久陈旧。

④ Reserve at cart-add vs. checkout-start④ 加购时预留 vs. 结账时预留

The tension: the moment you lock a unit in the reserved counter, other buyers can no longer purchase it. The question is whether that lock should happen when the buyer clicks "Add to cart" (early) or when they actually begin the checkout flow (late).

矛盾点：一旦你在 reserved 计数器中锁定一个单位，其他买家就无法再购买它。问题是这个锁应该在买家点击"加入购物车"时（早锁）还是在实际开始结账流程时（晚锁）发生。

Option A · Reserve at cart-add方案 A · 加购时预留

A unit is immediately added to reserved when the buyer adds the item to their cart, with a short TTL (e.g. 5 min).

买家将商品加入购物车时，立即将一个单位加入 reserved，并设置短 TTL（如 5 分钟）。

+ The buyer sees "this item is held for you" throughout the shopping session — no "item disappeared at checkout" surprise. Conversion rates improve for scarce items because buyers feel they have a slot.

+ 买家在整个购物会话中看到"此商品为您保留"——无结账时商品消失的意外。稀缺商品的转化率提升，因为买家感觉自己有一个名额。

− Window-shoppers and comparison-shopping browsers hold units for 5 minutes that could have been sold. High phantom-hold rate on popular SKUs artificially deflates the displayed available count, potentially showing "sold out" while units sit in abandoned carts.

− 浏览者和比价购物者会持有单位 5 分钟，这段时间本可销售。热门 SKU 上高幽灵预留率会人为压低显示的可用数量，可能在单位躺在被遗弃的购物车中时显示"售罄"。

Option B · Reserve at checkout-start方案 B · 结账时预留

No unit is locked in reserved until the buyer explicitly initiates checkout, at which point the conditional UPDATE fires with a longer TTL (e.g. 10–15 min).

在买家明确发起结账之前，不锁定任何单位到 reserved；此时条件 UPDATE 触发，TTL 更长（如 10–15 分钟）。

+ No phantom holds from casual browsers; available count is honest until the last moment. Simpler TTL management — one TTL tier instead of two. Works well for the vast majority of Shopify merchants where abandonment at cart is high but stock is not scarce.

+ 无随意浏览者产生的幽灵预留；available 计数直到最后一刻都是真实的。TTL 管理更简单——一个 TTL 层而非两个。适用于绝大多数购物车放弃率高但库存不稀缺的 Shopify 商家。

− A buyer who spent 10 minutes with an item in their cart may hit "sold out" at the checkout page because the stock sold during their browsing session — frustrating on high-demand launches.

− 将商品放在购物车里浏览 10 分钟的买家可能在结账页面遇到"售罄"，因为库存在其浏览期间已售出——在高需求商品发布时体验很差。

When to use which何时用哪个

Checkout-start is the right default for the general Shopify merchant base — stock is usually abundant and phantom holds hurt availability accuracy more than they help conversion. Offer cart-add reservation as an opt-in (configurable per launch) for high-demand product drops where protecting the "sold for you" experience is worth the phantom-hold cost; use an aggressive 5-minute TTL so abandoned carts drain quickly.

结账时预留是一般 Shopify 商家群体的正确默认值——库存通常充足，幽灵预留对可用性准确度的损害大于对转化率的帮助。将加购时预留作为可选功能（按发布活动配置）提供给高需求商品发布场景，此时保护"为您锁定"体验值得付出幽灵预留的代价；使用积极的 5 分钟 TTL，以便被遗弃的购物车快速释放。

⑤ Single available counter vs. three-counter model⑤ 单一 available 计数器 vs. 三计数器模型

The tension: a single available column is the simplest possible representation — one number, one write, one read. But inventory movements have semantically distinct reasons (physical stock on hand vs. order commitments vs. checkout holds), and collapsing them loses information that is valuable for audit, reconciliation, and debugging.

矛盾点：单一 available 列是最简单的表示——一个数字、一次写入、一次读取。但库存变动有语义上截然不同的原因（实物在手 vs. 订单承诺 vs. 结账预留），将它们合并会丢失对审计、对账和调试都有价值的信息。

Option A · Single available counter方案 A · 单一 available 计数器

One column stores the current sellable count; every event (sale, return, receipt, hold, release) is a direct delta to that column.

一列存储当前可售数量；每个事件（销售、退货、收货、预留、释放）都是对该列的直接增量。

+ Minimal schema, minimal write path: one conditional decrement is the entire reserve operation. Easiest to reason about for simple merchants.

+ 最小化 schema，最简写路径：一次条件扣减就是完整的预留操作。对简单商家最易理解。

− After a dispute ("why do I have 3 units when I expected 5?") you cannot determine whether units are in-transit, in active checkouts, or genuinely missing without querying an external audit table. Reconciliation is also harder — you can't verify the number is correct by summing the underlying components.

− 发生争议（"为什么我预期 5 件却显示 3 件？"）后，如果不查询外部审计表，你无法确定单位是在途中、在活跃结账中还是真正丢失。对账也更难——你无法通过对底层组成求和来验证数字是否正确。

Option B · on_hand / committed / reserved (available derived)方案 B · on_hand / committed / reserved（available 派生）

available is never stored — it is always computed as on_hand - committed - reserved. Each counter maps to a distinct business state: physical receipt/return events touch on_hand; order placement and fulfilment touch committed; checkout sessions touch reserved.

available 从不存储——始终作为 on_hand - committed - reserved 计算得出。每个计数器映射到不同的业务状态：实物收货/退货事件影响 on_hand；下单和履约影响 committed；结账会话影响 reserved。

+ Any "why is my count wrong?" question can be decomposed: is it committed to unfulfilled orders? Held in active checkouts? Or genuinely missing? Combined with the ledger, every unit has a full traceable lineage. Reconciliation is structural — just recompute the derived value and compare.

+ 任何"为什么我的数量不对？"都可以分解：是被未履约订单占用？被活跃结账持有？还是真正丢失？结合流水账，每个单位都有完整可追溯的谱系。对账是结构性的——只需重新计算派生值并比较。

− Three columns to update transactionally instead of one; application code must route events to the correct counter; more complex conditional UPDATE predicate. Slightly higher schema cognitive load for engineers unfamiliar with the model.

− 需要在事务中更新三列而非一列；应用代码必须将事件路由到正确的计数器；条件 UPDATE 谓词更复杂。对不熟悉该模型的工程师来说 schema 认知负担略高。

When to use which何时用哪个

Three counters are non-negotiable at Shopify's trust-and-safety bar. The single counter is fine for a toy or MVP, but the moment merchants dispute stock figures — and they will — you need to decompose the causes. The reconciliation job (ledger sum vs. level) cannot work without the component counters. A single-counter system would require a separate audit table to recover the same information, which is more complexity, not less.

在 Shopify 的信任与安全标准下，三计数器是不可妥协的。单计数器对玩具项目或 MVP 可以，但一旦商家开始争议库存数字——这必然会发生——你就需要分解原因。没有组件计数器，对账作业（流水账求和 vs. level 表）就无法运作。单计数器系统需要独立的审计表来恢复同样的信息，复杂度反而更高。

⑥ Channel sync: push webhooks vs. pull polling⑥ 渠道同步：推送 webhook vs. 拉取轮询

The tension: inventory changes inside Shopify must propagate to external channels like Amazon and eBay. The system can either push changes out (Kafka fan-out → webhook to channel) or let channels pull changes on a schedule (periodic API calls). These have opposing tradeoffs on freshness, coupling, and infrastructure complexity.

矛盾点：Shopify 内部的库存变更必须传播到 Amazon、eBay 等外部渠道。系统可以推送变更（Kafka 扇出 → webhook 到渠道），也可以让渠道按计划拉取变更（定期 API 调用）。两者在新鲜度、耦合和基础设施复杂度上有相反的权衡。

Option A · Push (Kafka fan-out → webhooks)方案 A · 推送（Kafka 扇出 → webhook）

After every successful inventory_level write, a CDC event lands in Kafka; a fan-out worker consumes it and delivers an inventory-update webhook to each subscribed external channel within seconds.

每次成功写入 inventory_level 后，CDC 事件进入 Kafka；扇出 worker 消费它并在数秒内向每个订阅的外部渠道推送库存更新 webhook。

+ Near-real-time propagation — channels receive the update event-driven rather than waiting for their next poll cycle. During a sell-through, Amazon's listing is corrected in ~1–2 s rather than ~5–15 min.

+ 近实时传播——渠道以事件驱动方式接收更新，而非等待下一个轮询周期。售罄期间，Amazon 的商品列表在约 1–2 秒内得到纠正，而非 5–15 分钟。

− Fan-out infrastructure must be maintained; webhook delivery is at-least-once and requires retries, deduplication on the receiver side, and dead-letter handling. Shopify owns the push; if a channel's webhook endpoint goes down, the burden of retrying and backpressure is on Shopify.

− 扇出基础设施必须维护；webhook 推送是至少一次语义，需要重试、接收端去重和死信处理。Shopify 负责推送；若渠道的 webhook 端点宕机，重试和背压的负担在 Shopify 这侧。

Option B · Pull (channels poll Shopify API)方案 B · 拉取（渠道轮询 Shopify API）

External channels call the Shopify Inventory API on a schedule (every N minutes) and diff against their local copy to detect changes.

外部渠道按计划（每 N 分钟）调用 Shopify Inventory API，并与本地副本做差异对比以检测变更。

+ Simple from Shopify's side: no Kafka pipeline, no fan-out worker, no webhook retry machinery. If a channel goes down, it just misses one cycle and catches up on the next poll — natural backpressure absorption.

+ 从 Shopify 一侧简单：无 Kafka 管道、无扇出 worker、无 webhook 重试机制。若渠道宕机，它只是错过一个周期，下次轮询时追上——自然背压吸收。

− Inherently laggy by the poll interval — in a flash sell-through that interval (e.g. 5–15 min) is an oversell window on external platforms. N channels × M merchants × M variants polling simultaneously generates enormous read QPS on the inventory API that must be rate-limited and cached.

− 固有的轮询间隔延迟——在快速售罄中，该间隔（如 5–15 分钟）是外部平台上的超卖窗口。N 个渠道 × M 个商家 × M 个变体同时轮询会在库存 API 上产生巨大的读取 QPS，必须进行速率限制和缓存。

When to use which何时用哪个

Push for owned integrations (Shopify Markets, POS, first-party apps) where you control both ends and the infrastructure investment is justified. Allow pull for third-party integrations where the channel demands it or the integration is low-volume — but enforce explicit rate limits (e.g. per-shop per-channel limits) and serve the pull endpoint from Redis cache, never the primary DB. For high-velocity channels, push should be the strong default.

自有集成（Shopify Markets、POS、第一方应用）使用推送——你控制两端，基础设施投入是值得的。允许第三方集成使用拉取——渠道要求这样做或集成量小时——但强制执行明确的速率限制（如每商家每渠道限制），并从 Redis 缓存提供拉取端点，绝不访问主 DB。对于高频渠道，推送应是强默认值。

How do you handle backorders and pre-orders — can available go negative?如何处理缺货预订和预购——available 可以变为负数吗？

Yes, with an explicit product configuration. When a variant is marked backorder_enabled or preorder, the conditional UPDATE drops the available >= qty guard and allows on_hand - committed - reserved to go negative, representing a backorder commitment. The UI shows "ships in X weeks" instead of "in stock." The ledger records these with reason='backorder_sale'. Critically, this is a per-variant setting, not a system-wide one — most merchants never enable it.可以，但需要显式的商品配置。当变体被标记为 backorder_enabled 或 preorder 时，条件 UPDATE 去掉 available >= qty 的守卫，允许 on_hand - committed - reserved 变为负数，代表缺货预订承诺。UI 显示"X 周内发货"而非"有货"。流水账以 reason='backorder_sale' 记录这些操作。关键是，这是每个变体的配置，而非全系统设置——大多数商家从不启用它。

A customer returns an item — how does inventory reflect that?客户退货——库存如何反映？

A return triggers a ledger entry with reason='return' and delta=+qty. But whether that immediately increments on_hand depends on merchant configuration: some merchants want to inspect returned goods before restocking. The pattern is a status='quarantine' flag on the return; when the merchant marks it "restockable," a second ledger row with reason='restock_approved' increments on_hand. This means committed can only decrease when an order ships (or is cancelled), not on return initiation — protecting against a merchant thinking stock is back before it physically arrives.退货触发一条 reason='return'、delta=+qty 的流水账条目。但是否立即增加 on_hand 取决于商家配置：有些商家希望在上架前检验退回商品。模式是在退货上设置 status='quarantine' 标志；当商家标记为"可上架"时，第二条 reason='restock_approved' 的流水账行才增加 on_hand。这意味着 committed 只在订单发货（或取消）时减少，而不是在退货发起时——防止商家在货物实际到达前误以为库存已恢复。

Two channels sell the last unit at the exact same instant — what happens?两个渠道在同一时刻卖出最后一件——会发生什么？

Both channels read available=1 from cache and attempt a conditional UPDATE. SQL serializes concurrent updates to the same row: one transaction gets 1 row affected (success); the other gets 0 rows affected (available is now 0). The losing caller receives a "sold out" response and must either reject the order or route to backorder. For external marketplace channels, the Inventory Service fires a correction webhook ("available is now 0") — Amazon or eBay must respect that and update their listings. No oversell occurs. This is the single conditional UPDATE acting as the global arbiter.两个渠道都从缓存读到 available=1 并尝试条件 UPDATE。SQL 将同一行的并发更新串行化：一个事务得到 1 row affected（成功）；另一个得到 0 rows affected（available 现在为 0）。失败方收到"售罄"响应，必须拒绝订单或转入缺货预订。对于外部平台渠道，Inventory Service 发送纠正 webhook（"available 现在为 0"）——Amazon 或 eBay 必须尊重并更新其商品列表。不会发生超卖。这就是单一条件 UPDATE 作为全局仲裁者。

How do you detect and fix drift between the Redis cache, the level table, and the ledger?如何检测和修复 Redis 缓存、level 表与流水账之间的漂移？

Three-way reconciliation job runs on a schedule (every few minutes for hot SKUs, hourly for cold ones): (1) compute SUM(delta) from inventory_ledger per variant-location → this is the ground truth; (2) compare to inventory_level.on_hand — if mismatch, alert and optionally self-heal with a reason='reconciliation_correction' ledger entry; (3) compare Redis cache value to inventory_level.available — if mismatch and within TTL window, acceptable; if stale beyond 2× TTL, force-invalidate. Persistent drift between the ledger sum and the level table is a critical bug — page on-call immediately, do not silently self-correct without alerting.三方对账作业定时运行（热点 SKU 每几分钟一次，冷 SKU 每小时一次）：(1) 按变体-位置从 inventory_ledger 计算 SUM(delta) → 这是基准真相；(2) 与 inventory_level.on_hand 比较——若不匹配，报警并可选地以 reason='reconciliation_correction' 流水账条目自愈；(3) 将 Redis 缓存值与 inventory_level.available 比较——若不匹配且在 TTL 窗口内，可接受；若陈旧超过 2× TTL，强制失效。流水账求和与 level 表之间的持久漂移是严重 bug——立即呼叫值班人员，不要在不报警的情况下静默自纠正。

A huge merchant has millions of SKUs and one variant goes viral — how do you handle the hot SKU?某大商家有数百万 SKU，某个变体突然爆红——如何处理热点 SKU？

For large-merchant scale: the shard keyed to their shop_id can be further split (sub-sharding by variant_id hash). For a genuinely viral hot SKU (think BFCM-level), escalate to the Redis-counter gate pattern from Q01: pre-load the available count into a Redis DECRBY counter; the SQL DB becomes the durable backstop with async reconciliation. This trades the durability gap (Redis not-yet-flushed state) for µs-level atomic decrements that can sustain millions of concurrent attempts. The Q01 flash-sale design is exactly this pattern generalized.对于大商家规模：以其 shop_id 为键的分片可以进一步拆分（按 variant_id 哈希子分片）。对于真正爆红的热点 SKU（黑五量级），升级到 Q01 的 Redis 计数器闸门模式：将 available 计数预加载到 Redis DECRBY 计数器；SQL DB 成为带异步对账的持久化后盾。这用持久性缺口（Redis 尚未落盘的状态）换取 µs 级原子扣减，可承受数百万并发尝试。Q01 的抢购设计正是这一模式的泛化。

How do search and PDP show stock status without hammering the inventory DB?搜索和 PDP 如何在不冲击库存 DB 的情况下展示库存状态？

Two-layer strategy: (1) Redis cache — the Inventory Service writes hot available counts to Redis on every successful adjustment; PDPs read Redis directly, not the SQL DB. Cache TTL is 60 s; CDC Kafka consumer invalidates the key immediately on any write, so cache staleness is bounded by the time between a write and the invalidation message processing (typically <1 s). (2) Search index — Elasticsearch/Typesense is updated from the Kafka CDC stream; the search "in-stock" filter reads from the index, not from the inventory DB at all. This means search can show slightly stale in-stock status (seconds), which is acceptable for discovery — exact availability is confirmed at checkout time by the conditional SQL UPDATE.两层策略：(1) Redis 缓存——Inventory Service 在每次成功调整后将热点 available 计数写入 Redis；PDP 直接读 Redis，不读 SQL DB。缓存 TTL 为 60 秒；CDC Kafka 消费者在任何写入时立即失效对应键，因此缓存陈旧度受限于写入与失效消息处理之间的时间（通常 <1 秒）。(2) 搜索索引——Elasticsearch/Typesense 由 Kafka CDC 流更新；搜索"有货"过滤器从索引读取，完全不触碰库存 DB。这意味着搜索可能显示略微陈旧的有货状态（秒级），对于商品发现是可接受的——确切可用性在结账时由条件 SQL UPDATE 确认。

How does a return / restock flow keep available correct?退货/补货流程如何保持 available 正确？

The return is modelled as a ledger append: reason='return', delta=+qty, ref=return_id. Idempotency is enforced by a unique index on ref — replaying the same return event is a no-op. on_hand increments only after inspection passes (a second ledger row with reason='restock_approved'), so available stays conservative until the goods are physically confirmed. This two-phase pattern prevents phantom availability and keeps the ledger as the single source of truth for every unit's lifecycle.退货被建模为一条流水账追加：reason='return', delta=+qty, ref=return_id。幂等性由 ref 上的唯一索引保证——重放同一退货事件是无操作。on_hand 仅在检验通过后才增加（第二条 reason='restock_approved' 的流水账行），因此在货物被实物确认前 available 保持保守值。这种两阶段模式防止了幽灵可用量，并让流水账成为每个单位全生命周期的唯一真相来源。

How does the model change for backorders / pre-orders (overselling intentionally allowed)?缺货预订/预购（有意允许超卖）时模型如何改变？

Two approaches: (a) allow available to go negative — the conditional UPDATE simply removes the >= qty guard when backorder_enabled=true for that variant, and the ledger records a reason='backorder_sale'; the UI surfaces "ships in X weeks." (b) maintain a separate backorder_qty counter alongside the normal counters, so the oversell commitment is always explicit and does not muddy the regular available semantics. Either way this is a per-variant policy, toggled by the merchant, never a system-wide default. Keeping it per-variant lets most of the codebase stay simple while allowing the edge case cleanly.两种方式：(a) 允许 available 变为负数——当该变体 backorder_enabled=true 时，条件 UPDATE 简单地去掉 >= qty 守卫，流水账记录 reason='backorder_sale'；UI 显示"X 周内发货"。(b) 在常规计数器旁维护独立的 backorder_qty 计数器，使超卖承诺始终显式，不污染常规 available 语义。无论哪种方式，这都是每个变体的策略，由商家切换，绝不是全系统默认值。按变体维护策略让绝大多数代码保持简单，同时干净地处理边缘情况。

How do you sync inventory to an external marketplace (e.g. Amazon) given their ingest lag?考虑到外部平台（如 Amazon）的摄入延迟，如何同步库存？

The canonical pattern is async push via CDC events: every inventory_level write emits a Kafka event; a channel-sync worker consumes it and calls Amazon's inventory API (or queues for their batch ingest). Because Amazon can take minutes to reflect updates, a safety buffer is essential: publish available − threshold (e.g. subtract 5–10 units) to Amazon, keeping a cushion that absorbs the window of concurrent sales. If both channels sell simultaneously and Amazon's side oversells due to lag, the Shopify conditional UPDATE still wins — fire a correction webhook immediately to push Amazon to 0. The rule is: eventual consistency is fine for display; Shopify's DB is the arbiter for committed stock.标准模式是通过 CDC 事件异步推送：每次 inventory_level 写入都触发 Kafka 事件；渠道同步 worker 消费它并调用 Amazon 的库存 API（或排入其批量摄入队列）。由于 Amazon 可能需要数分钟才能反映更新，安全缓冲区至关重要：向 Amazon 发布 available − threshold（例如减去 5–10 件），保留缓冲以吸收并发销售窗口。如果两个渠道同时销售，Amazon 因延迟超卖，Shopify 的条件 UPDATE 仍然获胜——立即发送纠正 webhook 将 Amazon 推为 0。规则是：最终一致性用于展示没问题；Shopify 的 DB 是已承诺库存的仲裁者。

A bug double-counted a shipment — how do you detect and correct it?一个 bug 导致某次出货被重复计数——如何检测和纠正？

Detection: the reconciliation job computes SUM(ledger.delta) per variant-location and diffs against inventory_level.on_hand. A double-counted shipment appears as a negative variance (level shows fewer units than ledger sum). The ledger is the truth — the level table is the derived view that drifted. Correction: never edit or delete the erroneous ledger rows (that destroys the audit trail). Instead, post a new correcting adjustment row: reason='reconciliation_correction', delta=+N, ref=bug-ticket-id. This brings the level back in sync while preserving full history. Then find and fix the root-cause bug so it cannot recur, and add a test that exercises the idempotency key to prevent replay double-counts.检测：对账作业按变体-位置计算 SUM(ledger.delta) 并与 inventory_level.on_hand 做差异。重复计数的出货表现为负偏差（level 显示的单位少于流水账求和）。流水账是真相——level 表是漂移的派生视图。纠正：永远不要编辑或删除错误的流水账行（那会破坏审计追踪）。而是发布一条新的纠正调整行：reason='reconciliation_correction', delta=+N, ref=bug-ticket-id。这在保留完整历史的同时让 level 重新同步。然后找出并修复根本原因 bug 防止复发，并添加测试来覆盖幂等键，防止重放导致的重复计数。

Bundles / kits: one sale must decrement several SKUs atomically — how?捆绑包/套件：一次销售必须原子性地扣减多个 SKU——如何实现？

Wrap all component decrements in a single database transaction: for each component SKU, issue the conditional UPDATE … WHERE available >= qty; if any UPDATE returns 0 rows affected, roll back the entire transaction and return "sold out" for the bundle. This gives all-or-nothing atomicity — no partial decrements leak. For cross-shard bundles (components on different shop_id shards), use a two-phase commit or, more practically, a saga with explicit compensation: decrement each component in sequence, and if any step fails, issue compensating increments for the already-decremented ones, all recorded in the ledger with reason='bundle_rollback'.将所有组件扣减包裹在单个数据库事务中：对每个组件 SKU 发出条件 UPDATE … WHERE available >= qty；如果任何 UPDATE 返回影响 0 行，回滚整个事务并返回捆绑包"售罄"。这提供全有或全无的原子性——不会有部分扣减泄漏。对于跨分片捆绑包（组件在不同 shop_id 分片上），使用两阶段提交，或更实用地，使用带显式补偿的 saga：按顺序扣减每个组件，如果任何步骤失败，对已扣减的组件发出补偿增量，全部以 reason='bundle_rollback' 记录在流水账中。

Multi-location: which location fulfills an online order, and how is that decided?多仓库：线上订单由哪个仓库履约，如何决定？

An allocation service runs a ranked policy at order placement time: (1) filter locations that have available >= qty; (2) score by proximity to the shipping address, shipping cost, and merchant-configured priority; (3) pick the highest-scoring location and immediately create a reservation against that specific location_id. The allocation decision is recorded in the order so it is durable. If the chosen location's stock drops to zero before the reservation commits (race with another order), the reservation attempt returns 0 rows — the allocator re-runs and picks the next best location. This keeps the reservation path identical to the single-location case; allocation is just a pre-step that selects the target.分配服务在下单时运行排名策略：(1) 过滤 available >= qty 的仓库位置；(2) 按与收货地址的距离、运费和商家配置的优先级打分；(3) 选择得分最高的位置并立即针对该特定 location_id 创建预留。分配决策记录在订单中以保证持久性。如果所选位置的库存在预留提交前降为零（与其他订单竞争），预留尝试返回 0 行——分配器重新运行并选择次优位置。这使预留路径与单仓库情况完全一致；分配只是选择目标的预处理步骤。

⭐ Staff-level summary — say these thingsStaff 级总结——面试时必说这些
  1. Correctness lives in the conditional SQL decrement — the DB is the arbiter; Redis is a fast display cache, not a source of truth for committed stock.正确性在于条件 SQL 扣减——DB 是仲裁者；Redis 是快速展示缓存，不是已承诺库存的真相来源。
  2. Model the three counters explicitly — on_hand / committed / reserved with available derived; conflating them loses auditability and makes reconciliation impossible.显式建模三个计数器——on_hand / committed / reserved，available 派生；混淆它们会丢失可审计性并使对账不可能。
  3. The ledger is the audit truth; the level table is a materialized view — never update a ledger row; if they drift, the ledger wins and you file a bug.流水账是审计真相；level 表是物化视图——永远不要更新流水账行；如果漂移，流水账获胜，你提一个 bug。
  4. Cache + CDC for read scale — 500k QPS of PDP reads never touch SQL; Redis + CDC invalidation serves them in microseconds.缓存 + CDC 扛读取规模——50 万 QPS 的 PDP 读取永远不触碰 SQL；Redis + CDC 失效在微秒内服务它们。
  5. Degrade to "sold out" gracefully, never oversell — when the conditional UPDATE returns 0 rows, the right answer is a clean "just sold out" response, not a retry loop that burns the system. The loser gets a graceful rejection, not a corrupted order.优雅降级为"售罄"，绝不超卖——当条件 UPDATE 返回 0 行时，正确答案是干净的"刚刚售罄"响应，而不是烧毁系统的重试循环。失败方获得优雅拒绝，而不是损坏的订单。
