🔥 Flash Sale / BFCM抢购 / 黑五尖峰

full →完整 →

Problem: 1,000 units, 1M buyers, sells out in 10s — never oversell, don't melt the rest of Shopify.问题:1000 件商品、100 万买家、10 秒售罄 —— 绝不超卖,且不能拖垮 Shopify 其它部分。

⭐ Must-hit points必讲重点
  • Shed at the cheapest layer — kill the herd at the edge (virtual waiting room), meter a thin admitted stream; do NOT scale checkout 1000×.在最便宜的层卸流 —— 在边缘用虚拟等候室拦住人潮,只放出一条细流;不要把结账扩容 1000 倍。
  • Defense in depth on "never oversell": Redis atomic DECRBY gate (fast) + DB conditional UPDATE … WHERE qty_sold < total (durable truth) + reconciliation (catches drift).纵深防御防超卖:Redis 原子 DECRBY 闸门(快) + 数据库条件更新 WHERE qty_sold < total(持久的真相) + 对账(发现漂移)。
  • Name the Redis durability gap — DB is authoritative; Redis is a fast front gate that can only over-reject, never oversell.主动点出 Redis 的持久性缺口 —— 数据库才是权威;Redis 只是快速前置闸门,最多多拒绝,绝不会超卖。
  • Isolate the sale — dedicated fleet/pod + kill switch so one drop can't hurt two million other merchants.隔离这场抢购 —— 专用机群/pod + 熔断开关,一场抢购不能影响其它两百万商家。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: reserve-then-pay (needs TTL release) vs pay-then-decrement. Follow-up: Redis dies mid-sale? strict FIFO fairness?权衡:先预留后付款(需 TTL 释放) vs 先付款后扣减。追问:抢购中途 Redis 挂了怎么办?要严格 FIFO 公平吗?

📦 Global Inventory全局库存

full →完整 →

Problem: stock across many locations & channels; never oversell, stay available, near-real-time.问题:跨多仓库、多渠道的库存;绝不超卖、保持可用、近实时。

⭐ Must-hit points必讲重点
  • Model three counters: available = on_hand − committed − reserved (not one number).用三个计数器建模:可售 = 在库 − 已承诺 − 已预留(不是单一数字)。
  • Correctness lives in the conditional decrement: UPDATE … WHERE available ≥ 1 (optimistic concurrency); the DB is the arbiter.正确性在于条件扣减:UPDATE … WHERE available ≥ 1(乐观并发);数据库是裁判。
  • Append-only ledger = audit truth; the inventory level is a materialized view you can rebuild & reconcile.只追加的流水账 = 审计真相;库存数量是可重建、可对账的物化视图。
  • Read scale via cache + CDC invalidation; degrade to "sold out" gracefully, never oversell.用缓存 + CDC 失效扛读取;优雅降级为"已售罄",绝不超卖。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: optimistic vs pessimistic locking; strong (own checkout) vs eventual (marketplaces). Follow-up: two channels sell the last unit at the same instant?权衡:乐观 vs 悲观锁;强一致(自家结账) vs 最终一致(第三方平台)。追问:两个渠道同一刻卖出最后一件怎么办?

3

💳 Checkout & Payments结账与支付

full →完整 →

Problem: multi-region, idempotent checkout that survives a payment-gateway outage and never double-charges.问题:多区域、幂等的结账,能扛住支付网关故障,绝不重复扣款。

⭐ Must-hit points必讲重点
  • Idempotency key end-to-end (client → us → PSP): store key + request hash + response; retries return the stored result, never re-charge.幂等键贯穿全链路(客户端 → 我们 → 支付商):存键 + 请求哈希 + 响应;重试返回已存结果,绝不再扣款。
  • Order = durable source of truth; payment = state machine (INITIATED→AUTHORIZED→CAPTURED…).订单 = 持久真相;支付 = 状态机(发起→授权→扣款…)。
  • Outbox pattern eliminates the dual-write problem: write order + event in one TX, relay publishes to Kafka.Outbox 模式消除双写问题:订单 + 事件在同一事务写入,由中继发布到 Kafka。
  • Saga with explicit compensation; treat the PSP as unreliable — circuit-break, failover, reconcile.Saga + 显式补偿;把支付商当作不可靠依赖 —— 熔断、切备用、对账。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: orchestration vs choreography saga; sync vs async capture. Follow-up: network timed out after we called the PSP — did the charge go through?权衡:编排式 vs 协同式 saga;同步 vs 异步扣款。追问:调用支付商后网络超时 —— 到底扣没扣?

🏢 Multi-Tenant (Pods)多租户(Pods)

full →完整 →

Problem: millions of shops on shared infra — shard, isolate, move a shop with zero downtime.问题:数百万店铺共享基础设施 —— 分片、隔离、零停机迁移店铺。

⭐ Must-hit points必讲重点
  • Shard by shop_id; group shards into self-contained pods (app+DB+Redis) for blast-radius isolation.按 shop_id 分片;把分片打包成自包含的 pod(应用+库+Redis),实现爆炸半径隔离。
  • Routing brain = a highly-available, edge-cached shard map (shop → shard → pod).路由大脑 = 高可用、边缘缓存的分片表(shop → shard → pod)。
  • Online shop move = copy → replay change-log → verify → atomically flip the map.在线迁移店铺 = 复制 → 重放变更日志 → 校验 → 原子切换分片表。
  • Protect against noisy neighbors with per-shop quotas; keep the hot path single-shard; push cross-tenant queries to a derived store.用按店配额防"吵闹邻居";热路径保持单分片;跨租户查询交给派生存储。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: shared-table vs schema vs shard-per-group; central lookup vs hash routing. Follow-up: a whale merchant outgrows one shard?权衡:共享表 vs 独立 schema vs 分片分组;中心查表 vs 哈希路由。追问:巨型商家撑爆单个分片怎么办?

🛒 Shopping Cart购物车

full →完整 →

Problem: carts for anonymous + logged-in users, merged on login, available during spikes.问题:匿名 + 登录用户的购物车,登录时合并,尖峰期保持可用。

⭐ Must-hit points必讲重点
  • A cart is AP, not money-critical — favor availability; degrade gracefully under load.购物车是 AP、非金钱关键 —— 优先可用性;高负载下优雅降级。
  • KV single-document storage (Redis/DynamoDB) keyed by cart_id — high write, ephemeral, single-key access.用 KV 单文档存储(Redis/DynamoDB),按 cart_id 取 —— 高写入、易失、单键访问。
  • Merge on login with explicit conflict rules (sum quantities, cap, dedupe).登录时合并并定义明确冲突规则(数量相加、设上限、去重)。
  • Never reserve inventory in the cart — snapshot price for display, re-validate price & stock at checkout. TTL + abandonment events.购物车里绝不预留库存 —— 加购时快照价格用于展示,结账时重新校验价格与库存。TTL + 弃购事件。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: AP vs CP; LWW vs versioned concurrency. Follow-up: item out of stock / price changed at checkout?权衡:AP vs CP;最后写入获胜 vs 版本化并发。追问:结账时缺货 / 价格变了怎么办?

🔎 Search & Catalog搜索与目录

full →完整 →

Problem: per-store search with facets, typo tolerance, near-real-time index updates; extreme size skew.问题:按店搜索,带分面、纠错、近实时索引更新;店铺规模极度倾斜。

⭐ Must-hit points必讲重点
  • Decouple indexing from writes via CDC/outbox → Kafka → indexer → search engine (bulk upsert).用 CDC/outbox 把索引与写入解耦 → Kafka → 索引器 → 搜索引擎(批量 upsert)。
  • Shared index + shop routing/filter; give whale merchants a dedicated index. Don't index-per-tiny-shop.共享索引 + 按店路由/过滤;给巨型商家独立索引。别给每个小店都开一个索引。
  • Near-real-time freshness is a deliberate eventual-consistency choice (seconds), acceptable for storefront.近实时新鲜度是有意为之的最终一致(秒级),店面可接受。
  • Alias-swap for zero-downtime reindex; relevance = BM25 + business boosts (in-stock, bestsellers).用别名切换实现零停机重建索引;相关性 = BM25 + 业务加权(有货、热销)。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: index-per-tenant vs shared; freshness vs cost. Follow-up: a just-edited product not showing; reindex with a mapping change?权衡:每租户独立索引 vs 共享;新鲜度 vs 成本。追问:刚改的商品搜不到;改了 mapping 要重建索引怎么办?

🔗 Webhook DeliveryWebhook 投递

full →完整 →

Problem: deliver order/inventory events to thousands of third-party apps — at-least-once, retries, DLQ.问题:把订单/库存事件投递给数千个第三方应用 —— 至少一次、重试、死信队列。

⭐ Must-hit points必讲重点
  • At-least-once + subscriber idempotency (dedupe by webhook id) is the honest contract — exactly-once over HTTP is impractical.至少一次 + 订阅方幂等(按 webhook id 去重)才是诚实的契约 —— HTTP 上做精确一次不现实。
  • Isolate per endpoint (per-destination queues + circuit breaker) to kill head-of-line blocking from one dead subscriber.按端点隔离(每目的地队列 + 熔断器),消除单个挂掉的订阅方造成的队头阻塞。
  • Backoff + jitter retries, capped → DLQ with replay from a dashboard.退避 + 抖动重试,有上限 → 进 DLQ,可从面板重放。
  • Sign with HMAC + replay protection; partition for ordering only where needed; buffer & autoscale for storms with per-tenant fairness.用 HMAC + 防重放签名;仅在需要处用分区保序;事件风暴时缓冲 + 自动扩容并保证按租户公平。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: per-endpoint vs shared queue; push vs pull. Follow-up: subscriber down for hours; guarantee order.created before order.updated?权衡:每端点队列 vs 共享队列;推 vs 拉。追问:订阅方宕机数小时;如何保证 order.created 先于 order.updated?

🚦 Rate Limiting限流

full →完整 →

Problem: per-tenant limits for REST + GraphQL (cost-based) — fair, distributed, cheap to check.问题:对 REST + GraphQL(按成本)做按租户限流 —— 公平、分布式、检查开销低。

⭐ Must-hit points必讲重点
  • Token / leaky bucket for smoothing (allows bursts); pick the algorithm consciously (vs fixed/sliding window).令牌桶 / 漏桶做平滑(允许突发);有意识地选算法(对比固定/滑动窗口)。
  • GraphQL = cost-based: one query can be arbitrarily expensive, so debit a points bucket by computed query cost.GraphQL 用按成本:单个查询可能任意昂贵,因此按计算出的查询成本从点数桶扣减。
  • Atomic Lua in centralized Redis; shard by client to handle the hot key.集中式 Redis + 原子 Lua;按客户端分片应对热点 key。
  • Make the fail-open vs fail-closed decision explicit (usually fail-open with a conservative local cap); always return Retry-After.明确失败放行 vs 失败拒绝(通常失败放行 + 本地保守上限);始终返回 Retry-After。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: accuracy vs cost; centralized vs local. Follow-up: Redis outage — open or closed? estimating GraphQL cost accurately?权衡:精确度 vs 开销;集中 vs 本地。追问:Redis 挂了 —— 放行还是拒绝?如何准确估算 GraphQL 成本?

🔔 Notifications通知系统

full →完整 →

Problem: order confirmations & alerts across email/SMS/push — templated, deduped, multi-provider, deliverable at spike.问题:跨邮件/短信/推送的订单确认与提醒 —— 模板化、去重、多供应商、尖峰可达。

⭐ Must-hit points必讲重点
  • Async queue absorbs spikes & decouples producers from providers; the real cap is provider rate limits.异步队列吸收尖峰并解耦生产者与供应商;真正的瓶颈是供应商速率上限。
  • dedupeKey → effectively-once (a retried order event must not email twice).dedupeKey → 实际一次(重试的订单事件不能发两封邮件)。
  • Multi-provider failover with circuit breakers; reconcile delivery status via provider webhooks.多供应商故障切换 + 熔断器;通过供应商回调对账投递状态。
  • Priority lanes (transactional > marketing); preferences & compliance (opt-out, quiet hours) are first-class.优先级队列(事务类 > 营销类);用户偏好与合规(退订、免打扰时段)是一等公民。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: single vs multi-provider; priority queues vs one queue. Follow-up: provider outage; don't send "shipped" before "confirmed"?权衡:单 vs 多供应商;优先级队列 vs 单队列。追问:供应商宕机;如何避免"已发货"早于"已确认"?

📊 Real-time Analytics实时分析

full →完整 →

Problem: live per-store dashboards — ingest the order/pageview firehose, aggregate, serve sub-second queries.问题:每店实时看板 —— 摄入订单/浏览的洪流,聚合,提供亚秒级查询。

⭐ Must-hit points必讲重点
  • Pick consistency per metric: exact revenue (exactly-once + idempotent writes) vs approximate unique visitors (HyperLogLog).按指标选一致性:精确营收(精确一次 + 幂等写入) vs 近似独立访客(HyperLogLog)。
  • Kappa (stream + replay) beats Lambda's dual code paths for corrections.做纠错时,Kappa(流 + 重放)优于 Lambda 的双套代码。
  • OLAP columnar store (ClickHouse/Druid/Pinot) for sub-second multi-tenant group-by; pre-aggregate rollups.OLAP 列式存储(ClickHouse/Druid/Pinot)做亚秒级多租户分组聚合;预聚合 rollup。
  • Watermarks + grace for late/out-of-order events; replay the log to recompute after a bug; tier hot/cold for cost.用水位线 + 宽限期处理迟到/乱序事件;出 bug 后重放日志重算;冷热分层控成本。
Core trade-off / Top follow-up核心权衡 / 高频追问

Trade-off: exact vs approximate; lambda vs kappa; pre-agg vs query-time. Follow-up: a late event updates an already-served window?权衡:精确 vs 近似;lambda vs kappa;预聚合 vs 查询时聚合。追问:迟到事件要更新已经返回过的时间窗怎么办?
