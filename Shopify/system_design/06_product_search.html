Component walk-through组件详解

  • Catalog Service — writes product mutations to MySQL and an outbox table atomically (same transaction). Synchronous indexing is intentionally not on this path; it would couple write latency to search cluster health. — 以原子方式（同一事务）将商品变更写入 MySQL 和 outbox 表。刻意不在此路径上进行同步索引，否则会将写入延迟与搜索集群健康状态耦合。
  • Debezium / outbox relay — reads the MySQL binlog (or polls the outbox table) and publishes change events to Kafka. Decouples the write path completely from the indexing pipeline. — 读取 MySQL binlog（或轮询 outbox 表）并将变更事件发布到 Kafka，将写入路径与索引管道完全解耦。
  • Kafka — durable, ordered event buffer. Partitioned by shop_id so all events for one shop arrive in order, preventing a later event from overwriting a newer document. — 持久有序的事件缓冲区。按 shop_id 分区，确保同一店铺的所有事件按序到达，防止旧事件覆盖更新的文档。
  • Indexer Fleet — stateless consumers. Fetch full denormalized documents (joining variants, options, collections), then bulk-upsert into the search cluster. Scales independently of the write and query paths. — 无状态消费者。获取完整的反规范化文档（关联变体、选项、系列），然后批量 upsert 到搜索集群。可独立于写入和查询路径进行扩缩容。
  • Search Cluster — Elasticsearch or OpenSearch. Queries arrive with _routing=shop_id so they hit the right shard(s) directly rather than scatter-gathering across the whole cluster. — Elasticsearch 或 OpenSearch。查询携带 _routing=shop_id，直接命中对应分片，避免在整个集群上进行 scatter-gather。
  • Search Service — translates the API query into a search DSL query + aggregations, handles relevance boosting, applies shop-level synonym and pinning configuration, then merges facet counts with hits. — 将 API 查询转换为搜索 DSL 查询 + 聚合，处理相关性加权，应用店铺级同义词和置顶配置，然后将分面计数与命中结果合并。
  • Redis Query Cache — caches the top query responses per shop for a short TTL (~5 s). Absorbs burst traffic on popular storefront pages without hitting the search cluster per request. — 以短 TTL（约 5 秒）缓存每个店铺的热门查询响应，吸收热门店铺页面的突发流量，无需每次请求都打到搜索集群。
  • CDN / Edge Cache — caches search response payloads for frequently repeated queries (e.g., browse-page results with no free-text query). Effective for collection browsing; less so for unique user queries. — 缓存频繁重复查询的搜索响应内容（如无自由文本查询的浏览页结果）。对系列浏览有效；对唯一用户查询效果较弱。

① Why a search engine, not SQL LIKE① 为什么用搜索引擎而非 SQL LIKE

A naive WHERE title LIKE '%running shoe%' performs a full table scan on every query — no index can help a leading wildcard. It cannot rank results (no scoring function), does not handle typos, and produces no facet counts without expensive sub-queries. An inverted index maps each analyzed term to the list of documents containing it; a query against even a billion products is a set intersection plus a BM25 scoring sort, completing in milliseconds.简单的 WHERE title LIKE '%running shoe%' 每次查询都要全表扫描——前缀通配符无法利用任何索引。它无法对结果排序（没有评分函数），无法处理拼写错误，且不经高代价子查询无法产生分面计数。倒排索引将每个分析后的词项映射到包含它的文档列表；即使对十亿件商品的查询，也只是集合求交加 BM25 评分排序，毫秒级完成。

② Indexing pipeline and freshness② 索引管道与新鲜度

The CDC/outbox pattern decouples the write path from the indexing path: merchants see immediate confirmation of their save, while the index update propagates asynchronously. The pipeline provides seconds-level freshness under normal load because Kafka lag on a healthy cluster is typically under one second.CDC/outbox 模式将写入路径与索引路径解耦：商家保存操作可立即得到确认，索引更新则异步传播。在正常负载下，健康集群的 Kafka 滞后通常低于一秒，因此管道可提供秒级新鲜度。

Key design points for the indexer:Indexer 的关键设计要点：

  • Ordered delivery per shop按店铺有序投递: Kafka partitioning by shop_id ensures events for a product arrive in sequence. An out-of-order update could overwrite a newer document with an older one.：Kafka 按 shop_id 分区，确保商品事件按序到达。乱序更新可能用旧文档覆盖更新的文档。
  • Denormalize at index time索引时反规范化: the indexer fetches variants and collections from MySQL (or a read replica) to build the full document. This is heavier than streaming just the changed row but keeps the search document complete.：Indexer 从 MySQL（或只读副本）获取变体和系列以构建完整文档。虽比仅流式传输变更行代价更高，但能保持搜索文档完整。
  • Bulk upsert批量 upsert: Elasticsearch's _bulk API amortizes HTTP overhead; the indexer micro-batches events for ~200 ms before flushing.：Elasticsearch 的 _bulk API 摊销 HTTP 开销；Indexer 将事件微批累积约 200 ms 后再刷写。
  • Deletes and archiving删除与归档: when a product is deleted or set to draft, the indexer issues a delete by document ID. The index filter on status=active also handles it as a query-time filter, providing defense in depth.：商品被删除或设为 draft 时，Indexer 按文档 ID 发出删除请求。status=active 的索引过滤器也作为查询时过滤器处理此情况，提供纵深防御。
Index lag is an intentional eventual-consistency trade-off索引滞后是有意为之的最终一致性权衡 A product the merchant just saved may not appear in search results for 2–5 seconds. This is acceptable for storefront search — buyers are unlikely to search for a product in the same second the merchant publishes it. If the SLA were stricter (sub-second), you would need synchronous dual-write to the search cluster, which couples write availability to the search cluster's health — a bad trade-off for most shops.商家刚保存的商品可能在 2–5 秒内不会出现在搜索结果中。对于店铺搜索而言这是可接受的——买家不太可能在商家发布商品的同一秒就搜索它。若 SLA 更严格（亚秒级），则需要对搜索集群进行同步双写，这会将写入可用性与搜索集群健康状态耦合——对大多数店铺而言是不划算的权衡。

④ Faceting and filtering④ 分面与筛选

Faceted search returns not just the matching products but also the count of matches per facet value (e.g., "Nike (42), Adidas (17)"). In Elasticsearch this is a single request: a query combined with aggregations. The aggregations run over the post-filter result set and produce bucket counts.分面搜索不仅返回匹配的商品，还返回每个分面值的匹配数量（如"Nike (42), Adidas (17)"）。在 Elasticsearch 中，这是单次请求：查询与聚合组合。聚合在后过滤结果集上运行并生成桶计数。

Performance concerns with faceting:分面的性能注意事项：

  • High-cardinality facets高基数分面 (e.g., unique price values, free-form tags) produce expensive terms aggregations. Mitigate by capping the result at top-N values, or by using numeric_range aggregation for price buckets.（如唯一价格值、自由格式标签）会产生高代价的 terms 聚合。可通过限制结果为 top-N 值，或对价格区间使用 numeric_range 聚合来缓解。
  • Global facets vs. post-filter facets全局分面 vs. 后过滤分面: when a user selects a facet value (e.g., "Vendor: Nike"), you typically want the other facet counts to reflect the full query without the vendor filter, so the buyer can see how many Adidas items also match. Elasticsearch's global aggregation or post-filter pattern handles this.：当用户选择一个分面值（如"供应商：Nike"）时，通常希望其他分面计数反映不带供应商过滤器的完整查询，以便买家看到有多少 Adidas 商品也匹配。Elasticsearch 的 global 聚合或 post-filter 模式可处理此情况。
  • Caching facet counts缓存分面计数: the filter cache in Elasticsearch automatically caches frequent filter terms. Hot shops with repeated browse queries benefit heavily.：Elasticsearch 的过滤器缓存会自动缓存高频过滤词项。频繁浏览查询的热门店铺可大幅受益。

⑦ Indexing pipeline under load — absorbing a 100k-product bulk edit without lag spikes⑦ 高负载下的索引管道 —— 吸收 10 万件商品的批量编辑而不引发延迟峰值

A merchant who bulk-edits their entire catalog — updating prices before a sale, or changing vendor names — fires a flood of CDC events in seconds. The naive response of consuming every event as fast as possible creates two problems: (1) the Indexer overwhelms the Elasticsearch cluster with thousands of individual document writes, causing cluster-wide latency spikes that hurt all shops' query performance; (2) a single merchant's bulk job can monopolize Indexer throughput, starving neighboring shops of near-real-time updates for minutes.一个批量编辑整个目录的商家——在促销前更新价格，或修改供应商名称——会在数秒内触发大量 CDC 事件。对所有事件无差别地尽快消费会产生两个问题：(1) Indexer 以数千个单独文档写入淹没 Elasticsearch 集群，造成全集群延迟尖峰，影响所有店铺的查询性能；(2) 单个商家的批量任务可独占 Indexer 吞吐量，使相邻店铺在数分钟内无法享受近实时更新。

The solution combines three mechanisms: Kafka as a durable buffer, batched bulk upsert, and per-shop fairness.解决方案结合三种机制：Kafka 作为持久缓冲区、批量 bulk upsert，以及每店铺公平调度。

Write path never blocks on the index. The Catalog Service writes to MySQL and outbox — it has no knowledge of how backed-up the Indexer is. Kafka absorbs the 100k-event burst with zero back-pressure to the write path. The merchant's save operations complete at normal speed regardless of how long it takes to drain the Kafka lag.写入路径永远不会因索引而阻塞。Catalog Service 写入 MySQL 和 outbox——它完全不知道 Indexer 有多积压。Kafka 以零背压吸收 10 万事件的突发，对写入路径毫无影响。无论 Kafka 延迟需要多久才能消化完，商家的保存操作都以正常速度完成。

Batched bulk upsert amortizes Elasticsearch overhead. Rather than sending one HTTP request per event, the Indexer accumulates events for a micro-batch window (~200 ms) or up to a maximum batch size (~500 documents) and flushes them in a single _bulk API call. Elasticsearch's bulk API is significantly cheaper per-document than individual index requests: it reduces HTTP connection overhead, allows the shard to merge segments less often, and batches the internal WAL write. At 50k events/sec, micro-batching reduces the number of Elasticsearch requests by 100×.批量 bulk upsert 摊销 Elasticsearch 开销。Indexer 不是每个事件发送一个 HTTP 请求，而是在微批时间窗口（约 200 ms）或达到最大批量大小（约 500 个文档）时积累事件，然后通过单次 _bulk API 调用刷写。Elasticsearch 的 bulk API 相比单独索引请求，每文档成本显著更低：减少 HTTP 连接开销、减少分片段合并频率，以及批量执行内部 WAL 写入。在 5 万事件/秒下，微批处理将 Elasticsearch 请求数量减少 100 倍。

Per-shop fairness prevents one bulk job from starving neighbors. Kafka is partitioned by shop_id, so events for each shop arrive on a dedicated partition. The Indexer assigns one consumer thread per partition. Inside each consumer, apply a token-bucket rate limit per shop: cap any single shop to at most some percentage of total bulk throughput per time window. A shop bursting 100k updates will have its events queued in Kafka (growing consumer lag for that shop) while neighboring shops on other partitions continue consuming at normal speed — fully independent goroutines/threads. The bulk-editing shop's lag drains steadily in the background, typically completing in minutes, while the freshness SLO for the rest of the platform is unaffected.每店铺公平调度防止一个批量任务饿死邻居。Kafka 按 shop_id 分区，因此每个店铺的事件到达专属分区。Indexer 为每个分区分配一个消费线程。在每个消费者内部，应用每店铺令牌桶限速：将任意单个店铺在时间窗口内的批量吞吐量上限设为总量的某个百分比。批量编辑 10 万件商品的店铺，其事件将在 Kafka 中排队（该店铺的消费者延迟增加），而其他分区上的相邻店铺继续以正常速度消费——完全独立的 goroutine/线程。批量编辑店铺的延迟在后台平稳消化，通常在数分钟内完成，而平台其余部分的新鲜度 SLO 不受影响。

Monitor consumer lag as the freshness SLO. Kafka consumer group lag (messages behind the latest offset) is the leading metric for indexing freshness. A healthy cluster maintains lag < a few hundred messages (sub-second delivery). A spike in lag for one shop partition signals a bulk edit in progress — expected and acceptable. A rising lag across all partitions signals an Indexer or Elasticsearch capacity problem requiring paging.监控消费者延迟作为新鲜度 SLO。Kafka 消费者组延迟（落后最新偏移量的消息数）是索引新鲜度的领先指标。健康集群保持延迟低于几百条消息（亚秒级传递）。单个店铺分区的延迟尖峰表示正在处理批量编辑——这是预期的、可接受的。所有分区延迟同时上升则表示 Indexer 或 Elasticsearch 容量问题，需要告警处理。

# Indexer consumer loop — per Kafka partition (one goroutine/thread per shop shard)
func consumePartition(partition, shopBucket):
  batch = []
  for msg in partition.poll(maxWaitMs=200, maxRecords=500):
    # per-shop token bucket: skip / re-queue if this shop is over its rate quota
    if not shopBucket[msg.shopId].consume(1):
      partition.seek(msg.offset)   # back-pressure: re-read this message next loop
      break
    doc = denormalize(msg)          # fetch variants + collections from read replica
    batch.append({"index": {"_id": doc.productId, "routing": doc.shopId}}, doc)

  if batch:
    resp = es.bulk(body=batch)      # single _bulk call — amortizes HTTP + WAL overhead
    for item in resp.errors:
      deadLetterQueue.send(item)    # mapping conflicts, circuit-breaker trips → DLQ
    partition.commit()              # only commit after successful flush
Why decoupling indexing from the write path keeps both fast将索引与写入路径解耦为何能让两者都保持高速

If the Indexer wrote synchronously on the Catalog Service's write path, a slow Elasticsearch cluster or a large bulk edit would directly inflate merchant save latency — even though the merchant only cares that their data is durably stored in MySQL. By using Kafka as the decoupling layer, the write path's performance is bounded only by MySQL write speed, and the Indexer's performance is bounded only by Elasticsearch throughput. The two can be scaled, tuned, and degraded entirely independently. This is the architectural insight that makes seconds-level search freshness achievable at 50k mutation events per second without compromising write availability.如果 Indexer 在 Catalog Service 的写入路径上同步写入，Elasticsearch 变慢或大批量编辑会直接拉高商家保存延迟——尽管商家只关心数据被持久化到 MySQL。通过使用 Kafka 作为解耦层，写入路径的性能仅受 MySQL 写入速度约束，Indexer 的性能仅受 Elasticsearch 吞吐量约束。两者可以完全独立地进行扩缩容、调优和降级。这是在 5 万事件/秒的变更速率下实现秒级搜索新鲜度、同时不损害写入可用性的关键架构洞察。

Option A · Index-per-shop方案 A · 每店铺独立索引

② Index freshness strategy — async CDC vs synchronous dual-write② 索引新鲜度策略 —— 异步 CDC vs 同步双写

The tension: when a merchant saves a product, when does the change appear in search results? You can make the write path also write to the search cluster synchronously, or you can let an async pipeline carry the update seconds later.矛盾点：商家保存商品后，变更何时出现在搜索结果中？可以在写入路径上同步写入搜索集群，也可以通过异步管道在数秒后传递更新。

Option A · Async CDC / Kafka pipeline方案 A · 异步 CDC / Kafka 管道

The Indexer fleet consumes and bulk-upserts into Elasticsearch — typically completing in under 5 seconds end-to-end.Catalog Service 原子地写入 MySQL 和 outbox。Debezium 读取 binlog 并发布到 Kafka。Indexer 集群消费并批量 upsert 到 Elasticsearch——通常端到端在 5 秒内完成。

+ Write path never blocks on search cluster health; the search cluster can be slow, reindexing, or restarted without affecting merchant saves; Kafka buffers spikes (e.g., a 100k-product bulk edit) without back-pressuring the write path.+ 写入路径永远不会因搜索集群健康状态而阻塞；搜索集群无论慢速、重建索引还是重启，都不影响商家保存；Kafka 缓冲突发（如 10 万件商品的批量编辑），不对写入路径产生背压。

On every product save, the Catalog Service writes to MySQL and calls the Elasticsearch bulk API in the same request lifecycle.每次商品保存时，Catalog Service 在同一请求生命周期内同时写入 MySQL 和 调用 Elasticsearch bulk API。

+ Near-instant freshness (sub-second); simple conceptually — the write path owns the update end-to-end.+ 近乎即时的新鲜度（亚秒级）；概念上简单——写入路径端到端拥有更新。

④ Inventory in the search index — denormalized flag vs real-time join④ 搜索索引中的库存 —— 反规范化标志 vs 实时关联

− CDC lag means up to ~5 seconds of staleness — a sold-out product may still appear as in-stock briefly, and a newly restocked product may stay hidden slightly too long.− CDC 延迟意味着最多约 5 秒的过时——已售罄商品可能短暂仍显示为有货，新补货商品可能略微延迟才出现。

When to use which何时用哪个

Store in the index with near-real-time CDC updates as the default. For storefront search, a 5-second lag on the in-stock flag is acceptable — buyers rarely search for a product in the exact second it sells out. Option A · Per-merchant relevance config方案 A · 每商家独立相关性配置

+ Maximum relevance quality — a vertically specialized catalog can surface the signals that matter most to its buyers.+ 最高相关性质量——垂直专业目录能够突出对其买家最重要的信号。

− Configuration explosion at millions of merchants; ML models need enough query volume to train (useless for small shops); operational complexity of storing and applying per-tenant search configs at query time.− 在数百万商家规模下配置爆炸；ML 模型需要足够的查询量才能训练（对小店铺无用）；在查询时存储和应用每租户搜索配置的运维复杂度高。

Option B · Global BM25 + per-merchant boost_score方案 B · 全局 BM25 + 每商家可写 boost_score

Base ranking uses a single global BM25 configuration. Merchants can inject additive boosts on individual products via a boost_score field in the index document, allowing pinning and demoting without touching the ranking model itself.基础排序使用单一全局 BM25 配置。商家可通过索引文档中的 boost_score 字段为单个商品注入加法加权，无需修改排序模型本身即可置顶和降权。

+ Single search config to tune and monitor; boost fields are just document data, so merchants can update them via the admin UI without any indexer changes; works well for 99% of shops.+ 单一搜索配置便于调优和监控；加权字段只是文档数据，商家可通过管理界面更新，无需任何 Indexer 变更；适用于 99% 的店铺。

− Niche verticals (e.g., a shop selling musical scores where opus number is critical) may see suboptimal relevance; cannot surface domain-specific signals without custom field weights.− 垂直细分领域（如乐谱店，作品编号至关重要）可能看到次优的相关性；没有自定义字段权重无法突出领域特定信号。

When to use which何时用哪个

Start with global BM25 + merchant-writable boosts. The boost field already covers the most impactful merchant customization (pinning heroes, demoting clearance). Offer full per-merchant relevance config as a premium feature gated behind catalog size or plan tier — it is operational complexity that only whale merchants with dedicated teams can actually leverage.从全局 BM25 + 商家可写加权开始。加权字段已覆盖最有影响力的商家自定义（置顶主推商品、降权清仓商品）。将完整的每商家相关性配置作为高级功能，按目录规模或计划级别设门槛——这是只有拥有专属团队的巨型商家才能真正利用的运维复杂度。

⑥ Reindex strategy — in-place mapping update vs blue/green alias swap⑥ 重建索引策略 —— 原地映射更新 vs 蓝绿别名切换

The tension: mapping changes (new field, changed analyzer, new scoring field) require reindexing. Do you update the live index in place, or build a new index alongside the old one and flip traffic over atomically?矛盾点：映射变更（新字段、修改分析器、新评分字段）需要重建索引。是原地更新线上索引，还是在旧索引旁构建新索引并原子切换流量？

Option A · In-place mapping update方案 A · 原地映射更新

PUT a new mapping onto the live index, then run _update_by_query or the reindex API against the same index.对线上索引 PUT 新映射，然后对同一索引运行 _update_by_query 或 reindex API。

+ Simpler — one index, no alias management, no dual-write window.+ 更简单——单一索引，无别名管理，无双写窗口。

− Elasticsearch may reject incoming documents that do not match the new mapping until all existing documents are updated — creating a silent data loss window; the reindex operation competes with live query traffic for cluster resources, causing latency spikes; impossible to validate the new mapping against a shadow index before exposing it to buyers.− Elasticsearch 可能在所有现有文档更新完成之前拒绝不符合新映射的入站文档——造成静默数据丢失窗口；重建索引操作与线上查询流量竞争集群资源，引发延迟尖峰；无法在向买家暴露新映射之前对影子索引进行验证。

Option B · Blue/green alias swap方案 B · 蓝绿别名切换

Create a new versioned index (products_v4), reindex data from the live index into it, enable dual-write in the Indexer during the transition, validate quality, then atomically swap the products alias to point to products_v4.创建新的带版本号索引（products_v4），从线上索引将数据 reindex 到其中，过渡期间在 Indexer 中启用双写，验证质量后原子性地将 products 别名指向 products_v4。

+ The alias flip is instantaneous and atomic — zero downtime; the new mapping is fully validated before any buyer sees it; rollback is trivial (flip alias back); the old index absorbs all reads until the swap.+ 别名切换瞬间完成且是原子操作——零停机；新映射在任何买家看到之前已完全验证；回滚简单（将别名切回）；切换前所有读取由旧索引承担。

− Temporarily doubles cluster storage; requires dual-write logic in the Indexer (a feature-flagged code path); alias management adds a small layer of indirection to routing.− 临时使集群存储翻倍；需要 Indexer 中的双写逻辑（功能开关控制的代码路径）；别名管理在路由上增加了一小层间接性。

When to use which何时用哪个

Always use the alias swap — never reindex in place under live traffic. The risk of silent data loss during an in-place reindex is real and hard to detect until a buyer notices missing products. The alias pattern is standard practice in every production Elasticsearch deployment. The short period of doubled storage cost is a small price for zero-downtime, zero-risk mapping changes.始终使用别名切换——绝不在线上流量下原地重建索引。原地重建过程中静默数据丢失的风险是真实存在的，且难以在买家发现商品缺失之前检测到。别名模式是每个生产 Elasticsearch 部署的标准实践。短暂的存储成本翻倍，换取零停机、零风险的映射变更，代价微小。

A merchant just saved a product and it does not appear in search results — how do you debug?商家刚保存了一件商品，但它未出现在搜索结果中——如何排查？

Work through the pipeline stages: (1) confirm the row exists in MySQL with the expected updated_at timestamp; (2) check the outbox table or Debezium connector lag — did the event publish to Kafka? (3) check Kafka consumer lag on the catalog.product.changes topic — is the indexer keeping up? (4) query the search cluster directly by document ID to see if the document is present and what its current field values are; (5) check indexer error logs for rejected bulk upsert requests (mapping conflicts, circuit-breaker trips). The most common root causes are: Debezium connector falling behind, indexer rejecting documents due to a mapping incompatibility, or the merchant editing a product in draft status (which is filtered from search).逐级排查管道各阶段：(1) 确认 MySQL 中该行存在且 updated_at 时间戳符合预期；(2) 检查 outbox 表或 Debezium 连接器延迟——事件是否发布到 Kafka？(3) 检查 catalog.product.changes topic 上的 Kafka 消费者延迟——Indexer 是否跟得上？(4) 直接通过文档 ID 查询搜索集群，确认文档是否存在及当前字段值；(5) 检查 Indexer 错误日志中被拒绝的 bulk upsert 请求（映射冲突、熔断器触发）。最常见的根本原因：Debezium 连接器滞后、Indexer 因映射不兼容拒绝文档，或商家编辑的商品处于 draft 状态（被搜索过滤）。

How do you perform a zero-downtime reindex when the mapping changes?映射变更时如何执行零停机重建索引？

Use the alias swap pattern described in the deep dive: create a versioned new index, run the reindex API to copy documents, enable dual-write in the indexer (all new CDC events go to both old and new indices during the transition), validate quality, then atomically swap the search alias. The alias flip is a metadata operation — it is instantaneous and search queries targeting the alias are redirected transparently. Disable dual-write and delete the old index after a confidence window of ~24 hours.使用深度分析中描述的别名切换模式：创建带版本号的新索引，运行 reindex API 复制文档，在 Indexer 中启用双写（过渡期间所有新 CDC 事件同时写入新旧两个索引），验证质量后原子性切换搜索别名。别名切换是元数据操作——瞬间完成，针对别名的搜索查询会透明重定向。约 24 小时置信窗口后禁用双写并删除旧索引。

A merchant has 5 million products — how do you handle their initial index build and ongoing operations?某商家有 500 万件商品——如何处理初始索引构建和持续运营？

For initial ingestion: provision a dedicated index for this merchant (skipping the shared index), run a bulk import job reading directly from MySQL with high parallelism (not through Kafka, which would serialize the load). The bulk import can use a higher refresh_interval (60 s instead of 1 s) and number_of_replicas: 0 during indexing, then restore replicas afterward. A 5M-product index takes ~1–2 hours at 2,000 docs/sec. Ongoing: the CDC pipeline routes their events to their dedicated index; reindex operations are scoped to their index only, not the shared cluster.初始导入：为该商家分配专属索引（跳过共享索引），直接从 MySQL 高并发读取并运行批量导入任务（不经 Kafka，否则会序列化负载）。批量导入期间可使用更高的 refresh_interval（60 秒而非 1 秒）和 number_of_replicas: 0，完成后再恢复副本。500 万商品的索引在 2,000 文档/秒的速度下约需 1–2 小时。持续运营：CDC 管道将其事件路由到专属索引；重建索引操作仅限于其索引，不影响共享集群。

How would you add ML-based personalized ranking?如何加入基于机器学习的个性化排序？

The canonical approach: train a Learning-to-Rank (LTR) model offline using click/purchase signals (query, product_id, position, clicked). Deploy it as a re-ranking layer: retrieve the top-100 candidates from the search cluster using BM25 + business boosts (fast), then apply the LTR model to re-rank them (using features like buyer history, seasonal signals, product recency). Elasticsearch has a native LTR plugin; alternatively run re-ranking in the Search Service. Key constraint: the first-stage retrieval must be fast and recall-high enough that the LTR stage is operating on a complete candidate set.标准方案：使用点击/购买信号（query、product_id、position、clicked）离线训练 Learning-to-Rank (LTR) 模型。将其部署为重排序层：先用 BM25 + 业务加权从搜索集群检索 top-100 候选（速度快），再应用 LTR 模型重排序（使用买家历史、季节性信号、商品新鲜度等特征）。Elasticsearch 有原生 LTR 插件；也可在 Search Service 中运行重排序。关键约束：第一阶段检索必须足够快且召回率足够高，确保 LTR 阶段在完整候选集上运行。

How do you handle multi-language storefronts?如何处理多语言店铺？

Each language requires its own analyzer (English uses the English stemmer; Japanese requires kuromoji tokenization; Arabic needs right-to-left handling). The document should store translated fields per locale: title_en, title_ja, etc. The search query targets the field for the active locale. Synonym dictionaries are also per-locale. At index time, the indexer fetches available translations from the translations service and indexes all locale-specific fields in one document. This avoids per-locale indices (which would multiply cluster size by the number of languages).每种语言需要独立的分析器（英语用英语词干分析器；日语需要 kuromoji 分词；阿拉伯语需要从右到左处理）。文档应按语言区域存储翻译字段：title_en、title_ja 等。搜索查询针对当前语言区域对应的字段。同义词词典也按语言区分。索引时，Indexer 从翻译服务获取可用翻译，在单个文档中索引所有语言区域字段。这避免了按语言区域建立独立索引（否则集群规模会随语言数量成倍增加）。

How do out-of-stock items get filtered without stale index data?如何在不依赖过时索引数据的情况下过滤缺货商品？

Inventory quantity changes are high-frequency (every sale updates a variant). The CDC pipeline captures these changes and the indexer updates the has_inventory boolean field. With a healthy pipeline, staleness is seconds. For storefronts that require exact in-stock filtering, add a lightweight join at query time: retrieve the top-N results from the search cluster (ignoring inventory), then hit the inventory service in a batched call to filter or re-rank based on live stock. This adds ~10–20 ms but is exactly accurate. The choice between these two approaches is a freshness vs. latency trade-off that should be discussed with the product team.库存数量变更频率很高（每次销售都会更新变体）。CDC 管道捕获这些变更，Indexer 更新 has_inventory 布尔字段。管道健康时，过时时长为秒级。对于需要精确库存过滤的店铺，可在查询时增加轻量级关联：从搜索集群检索 top-N 结果（忽略库存），然后批量调用库存服务根据实时库存过滤或重排序。这增加约 10–20 ms 但完全精确。两种方案的选择是新鲜度与延迟的权衡，应与产品团队讨论。

A merchant bulk-edits 100k products — how does the index keep up without lag spikes?商家批量编辑 10 万件商品时，索引如何保持同步而不出现延迟峰值？

Bulk edits produce a burst of CDC events that can overwhelm the indexer if consumed naively. The solution is a combination of buffering and fairness. Kafka naturally absorbs the burst; the indexer reads in micro-batches and uses the Elasticsearch _bulk API to amortize per-document overhead. Crucially, Kafka partitions by shop_id, and the indexer assigns one consumer thread per partition. To prevent one bulk-editing merchant from starving others sharing the same partition, implement per-shop token-bucket rate limiting or a weighted fair-queue inside the indexer: cap any single shop to at most N% of bulk throughput per window. This ensures a 100k-product edit is processed steadily in the background — finishing in minutes — while neighboring shops continue to receive near-real-time updates.批量编辑会产生 CDC 事件洪峰，若不加控制会淹没 Indexer。解决方案是缓冲与公平调度相结合。Kafka 天然吸收流量突增；Indexer 以微批方式消费并通过 Elasticsearch _bulk API 摊销单文档开销。关键在于：Kafka 按 shop_id 分区，Indexer 为每个分区分配一个消费线程。为防止一个大批量任务饿死同分区的其他商家，可在 Indexer 内部实现令牌桶限速或加权公平队列：将任意单个商家在时间窗口内的批量吞吐量上限设为总量的 N%。这样 10 万件商品的编辑任务将在后台平稳处理（约需数分钟），而其他商家仍能享受近实时的索引更新。

How do you implement "did you mean" / spell correction?如何实现"您是否要搜索"/ 拼写纠错功能？

Spell correction combines three signals. First, fuzzy matching (edit distance 1–2 via fuzziness: AUTO) catches common typos inline and requires no extra infrastructure. Second, Elasticsearch's phrase suggester compares the query against indexed terms and proposes the closest real term by edit distance — this produces classic "did you mean" suggestions. Third, and most effective for a large catalog, mine historical query logs: when a session with query "runing shoe" is followed by a correction to "running shoe" and a purchase, record that mapping. Aggregate these correction pairs into a learned correction dictionary and apply them as a query rewrite before the search executes. Popular-term suggestions (autocomplete-style) also naturally bias users toward well-spelled queries.拼写纠错结合三种信号。第一，模糊匹配（fuzziness: AUTO，编辑距离 1–2）可内联修正常见拼写错误，无需额外基础设施。第二，Elasticsearch 的 phrase suggester 将查询词与索引词对比，按编辑距离推荐最接近的真实词——产生经典的"您是否要搜索"提示。第三，也是最有效的方式：挖掘历史查询日志——当会话中"runing shoe"之后被纠正为"running shoe"并促成购买，就记录该映射。将这些纠错对汇聚成学习型纠错词典，在搜索执行前以查询重写的方式应用。热门词建议（自动补全）也会自然地引导用户输入拼写正确的词。

Where does personalized ranking per buyer live in the architecture?买家个性化排序在架构中处于哪个位置？

The search index is intentionally kept generic — it stores base relevance signals (BM25 scores, inventory status, merchant boosts) shared across all buyers of a shop. Personalization sits in a separate re-ranking layer between the search cluster and the response to the buyer. The flow is: (1) first-stage retrieval from Elasticsearch returns the top-100–500 candidates using fast BM25 + business boosts; (2) a lightweight re-ranker (running in the Search Service or a dedicated ranking service) applies per-user signals — purchase history, category affinity, session context — to re-order the candidates; (3) only the final top-N are returned to the buyer. Keeping the index shared means you avoid per-user index maintenance; all personalization state lives in a fast user-feature store (Redis or a feature platform) that the re-ranker reads at query time.搜索索引被有意保持通用——存储所有买家共享的基础相关性信号（BM25 分数、库存状态、商家加权）。个性化位于搜索集群与买家响应之间独立的重排序层。流程如下：(1) Elasticsearch 的第一阶段检索利用快速的 BM25 + 业务加权返回 100–500 个候选；(2) 轻量级重排序器（运行在 Search Service 或专用排序服务中）应用用户级信号——购买历史、品类偏好、会话上下文——对候选重新排序；(3) 仅将最终 top-N 返回给买家。保持索引共享意味着无需维护每用户索引；所有个性化状态存储在快速的用户特征存储（Redis 或特征平台）中，供重排序器在查询时读取。

How do you handle synonyms, including merchant-specific synonym dictionaries?如何处理同义词，包括商家自定义的同义词词典？

Synonyms can be applied at index time (the analyzer expands synonyms when indexing a document) or at query time (a synonym_graph token filter rewrites the query before it hits the inverted index). Query-time synonyms are strongly preferred for Shopify's use case: merchants can update their synonym dictionaries instantly without triggering a full reindex of their catalog. The global synonym dictionary (e.g., "sneaker ↔ trainer ↔ shoe") lives in a shared configuration store; each shop's overrides are stored per-shop and injected into the search request DSL dynamically by the Search Service. Multi-word synonyms (e.g., "t-shirt → tee shirt") require the synonym_graph filter rather than the simple synonym filter to correctly handle phrase tokenization.同义词可在索引时应用（分析器在索引文档时展开同义词），也可在查询时应用（synonym_graph token filter 在查询命中倒排索引前重写查询）。对于 Shopify 的场景，强烈推荐查询时同义词：商家可即时更新同义词词典，无需触发全量重建索引。全局同义词词典（如"sneaker ↔ trainer ↔ shoe"）存储在共享配置中心；每个商家的覆盖配置按商家存储，由 Search Service 在请求时动态注入搜索 DSL。多词同义词（如"t-shirt → tee shirt"）需使用 synonym_graph filter 而非简单的 synonym filter，以正确处理短语分词。

How do you support multi-language product catalogs?如何支持多语言商品目录？

Language-specific text analysis is the core requirement: the English analyzer (stemming, stopwords) is wrong for Japanese or Arabic. The recommended approach is to store per-locale fields on the single product document — e.g., title_en, title_ja, title_ar — each mapped with the appropriate analyzer (English stemmer, Kuromoji tokenizer for Japanese, ICU tokenizer for CJK characters in general). The search query targets the field matching the active locale. Language detection (using a library like langdetect or the ICU plugin) runs at index time to pick the right analyzer when the merchant has not explicitly specified a locale. Synonym dictionaries and autocomplete sub-fields are also per-locale. This avoids multiplying the number of Elasticsearch indices by language count, keeping cluster management feasible.语言特定的文本分析是核心需求：英语分析器（词干化、停用词）对日语或阿拉伯语完全不适用。推荐方案是在单个商品文档中存储每语言字段——如 title_en、title_ja、title_ar——每个字段使用相应的分析器（英语词干分析器、日语 Kuromoji tokenizer、CJK 通用 ICU tokenizer）。搜索查询针对与当前语言环境匹配的字段。语言检测（使用 langdetect 库或 ICU 插件）在索引时运行，在商家未明确指定语言环境时选择正确的分析器。同义词词典和自动补全子字段也是按语言区分的。这避免了 Elasticsearch 索引数量随语言数量成倍增加，保持集群管理的可行性。

How do you measure and continuously improve search relevance?如何衡量并持续提升搜索相关性？

Relevance improvement requires a closed feedback loop combining offline evaluation and online experimentation. Offline: curate a set of judged query–product pairs (human-labeled or sampled from merchant merchandising rules) and compute nDCG (Normalized Discounted Cumulative Gain) against the current ranking — this gives a stable, reproducible metric for comparing ranking changes. Online: run A/B tests on live traffic, measuring click-through rate (CTR), add-to-cart rate, and conversion rate on search result pages. Zero-result rate and search abandonment rate are leading indicators of relevance problems. The critical discipline is closing the loop: behavioral signals (clicks, purchases, zero-result queries) should feed back into the ranking model and synonym dictionaries on a regular cadence, so relevance improves automatically as query patterns evolve.相关性提升需要结合离线评估与在线实验的闭环反馈。离线：整理一组有标注的"查询-商品"对（人工标注或从商家选品规则中采样），针对当前排序计算 nDCG（归一化折损累积增益）——这提供了稳定、可复现的指标用于比较排序变更效果。在线：在真实流量上运行 A/B 测试，衡量搜索结果页面的点击率（CTR）、加购率和转化率。零结果率和搜索放弃率是相关性问题的领先指标。最关键的纪律是关闭反馈循环：行为信号（点击、购买、零结果查询）应定期回流到排序模型和同义词词典，使相关性随查询模式演化而自动提升。

  1. Decouple indexing from writes via CDC/outbox:通过 CDC/outbox 将索引与写入解耦： the Catalog Service never touches the search cluster; Kafka absorbs spikes and provides durability. Freshness is a deliberate eventual-consistency choice, not a bug. Catalog Service 从不直接操作搜索集群；Kafka 吸收流量峰值并提供持久性。新鲜度是有意为之的最终一致性选择，不是缺陷。
  2. Shared index + shop routing for the long tail, dedicated indices for whales:长尾使用共享索引 + 店铺路由，巨型商家使用专属索引： index-per-shop is operationally impossible at Shopify's merchant count; routing + mandatory shop_id filter gives isolation at low overhead. 在 Shopify 的商家体量下，每店铺独立索引在运维上不可行；路由 + 强制 shop_id 过滤器以低开销实现隔离。
  3. Relevance = BM25 + business boosts:相关性 = BM25 + 业务加权： in-stock, merchant pins, and historical popularity are injected at query time via function scores, keeping the base BM25 ranking clean and separately tunable. 库存状态、商家置顶和历史热度通过函数评分在查询时注入，保持基础 BM25 排序的清晰性和独立可调性。
  4. Alias swap is the only safe way to reindex:别名切换是唯一安全的重建索引方式： always build the new index alongside the live one, validate, and flip the alias atomically. Reindexing in place under live traffic risks data loss. 始终在线上索引旁边构建新索引，验证后原子性切换别名。在线上流量下原地重建索引存在数据丢失风险。
  5. Inventory in the index is an intentional staleness trade-off:索引中存储库存是有意为之的过时权衡： constant inventory updates can be propagated via the same CDC pipeline; if exact freshness is required, a lightweight join at query time is the safety valve. 持续的库存更新可通过同一 CDC 管道传播；若需要精确新鲜度，查询时的轻量级关联是安全阀。
